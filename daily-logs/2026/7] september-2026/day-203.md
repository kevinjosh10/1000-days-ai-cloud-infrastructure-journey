# 2. Linux Permissions Review

Linux permissions follow the:

```text
User → Group → Others
```

Example:

```text
-rwxr-x---
```

Breakdown:

```text
User:   rwx
Group:  r-x
Other:  ---
```

Octal representation:

```text
750
```

## Permission Values

```text
r = 4
w = 2
x = 1
```

| Permission | Octal |
| ---------- | ----: |
| `---`      |     0 |
| `--x`      |     1 |
| `-w-`      |     2 |
| `-wx`      |     3 |
| `r--`      |     4 |
| `r-x`      |     5 |
| `rw-`      |     6 |
| `rwx`      |     7 |

Examples:

```text
755 = rwxr-xr-x
644 = rw-r--r--
700 = rwx------
750 = rwxr-x---
```

# 3. World-Writable Files

A world-writable file allows the `other` permission group to write to it.

Example:

```text
-rw-rw-rw-
```

Octal:

```text
666
```

The final digit:

```text
6 = rw-
```

means other users can read and write the file.

A completely open file might have:

```text
-rwxrwxrwx
```

which is:

```text
777
```

## Why Is This Important?

A world-writable file can potentially be modified by users who should not have modification access.

For example:

```text
/opt/application/config.sh
```

If it is writable by everyone, another local user might modify its contents.

If a privileged service later executes that file, the consequences can be serious.

Therefore:

> World-writable files should be identified and reviewed.

## Find World-Writable Files

```bash
find /home -type f -perm -0002
```

More explicitly:

```bash
find /home -type f -perm -0002 -print
```

---

# 4. SUID

SUID stands for:

```text
Set User ID
```

SUID allows an executable to run with the effective privileges of the file owner.

Example:

```text
-rwsr-xr-x
```

Notice:

```text
s
```

instead of:

```text
x
```

## SUID Octal Value

```text
4000
```

## Find SUID Files

```bash
find / -type f -perm -4000 2>/dev/null
```

Some SUID files are completely legitimate.

Therefore:

```text
SUID ≠ automatically malicious
```

The goal is to identify unexpected or unusual SUID files for investigation.

---

# 5. SGID

SGID stands for:

```text
Set Group ID
```

SGID on an executable allows it to run with the effective group privileges of the file owner.

Example:

```text
-rwxr-sr-x
```

## SGID Octal Value

```text
2000
```

## Find SGID Files

```bash
find / -type f -perm -2000 2>/dev/null
```

---

# 6. SUID + SGID Audit

Find both:

```bash
find / -type f \( -perm -4000 -o -perm -2000 \) 2>/dev/null
```

The important security question is:

> Is this SUID/SGID file located somewhere expected?

Common standard locations include:

```text
/bin
/sbin
/usr/bin
/usr/sbin
```

A SUID/SGID executable appearing in locations such as:

```text
/home
/tmp
/custom application directories
```

should receive additional review.

The auditor should **report findings rather than automatically delete or modify them**.

# 7. Symbolic Links Review

A symbolic link points to another path.

Example:

```bash
ln -s /some/file mylink
```

Conceptually:

```text
mylink
   ↓
/some/file
```

A symbolic link becomes broken when its target no longer exists.

Example:

```text
mylink
   ↓
/some/file
     X
```

---

# 8. Find Broken Symlinks

Search `/opt`, `/home`, and `/var`:

```bash
find /opt /home /var -xtype l 2>/dev/null
```

Another approach:

```bash
find /opt /home /var -type l ! -exec test -e {} \; -print
```

Broken symlinks can indicate:

* Removed software
* Incomplete deployments
* Incorrect application paths
* Stale configuration
* Deployment problems

# 9. ACL Review

Traditional Linux permissions provide:

```text
Owner
Group
Others
```

Access Control Lists provide more granular permissions.

Example:

```text
user::rw-
user:bob:rwx
group::r--
mask::rwx
other::---
```

Here:

```text
user:bob:rwx
```

gives Bob additional access.

## View ACLs

```bash
getfacl filename
```

Example:

```bash
getfacl project.txt
```

---

# 10. Detect Extended ACLs

A `+` after the permissions in `ls -l` indicates extended ACL information.

Example:

```text
-rw-r-----+
```

The `+` means there are additional ACL entries.

You can inspect the ACL with:

```bash
getfacl filename
```

Important principle:

> The existence of an ACL does not automatically mean the file is insecure.

The auditor should look for unexpected or overly broad access, especially:

```text
rwx
```

on sensitive files.

# 11. Bash Defensive Scripting Review

Today's script should use:

```bash
#!/usr/bin/env bash

set -euo pipefail
```

## `set -e`

Exit when a command fails.

## `set -u`

Treat undefined variables as errors.

## `set -o pipefail`

Make a pipeline fail if an earlier command fails.

Together:

```bash
set -euo pipefail
```

help make scripts more predictable and safer.

# 15. World-Writable File Audit

Add:

```bash
echo "========================================" >> "$REPORT_FILE"
echo "WORLD-WRITABLE FILES" >> "$REPORT_FILE"
echo "========================================" >> "$REPORT_FILE"

    >> "$REPORT_FILE" 2>/dev/null || true
```

This searches `/home` for regular files with the world-write bit enabled.

# 18. ACL Audit

A starting point for finding files with extended ACLs:

```bash
echo >> "$REPORT_FILE"
echo "========================================" >> "$REPORT_FILE"
echo "FILES WITH EXTENDED ACLs" >> "$REPORT_FILE"
echo "========================================" >> "$REPORT_FILE"

find /home /opt /var -type f -exec ls -ld {} \; \
    2>/dev/null | grep '+' >> "$REPORT_FILE" || true
```

Files found here should be inspected with:

```bash
getfacl filename
```

The final auditor should distinguish ordinary ACL usage from ACLs that grant unexpectedly broad access.
