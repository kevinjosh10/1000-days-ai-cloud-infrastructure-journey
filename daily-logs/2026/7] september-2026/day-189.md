## 1. The Probes (Liveness, Readiness, Startup)

I learned that Kubernetes doesn't actually know if my application is working—it only knows if the container process is running. If my API gets stuck in a deadlock, the process is still "running", so Kubernetes won't restart it. 

I fixed this by configuring Probes:
* **Liveness Probe:** "Are you alive?" If this fails, the `kubelet` forcefully kills the container and restarts it.
* **Readiness Probe:** "Are you ready to take traffic?" If this fails, the Pod is removed from the Service's load-balancing pool so users don't get 502 errors.
* **Startup Probe:** "Have you finished booting?" Useful for slow-starting applications (like massive ML model loading) to prevent the Liveness probe from killing it prematurely.

## 2. Zero-Downtime Rolling Updates

I took control of exactly *how* Kubernetes updates my deployments. The default `RollingUpdate` strategy is good, but I enforced mathematical perfection:
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```
This guarantees absolute zero downtime. Kubernetes will spin up 1 new Pod (`maxSurge`), wait for its Readiness Probe to pass, and only then will it kill 1 old Pod (because I strictly defined that 0 Pods are allowed to be unavailable).

## 3. LimitRanges: The Safety Net

Earlier this week, I learned about resource Limits and Requests. But what if a developer forgets to add them to their YAML? A rogue Pod could still crash a node.

I deployed a **LimitRange** into my `development` namespace. 
Now, if a Pod is submitted without resource blocks, Kubernetes automatically injects defaults: `100m` CPU request and `128Mi` memory request. This is how cluster administrators protect the cluster from careless users.

## 5. The Kustomize Architecture

Finally, I organized all the YAML I've written over the last two weeks. I adopted the **Kustomize** pattern, which is the industry standard for managing environments without duplicating YAML.

I structured my repository like this:
```text
kubernetes/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   ├── configmap-dev.yaml
    │   └── kustomization.yaml (points to base)
    └── prod/
        ├── configmap-prod.yaml
        ├── hpa.yaml
        └── kustomization.yaml (points to base)
```
This structure allows me to reuse the core `base` deployment while injecting environment-specific configurations (like an HPA in Prod, but not in Dev).

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is the difference between a Liveness Probe and a Readiness Probe?**
   > A Liveness Probe restarts the container if it fails. A Readiness Probe merely stops routing traffic to it if it fails.
2. **How do you guarantee zero downtime during a deployment update?**
   > By using a `RollingUpdate` strategy with `maxUnavailable` set to `0` and a properly configured Readiness Probe.
3. **What is a LimitRange?**
   > A policy applied to a Namespace that enforces default CPU/Memory requests and limits for any Pod that forgets to specify them.
4. **Why use Pod Anti-Affinity?**
   > To explicitly instruct the Scheduler to spread Replicas across different physical worker nodes, preventing a single EC2 outage from taking down the entire application.
5. **What is the Kustomize `base` and `overlays` pattern?**
   > It is a directory structure that allows you to define core Kubernetes resources in a `base` folder, and then use `overlays` to apply environment-specific patches (like Dev vs Prod configs) without duplicating the YAML.
