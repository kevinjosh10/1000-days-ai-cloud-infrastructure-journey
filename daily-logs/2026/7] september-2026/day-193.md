## 1. Advanced StorageClasses with EBS CSI Driver (`gp3`)

In AWS EKS, creating a storage class without parameters leaves performance on the table and creates security risks. I wrote an optimized `StorageClass` using the AWS EBS CSI driver:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-gp3-secure
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
```

### Key Takeaways:
* **`gp3` vs `gp2`:** `gp3` provides 20% lower cost per GB with baseline 3,000 IOPS and 125 MB/s throughput decoupled from volume size.
* **`encrypted: 'true'`:** Enforces KMS encryption at rest automatically for every newly carved EBS block device.
* **`allowVolumeExpansion: true`:** Enables expanding PVC sizes dynamically without taking down the running Pod.

## 2. Solving the AZ Trap: `WaitForFirstConsumer`

I discovered a subtle and dangerous failure mode when using AWS EBS volumes in multi-AZ clusters:
* **`volumeBindingMode: Immediate` (Default):** As soon as a PVC is created, Kubernetes immediately provisions an EBS volume in a random Availability Zone (e.g., `us-east-1a`). Later, if the `kube-scheduler` places the Pod on a node in `us-east-1b`, the Pod gets stuck forever in `ContainerCreating` because **EBS volumes cannot cross AZ boundaries**.
* **`volumeBindingMode: WaitForFirstConsumer` (Best Practice):** Delays EBS volume provisioning until the Pod is actually scheduled on a specific node. The CSI driver then creates the EBS volume in the *exact same AZ* where the Pod is running.

## 3. StatefulSet Dynamic Storage: `volumeClaimTemplates`

When scaling stateful applications (like a 3-node PostgreSQL cluster or Elasticsearch), a standard Deployment sharing a single PVC fails because EBS block storage only supports `ReadWriteOnce` (RWO).

Instead, I used `volumeClaimTemplates` inside a `StatefulSet`:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres-cluster
spec:
  serviceName: "postgres-svc"
  replicas: 3
  template:
    ...
  volumeClaimTemplates:
  - metadata:
      name: pgdata
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: ebs-gp3-secure
      resources:
        requests:
          storage: 20Gi
```

When this is applied, Kubernetes automatically creates dedicated, isolated PVCs for each replica: `pgdata-postgres-cluster-0`, `pgdata-postgres-cluster-1`, and `pgdata-postgres-cluster-2`. Even if the StatefulSet is deleted, these PVCs remain intact to prevent accidental data loss.

## 4. Point-in-Time Backups with `VolumeSnapshot`

Backing up Kubernetes block storage used to require custom scripts. With the Kubernetes CSI Snapshotter, I can capture native point-in-time EBS snapshots declaratively.

1. **Define the `VolumeSnapshotClass`:**
   ```yaml
   apiVersion: snapshot.storage.k8s.io/v1
   kind: VolumeSnapshotClass
   metadata:
     name: ebs-snapshot-class
   driver: ebs.csi.aws.com
   deletionPolicy: Retain
   ```
2. **Create the `VolumeSnapshot`:**
   ```yaml
   apiVersion: snapshot.storage.k8s.io/v1
   kind: VolumeSnapshot
   metadata:
     name: pg-backup-snapshot
   spec:
     volumeSnapshotClassName: ebs-snapshot-class
     source:
       persistentVolumeClaimName: pgdata-postgres-cluster-0
   ```

## 5. Hands-On Disaster Recovery Drill

I tested the full backup and restore loop with PostgreSQL:

1. **Populate Data:** Deployed PostgreSQL, connected via `kubectl exec`, and inserted records into a `users` table.
2. **Snapshot:** Applied the `VolumeSnapshot` manifest to capture the underlying EBS volume state.
3. **Simulate Disaster:** Dropped the table inside PostgreSQL.
4. **Restore to New PVC:** Created a fresh PVC referencing the snapshot as its `dataSource`:
   ```yaml
   apiVersion: v1
   kind: PersistentVolumeClaim
   metadata:
     name: pgdata-restored-pvc
   spec:
     storageClassName: ebs-gp3-secure
     dataSource:
       name: pg-backup-snapshot
       kind: VolumeSnapshot
       apiGroup: snapshot.storage.k8s.io
     accessModes:
       - ReadWriteOnce
     resources:
       requests:
         storage: 20Gi
   ```
5. **Validation:** Mounted `pgdata-restored-pvc` to a new PostgreSQL pod and queried the database. **All user records were 100% restored.**

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **Why should you use `WaitForFirstConsumer` instead of `Immediate` binding mode?**
   > `WaitForFirstConsumer` delays volume provisioning until the Pod is assigned to a node, ensuring the cloud block storage (EBS) is created in the exact Availability Zone where the node resides.
2. **What advantages does `gp3` offer over `gp2` in AWS EKS?**
   > `gp3` delivers predictable baseline performance (3,000 IOPS and 125 MB/s) independently of volume size, while being approximately 20% cheaper per gigabyte than `gp2`.
3. **How do `volumeClaimTemplates` work in a StatefulSet?**
   > They automatically stamp out a unique, persistent PVC for each sequential Pod ordinal (`pod-0`, `pod-1`), ensuring stateful replicas maintain independent storage lifecycles.
4. **What happens to PVCs created by a StatefulSet when the StatefulSet is deleted?**
   > By default, the PVCs are intentionally retained to prevent catastrophic data loss during rollouts or scale-downs.
5. **How does Kubernetes restore a volume from a `VolumeSnapshot`?**
   > By specifying the `VolumeSnapshot` name and kind inside the `spec.dataSource` block of a new PersistentVolumeClaim.
