# 🧠 1. What Is an Inode?

An **inode** is a filesystem data structure containing metadata about a filesystem object.

An inode typically contains:

* File type
* Permissions
* Owner UID
* Group GID
* File size
* Timestamps
* Link count
* References to data blocks

The filename is **not normally stored inside the inode**.

A useful mental model:

```text
Filename
    │
    ▼
Directory Entry
    │
    ▼
  INODE
    │
    ├── Permissions
    ├── Owner
    ├── Group
    ├── Size
    ├── Timestamps
    ├── Link Count
    └── Data Block References
```

# ⏱️ 4. Linux File Timestamps

Linux commonly exposes three important timestamps.

## Access Time — atime

The last time the file was accessed/read.

Example:

```bash
cat cloud.txt
```

Check:

```bash
stat cloud.txt
```

Look at:

```text
Access:
```

Remember:

```text
ATIME = Access
```

Modern Linux systems often use `relatime`, so access-time updates may not happen on every read.

---

## Modify Time — mtime

The time when the **contents of the file were modified**.

Example:

```bash
echo "Day 199" >> cloud.txt
```

Then:

```bash
stat cloud.txt
```

The `Modify` timestamp changes.

Remember:

```text
MTIME = Content Modified
```

---

## Change Time — ctime

The time when the file's **metadata/status changed**.

For example:

```bash
chmod 600 cloud.txt
```

The contents did not change.

But the permissions changed.

Therefore:

```text
mtime → generally unchanged
ctime → changed
```

Important:

> `ctime` does NOT mean creation time.

Remember:

```text
ATIME → Access
MTIME → Content modification
CTIME → Metadata/status change
```

# 🔗 5. Hard Links

A hard link is another directory entry pointing to the **same inode**.

Create a file:

```bash
echo "Cloud Engineer" > original.txt
```

Create a hard link:

```bash
ln original.txt hardlink.txt
```

Check both:

```bash
ls -li original.txt hardlink.txt
```

Example:

```text
123456 -rw-r--r-- 2 user user 15 ... original.txt
123456 -rw-r--r-- 2 user user 15 ... hardlink.txt
```

Both files have:

```text
Same inode number
```

---

# 🧠 6. How Hard Links Work

Conceptually:

```text
original.txt ─────┐
                  │
                  ▼
               INODE
                  │
                  ▼
                 DATA
                  ▲
                  │
hardlink.txt ─────┘
```

There are two filenames but only one underlying inode/data object.

The hard-link count becomes:

```text
Links: 2
```

Check:

```bash
stat original.txt
```

---

# 🗑️ 7. Deleting a Hard Link

Delete the original:

```bash
rm original.txt
```

Now:

```bash
cat hardlink.txt
```

The file still works.

Why?

Because the inode still has another directory entry pointing to it.

```text
hardlink.txt
      │
      ▼
   INODE
      │
      ▼
    DATA
```

The underlying data is removed only after the inode no longer has directory links and no relevant open references remain.

---

# ⚠️ 8. Hard-Link Restrictions

Hard links generally:

* Cannot cross filesystems
* Cannot normally be created for directories
* Point directly to an inode

Why can't they cross filesystems?

Because an inode belongs to a specific filesystem.

Conceptually:

```text
Filesystem A
    │
    └── inode 123

Filesystem B
    │
    └── cannot hard-link to inode 123
```

---

# 🔗 9. Symbolic Links

A symbolic link, or symlink, is a special filesystem object that points to another path.

Create:

```bash
echo "AWS Linux Infrastructure" > target.txt
```

Create a symlink:

```bash
ln -s target.txt symlink.txt
```

Check:

```bash
ls -li target.txt symlink.txt
```

The inode numbers will be different.

Example:

```text
111111 -rw-r--r-- target.txt
222222 lrwxrwxrwx symlink.txt -> target.txt
```

The `l` at the beginning indicates a symbolic link.

---

# 🧠 10. How Symlinks Work

Conceptually:

```text
symlink.txt
     │
     ▼
  INODE B
     │
     ▼
"target.txt"
     │
     ▼
  INODE A
     │
     ▼
   DATA
```

Unlike a hard link, a symlink has its **own inode**.

It stores/references a pathname to its target.

---

# 💥 11. Broken Symlinks

Delete the target:

```bash
rm target.txt
```

Now:

```bash
cat symlink.txt
```

The command fails because the target no longer exists.

The symlink is now **broken**.

Check:

```bash
ls -l symlink.txt
```

You may see:

```text
symlink.txt -> target.txt
```

but `target.txt` no longer exists.

---

# 🔎 12. Finding Broken Symlinks

Use:

```bash
find . -type l ! -exec test -e {} \; -print
```

Breakdown:

```text
find .
```

Search current directory.

```text
-type l
```

Find symbolic links.

```text
! -exec test -e {} \;
```

Select links whose target does not exist.

```text
-print
```

Print the broken links.

# ⚖️ 13. Hard Link vs Symbolic Link

| Feature                          | Hard Link | Symbolic Link |
| -------------------------------- | --------- | ------------- |
| Shares inode?                    | Yes       | No            |
| Own inode?                       | No        | Yes           |
| Points to                        | Inode     | Path          |
| Cross filesystem?                | No        | Yes           |
| Survives target deletion?        | Yes       | No            |
| Can become broken?               | No        | Yes           |
| Normally works with directories? | No        | Yes           |
| `ls -li` inode                   | Same      | Different     |

Mental model:

```text
HARD LINK

name A ──┐
         ├──► SAME INODE
name B ──┘
```

```text
SYMLINK

name A ──► INODE A

name B ──► INODE B ──► "name A"
```

---

# 🏗️ 14. When to Use Hard Links

Hard links are useful when multiple filenames should reference the same underlying file data.

Example:

```text
file1 ──┐
        ├──► SAME INODE
file2 ──┘
```

Deleting one filename doesn't destroy the underlying file as long as another hard link remains.

---

# 🏗️ 15. When to Use Symbolic Links

Symbolic links are extremely common in Linux administration.

Examples include:

* Application deployments
* Configuration paths
* Version management
* Shared libraries
* Executable paths
* Current-release pointers

Example deployment structure:

```text
app/
├── releases/
│   ├── v1/
│   ├── v2/
│   └── v3/
│
└── current -> releases/v3
```

The `current` symlink can be changed to point to another release.

# 📊 17. `df` vs `du`

This distinction is important for cloud engineering.

## `df`

Shows filesystem-level disk usage:

```bash
df -h
```

Think:

```text
How much space is available on the filesystem?
```

## `du`

Shows usage by files/directories:

```bash
du -sh /var/log
```

Think:

```text
Which files/directories are consuming the space?
```

Mental model:

```text
df
↓
Filesystem-level usage

du
↓
File/directory-level usage
```

# ☁️ 18. Cloud Engineering Connection

These concepts matter directly on Linux servers.

Example:

```text
AWS EC2
   │
   ▼
EBS Volume
   │
   ▼
Linux Filesystem
   │
   ├── Files
   ├── Directories
   ├── Inodes
   ├── Links
   └── Data Blocks
```

If an EC2 server reports:

```text
No space left on device
```

I need to investigate using:

```bash
df -h
du -sh /*
df -i
```

The last command:

```bash
df -i
```

is also useful because a filesystem can run out of **inodes** even when it still has some disk space available.

# 🔍 24. Finding Hard-Link Candidates

Use inode numbers:

```bash
find . -type f -printf '%i %p\n'
```

Example:

```text
12345 ./file1
12345 ./file2
67890 ./file3
```

Here:

```text
file1
file2
```

share inode `12345`.

Therefore they are multiple directory entries referencing the same inode.

A useful auditor should report them as:

```text
Same inode / hard-link candidates
```

---

# ⚠️ 25. Important Terminology

Don't confuse:

```text
Same content
```

with:

```text
Same inode
```

Example:

```text
file1 → inode 100 → "hello"
file2 → inode 200 → "hello"
```

These files have identical content but are separate filesystem objects.

Hard links:

```text
file1 ──┐
        ├──► inode 100 → "hello"
file2 ──┘
```

These are multiple names for the same underlying file.
