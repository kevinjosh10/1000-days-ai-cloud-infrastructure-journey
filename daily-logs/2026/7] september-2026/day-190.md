## 1. The 4 Fundamental Rules of K8s Networking

Kubernetes is incredibly opinionated about networking. I learned that any cluster must satisfy four absolute rules:
1. Every Pod must get its own unique IP address.
2. Pods on any node must be able to communicate with Pods on *any other node* **without** NAT (Network Address Translation).
3. Agents on a node (like `kubelet`) can communicate with all Pods on that node.
4. A Pod's IP address must be exactly what other Pods see (no SNAT masquerading).

This creates a massive, flat IP network where every container can talk to every other container, bypassing the physical restrictions of the EC2 worker nodes they live on.

## 2. CNI: Container Network Interface

Kubernetes doesn't actually implement these 4 rules itself. It delegates the job to a **CNI plugin**.
I researched the industry standards:
* **Flannel:** Simple, uses VXLAN overlay.
* **Calico:** The legacy enterprise standard. Uses BGP routing and supports complex Network Policies.
* **Cilium:** The modern, ultra-high-performance standard. Uses eBPF (extended Berkeley Packet Filter) directly in the Linux kernel to route packets at blazing speeds.

*(In AWS EKS, the default is the AWS VPC CNI, which literally assigns real AWS VPC IP addresses directly to Pods, bypassing overlay networks entirely!)*

## 3. Pod-to-Pod Communication Mechanics

I mapped out exactly how a packet travels:
* **Same Node:** If Pod A talks to Pod B on the same EC2 instance, the traffic travels via a virtual ethernet (`veth`) pair across a Linux bridge. It never hits the physical network interface.
* **Different Nodes:** If Pod A talks to Pod C on a different EC2 instance, the CNI plugin encapsulates the packet (putting the Pod IP packet inside an EC2 IP packet using an overlay tunnel like VXLAN), sends it across the physical AWS network, and unpackages it on the destination node.

## 4. Internal DNS (CoreDNS)

I learned that every Service automatically gets a fully qualified domain name (FQDN) managed by **CoreDNS**. The format is always:
`<service-name>.<namespace>.svc.cluster.local`

I proved this by spinning up a debug pod:
```bash
kubectl run -it debug --image=busybox -- sh
```
Inside the pod, I ran:
```bash
nslookup kubernetes.default.svc.cluster.local
```
It immediately resolved to the internal API server IP (`10.96.0.1`). This is how microservices find each other dynamically without hardcoded IPs.

## 5. Demystifying ClusterIP (kube-proxy)

The biggest revelation of the day was understanding how `ClusterIP` actually works.
A ClusterIP is a *fake* IP address. It doesn't belong to any physical network interface. 

When I create a Service, **`kube-proxy`** (running as a DaemonSet on every node) watches the API server. It immediately writes native Linux `iptables` (or IPVS) rules on every single node. 
When my frontend Pod sends a packet to the `ClusterIP`, the Linux kernel intercepts it, reads the `iptables` rule, and rewrites the destination IP (DNAT) to a random, healthy backend Pod IP. 

The application has no idea this rewriting just happened. The magic is just `iptables`.

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is a CNI plugin?**
   > Container Network Interface. It is the third-party software (like Calico or Cilium) responsible for assigning Pod IPs and maintaining the flat pod-to-pod overlay network.
2. **How do Pods on different nodes communicate?**
   > The CNI creates an overlay network (usually via VXLAN encapsulation or BGP) that tunnels Pod traffic across the physical node network.
3. **What is the standard DNS format for a Kubernetes Service?**
   > `service-name.namespace.svc.cluster.local`
4. **Is a Service ClusterIP a real network interface?**
   > No, it is a virtual IP. It only exists as an `iptables` (or IPVS) routing rule managed by `kube-proxy`.
5. **How does traffic actually get load-balanced across multiple Pods?**
   > When traffic hits the `iptables` rules for a ClusterIP, Linux randomly selects one of the backend Pod IPs (based on the Service endpoints) and performs Destination NAT (DNAT).
