---

## 1. The Ingress Paradigm: Resource vs. Controller

I learned a fundamental architectural distinction that trips up many beginners:
* **The Ingress Resource:** A declarative YAML file where I define HTTP/HTTPS routing rules (hostnames, paths, backend services, and TLS certificates).
* **The Ingress Controller:** The actual reverse proxy running inside the cluster (like NGINX, Traefik, or AWS ALB) that watches for Ingress resources and dynamically updates its routing configuration.

Kubernetes does **not** include an Ingress Controller out-of-the-box. Without an active controller, creating an Ingress resource does absolutely nothing.

## 3. Host-Based & Path-Based Routing

I wrote an Ingress manifest demonstrating both host-based and path-based routing under a single configuration:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  # Host-Based Routing (Subdomains)
  - host: api.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
  # Path-Based Routing on main domain
  - host: www.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
      - path: /analytics
        pathType: Prefix
        backend:
          service:
            name: analytics-service
            port:
              number: 80
```

With this single Ingress configuration, external clients can hit `api.myapp.com` or `www.myapp.com/analytics`, and the Ingress Controller seamlessly proxies traffic to the appropriate backend `ClusterIP` services.

## 4. Securing Ingress with TLS Secrets

Production web traffic requires encryption in transit. I practiced setting up SSL/TLS termination right at the Ingress boundary:

1. Generated TLS private keys and certificates, then created a Kubernetes TLS Secret:
   ```bash
   kubectl create secret tls my-tls-secret --cert=tls.crt --key=tls.key
   ```
2. Attached the Secret directly to the Ingress resource:
   ```yaml
   spec:
     tls:
     - hosts:
       - www.myapp.com
       - api.myapp.com
       secretName: my-tls-secret
   ```

In cloud environments, this process is fully automated using **cert-manager** along with Let's Encrypt or AWS Certificate Manager (ACM), automatically issuing and renewing certificates without manual intervention.

## 5. Supercharging Behavior with Annotations

The Ingress specification in Kubernetes is deliberately generic. To unlock vendor-specific features of the NGINX Ingress Controller, I used **annotations**:

* `nginx.ingress.kubernetes.io/rewrite-target: /` — Rewrites the URI path before forwarding to the upstream service.
* `nginx.ingress.kubernetes.io/ssl-redirect: 'true'` — Automatically forces HTTP requests to redirect to HTTPS.
* `nginx.ingress.kubernetes.io/proxy-body-size: '100m'` — Increases the upload payload limit (vital for AI applications that upload images or datasets for inference).

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is the difference between an Ingress resource and an Ingress Controller?**
   > An Ingress resource is just a declarative configuration manifest specifying routing rules. The Ingress Controller is the running reverse proxy (e.g., NGINX) that executes those rules.
2. **Why use an Ingress Controller instead of individual `LoadBalancer` Services?**
   > Cost and efficiency. A single Ingress Controller exposes dozens of backend services behind a single cloud load balancer and IP address using Layer 7 host and path rules.
3. **What is the difference between host-based and path-based routing?**
   > Host-based routing routes requests based on the HTTP `Host` header (e.g., `api.example.com` vs `app.example.com`). Path-based routing routes based on the URL path (e.g., `example.com/api` vs `example.com/web`).
4. **How is TLS encryption handled at the Ingress layer?**
   > By referencing a `kubernetes.io/tls` secret in the `spec.tls` block. The Ingress Controller terminates the SSL connection at the edge before forwarding unencrypted traffic to internal ClusterIP services.
5. **What role do annotations play in Ingress manifests?**
   > Annotations allow configuring controller-specific behaviors (such as SSL redirection, URL rewriting, rate limiting, and request payload size limits) that aren't part of the core Kubernetes Ingress API.
