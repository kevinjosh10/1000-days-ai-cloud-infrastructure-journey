## 1. The Production-Ready Helm Stack

I orchestrated a complete multi-tier application stack inside an isolated namespace (`production-app`) on Minikube:

* **Custom Flask API:** Deployed using my authored Helm chart with strict requests/limits (`cpu: 100m/500m`, `memory: 128Mi/512Mi`).
* **Relational Database (PostgreSQL):** Installed via Bitnami chart with persistent volume claim backing:
  ```bash
  helm install app-db bitnami/postgresql \
    --namespace production-app \
    --set auth.database=appdb \
    --set primary.persistence.size=10Gi \
    --set primary.resources.requests.cpu=200m
  ```
* **In-Memory Cache (Redis):** Installed via Bitnami chart for caching and session state:
  ```bash
  helm install app-cache bitnami/redis \
    --namespace production-app \
    --set architecture=standalone \
    --set master.persistence.enabled=true
  ```
* **NGINX Ingress Controller:** Managed L7 path and host routing with SSL redirection into the cluster.

## 2. Zero-Trust Hardening with NetworkPolicies

With the stack running, I locked down the entire `production-app` namespace with granular firewalls:

1. **Default-Deny:** Applied a blanket deny on all Ingress and Egress for all Pods (`podSelector: {}`).
2. **Ingress to Flask API:** Allowed traffic from NGINX Ingress controller pods exclusively to port `5000`.
3. **API to PostgreSQL:** Allowed egress from `app.kubernetes.io/name: flask-api` to `app.kubernetes.io/name: postgresql` strictly on TCP `5432`.
4. **API to Redis:** Allowed egress from the Flask API to Redis strictly on TCP `6379`.
5. **The CoreDNS Lifeline:** Whitelisted egress to `kube-system` on UDP/TCP port `53` so microservices could resolve `app-db-postgresql.production-app.svc.cluster.local`.

## 3. Dynamic Scaling: Conditional HPA in Custom Chart

I enhanced my `my-flask-api` Helm chart by adding a modular Horizontal Pod Autoscaler template in `templates/hpa.yaml`:

```yaml
{{- if .Values.autoscaling.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ include "my-flask-api.fullname" . }}
  labels:
    {{- include "my-flask-api.labels" . | nindent 4 }}
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ include "my-flask-api.fullname" . }}
  minReplicas: {{ .Values.autoscaling.minReplicas }}
  maxReplicas: {{ .Values.autoscaling.maxReplicas }}
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.autoscaling.targetCPUUtilizationPercentage }}
{{- end }}
```

In `values.yaml`, I enabled it declaratively:
```yaml
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70
```

## 4. Publishing My Helm Chart to GitHub Pages

I turned my GitHub profile into a public, globally accessible Helm repository:

1. **Package the Chart:**
   ```bash
   helm package ./my-flask-api
   # Output: Successfully packaged chart and saved it to: ./my-flask-api-0.1.0.tgz
   ```
2. **Generate the Repository Index:**
   ```bash
   helm repo index . --url https://kevinjosh10.github.io/helm-charts
   ```
3. **Publish to GitHub Pages:**
   Pushed `index.yaml` and `my-flask-api-0.1.0.tgz` to the `gh-pages` branch of my repository.

Now, anyone in the world (or my CI/CD runner) can add my repository and install my microservice chart with:
```bash
helm repo add kevin-charts https://kevinjosh10.github.io/helm-charts
helm repo update
helm install my-api kevin-charts/my-flask-api
```

| **8** | What happens if a NetworkPolicy is applied in a cluster with a basic Flannel CNI? | The policy is accepted by the API server but silently ignored; no traffic is blocked. |
| **9** | What does an empty `podSelector: {}` in a NetworkPolicy mean? | It selects all Pods in the target namespace (often used for default-deny). |
| **10** | What critical egress rule must be added when applying default-deny to a namespace? | Egress to CoreDNS on UDP/TCP port 53 (usually in `kube-system`), otherwise service name resolution breaks. |
| **11** | What is the difference between an Ingress Resource and an Ingress Controller? | An Ingress resource defines Layer 7 routing rules; the Ingress Controller is the reverse proxy (e.g. NGINX) that executes them. |
| **12** | How do you specify host-based routing in an Ingress manifest? | Use the `spec.rules[].host` field (e.g., `api.example.com`). |
| **13** | How do you force HTTPS redirection in NGINX Ingress? | Add annotation: `nginx.ingress.kubernetes.io/ssl-redirect: "true"`. |
| **14** | Where are TLS certificates stored for an Ingress resource? | In a Secret of type `kubernetes.io/tls` containing `tls.crt` and `tls.key`. |
| **15** | What are the three core files/directories in a Helm chart? | `Chart.yaml` (metadata), `values.yaml` (defaults), and `templates/` (manifest templates). |
| **16** | What does the `nindent` function do in Helm templates? | Prepends a newline and indents the rendered string by $N$ spaces to maintain valid YAML formatting. |
| **17** | What does `toYaml` do in Helm? | Converts Go objects, maps, or arrays into valid YAML formatting. |
| **18** | What is the purpose of `templates/_helpers.tpl`? | Defines reusable named template partials (`define`) that can be included (`include`) across manifests to follow DRY principles. |
| **19** | How do you test a Helm chart locally without contacting the cluster? | Run `helm template <release-name> <chart-path>`. |
| **20** | How do you simulate a server-side Helm deployment? | Run `helm install <release-name> <chart-path> --dry-run`. |
| **21** | How does Helm track releases inside the cluster? | Stores release metadata as versioned Kubernetes Secrets in the release namespace. |
| **22** | How do you roll back a Helm release to revision 2? | `helm rollback <release-name> 2`. |
| **23** | What tool turns a directory of packaged charts into a valid Helm repository? | `helm repo index <directory-path> --url <repo-url>`. |
| **24** | What is the difference between Liveness and Readiness probes? | Liveness probe restarts a failed container; Readiness probe temporarily stops sending traffic to a container until it passes. |
| **25** | How do you configure zero-downtime rolling updates in a Deployment? | Use `strategy.type: RollingUpdate` with `maxUnavailable: 0` and `maxSurge: 1` alongside valid Readiness probes. |

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **How do you build a secure, zero-trust microservice architecture in Kubernetes?**
   > Deploy services in dedicated namespaces, enforce default-deny NetworkPolicies, explicitly whitelist port-specific ingress/egress between dependent tiers, and preserve port 53 egress for CoreDNS.
2. **How does an Ingress Controller work with backend services and NetworkPolicies?**
   > The Ingress Controller acts as the Layer 7 edge router. NetworkPolicies must explicitly allow ingress from the Ingress Controller's pod IP/labels to the backend service's target port.
3. **Why package applications as Helm charts instead of raw manifests?**
   > Helm introduces variable parameterization, environment-specific `values.yaml` files, atomic rollouts, release versioning, rollback history, and dependency management.
4. **How do you host your own Helm chart repository without dedicated server infrastructure?**
   > Package charts with `helm package`, generate an `index.yaml` pointing to a static hosting URL with `helm repo index`, and serve both files via GitHub Pages or an AWS S3 bucket.
5. **When does HPA trigger a scale-up vs scale-down?**
   > HPA polls the `metrics-server` every 15 seconds. If average CPU/memory exceeds target utilization, it scales up immediately. When load drops, it observes a default 5-minute stabilization window before scaling down to prevent thrashing.
