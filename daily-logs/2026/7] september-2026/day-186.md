Containers are inherently stateless. When a Pod dies, anything written to its local filesystem dies with it. Today, I solved the persistence problem by mastering the Kubernetes storage abstraction layer: **PVs, PVCs, and StorageClasses.**

## 1. The Storage Abstraction Triangle

Just like Kubernetes abstracts compute (Pods instead of containers) and networking (Services instead of IP addresses), it completely abstracts storage.

I learned the three core components:
* **PersistentVolume (PV):** The actual, physical slice of storage (like an AWS EBS volume).
* **PersistentVolumeClaim (PVC):** A ticket or request submitted by a user for storage.
* **StorageClass (SC):** The automated factory that dynamically builds PVs when a PVC is submitted.

## 2. The Dynamic Lifecycle

I traced the exact lifecycle of how storage attaches to a Pod:
1. I submit a PVC requesting `10Gi` of storage.
2. The API Server looks at the `StorageClass` attached to the PVC.
3. The `StorageClass` dynamically provisions a real PV (talking to the AWS API to create an EBS volume).
4. The PVC **binds** to the PV.
5. My Pod mounts the PVC as a volume.
6. If the PVC is deleted, the `ReclaimPolicy` determines if the physical EBS volume is `Retained` (saved) or `Deleted` (destroyed).

## 3. StorageClasses (The AWS Connection)

I practiced defining a `StorageClass` specifically for AWS EKS:
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3-encrypted
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  encrypted: "true"
```
Instead of manually going into the AWS Console to create an EBS volume, this YAML ensures that anytime I ask for storage, Kubernetes automatically creates an encrypted, high-performance `gp3` drive for me. (In Minikube, I just enabled the `storage-provisioner` addon to simulate this locally).

## 4. Writing the PVC and Pod Mount

I wrote the manifest to claim my storage:
```yaml
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: my-database-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: gp3-encrypted
  resources:
    requests:
      storage: 10Gi
```
And then injected it into my Pod:
```yaml
    volumes:
      - name: data-volume
        persistentVolumeClaim:
          claimName: my-database-pvc
```

## 5. The Critical Trap: Access Modes

I learned a massive architectural constraint regarding **Access Modes**:
* **ReadWriteOnce (RWO):** The volume can only be mounted as read-write by a *single worker node* at a time.
* **ReadOnlyMany (ROX):** Many nodes can mount the volume, but only to read.
* **ReadWriteMany (RWX):** Many nodes can mount the volume to read and write simultaneously.

**The Golden Rule:** AWS EBS volumes *only* support `ReadWriteOnce`. If I have a Deployment with 3 Replicas spanning across 3 different EC2 nodes, they **cannot** share the same EBS volume. If I need shared multi-node storage (RWX), I must use AWS EFS (Elastic File System). This is a classic CKA exam trap!

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is the difference between a PV and a PVC?**
   > A PV is the actual physical storage resource. A PVC is a request ticket for storage. A Pod mounts the PVC, not the PV directly.
2. **What does a StorageClass do?**
   > It acts as a template for dynamically provisioning PersistentVolumes on demand, eliminating the need for administrators to pre-provision storage manually.
3. **What is `ReadWriteOnce`?**
   > An Access Mode stating the volume can be mounted as read-write by only one Node at a time. Standard block storage (like AWS EBS) is strictly RWO.
4. **How do you achieve shared `ReadWriteMany` storage in AWS Kubernetes?**
   > You cannot use EBS. You must use a network file system like AWS EFS.
5. **What happens to the physical drive when a PVC is deleted?**
   > It depends on the `ReclaimPolicy` set on the PV (usually defined by the StorageClass). It will either be `Deleted` (destroyed) or `Retained` (kept for manual recovery).
