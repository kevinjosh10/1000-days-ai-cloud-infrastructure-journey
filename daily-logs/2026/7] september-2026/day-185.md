A few weeks ago, I learned how to limit resources on a single Docker container. Today, I translated that knowledge into Kubernetes, learning the exact mechanics of how the cluster schedules and throttles workloads across hundreds of nodes.

## 1. Requests: The Scheduler's Blueprint

In Kubernetes, a **Request** is the *minimum guaranteed* amount of CPU or RAM a container needs to function. 
I learned that the `kube-scheduler` relies exclusively on Requests to do its job. If I request `500m` of CPU (half a core) and `1Gi` of memory, the Scheduler scans all the worker nodes. If no single node has that much free capacity, the Pod remains forever stuck in the `Pending` state.

## 2. Limits: The Execution Guardrails

A **Limit** is the absolute *maximum* ceiling a container is allowed to consume.
The consequences of hitting a limit depend entirely on the resource type:
* **CPU Limit Exceeded:** The container is *throttled*. The kernel literally slows the container down, but it keeps running.
* **Memory Limit Exceeded:** The container is violently terminated by the Linux kernel with an `OOMKilled` (Out of Memory) error, and the `kubelet` attempts to restart it.

## 3. Writing Resource Specs

I practiced injecting these definitions directly into my Deployment manifests. I also learned the crucial difference between Kubernetes units: `1000m` equals 1 full CPU core, and I must use `Mi` (Mebibytes) instead of `MB` for accurate memory allocation.

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"
```

## 4. Quality of Service (QoS) Classes

This was the most fascinating architectural discovery of the day. Kubernetes automatically assigns a QoS class to every Pod based purely on how I configure Requests and Limits. When a worker node runs out of memory, the `kubelet` uses these classes to decide who to kill first:

1. **Guaranteed:** Requests exactly equal Limits for all containers in the Pod. (Highest priority; last to be killed).
2. **Burstable:** Requests are strictly less than Limits. (Middle priority).
3. **BestEffort:** No Requests or Limits are set at all. (Lowest priority; these are evicted immediately under pressure).

To run mission-critical AI inference without interruption, I must ensure my Pods achieve **Guaranteed** QoS status.

## 5. Live Chaos Testing

To prove all of this, I deliberately built a Pod designed to fail. I wrote a small Python script that consumes RAM in a `while True` loop and deployed it with a hard memory limit of `64Mi`.

I watched it live:
```bash
kubectl get pods -w
```
Within seconds, the status flipped to `OOMKilled`. 

I ran `kubectl describe pod` to inspect the forensic evidence. Under the container's `State` section, the termination reason clearly stated: `OOMKilled`.

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is the difference between a Request and a Limit?**
   > A Request is the minimum resources guaranteed to the Pod (used for scheduling). A Limit is the maximum allowed (used for throttling/killing).
2. **What happens if a container exceeds its CPU limit?**
   > The container is not killed; it is CPU-throttled, meaning its performance degrades significantly.
3. **What happens if a container exceeds its Memory limit?**
   > The Linux kernel triggers an Out Of Memory (OOM) killer event, immediately terminating the container.
4. **How do you achieve a 'Guaranteed' Quality of Service class?**
   > By explicitly setting the CPU and Memory Requests to be exactly equal to the CPU and Memory Limits for every container in the Pod.
5. **Why might a Pod be stuck in `Pending`?**
   > Often because its resource Requests exceed the available capacity on any single worker node in the cluster.
