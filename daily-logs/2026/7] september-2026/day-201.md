## 1. The Limitation of Standard UGO & The Power of POSIX ACLs

Yesterday on Day 200, I mastered the classic Linux UGO model. But in modern cloud and enterprise environments, UGO quickly breaks down:
* **The Problem:** Suppose `developer-alice` needs read-write access to a production configuration file owned by `root:webadmins`, but `developer-bob` should only have read-only access. Under standard UGO, you are forced to create complex overlapping groups or grant broad permissions.
* **The Solution:** **POSIX Access Control Lists (ACLs)** allow me to attach arbitrary, granular permission entries directly to an inode for specific users or groups without altering the primary owner or group.

I used `getfacl` to inspect extended permissions and `setfacl` to modify them:
```bash
# Grant user alice read-write-execute without altering file group ownership
setfacl -m u:alice:rwx app-config.json

# Grant group auditors read-only access
setfacl -m g:auditors:r-- app-config.json

# View the full ACL table
getfacl app-config.json
```

When an ACL is present on a file, running `ls -l` shows a `+` symbol at the end of the permission string (e.g., `-rw-rwxr--+`).

## 2. Default ACLs for Directory Inheritance

When multiple developers or services write to a shared repository or log directory, newly created files often inherit the creator's default `umask`, breaking collaboration. 

I solved this by setting **Default ACLs** on parent directories:
```bash
# Set default ACL so every newly created child file/folder grants rwx to devteam
setfacl -d -m g:devteam:rwx /var/shared/models
```
Any file created inside `/var/shared/models` automatically inherits `g:devteam:rwx`, eliminating permission drift without manual intervention.

## 3. Extended File Attributes: `chattr` and `lsattr`

Standard Linux permissions protect files from regular users, but **even the `root` superuser can accidentally delete or overwrite files**. Extended filesystem attributes provide kernel-level protection:

* **Immutable Flag (`+i`):** Prevents modification, renaming, deletion, or symlinking—even by `root`.
  ```bash
  sudo chattr +i /etc/resolv.conf
  sudo rm -f /etc/resolv.conf
  # Output: rm: cannot remove '/etc/resolv.conf': Operation not permitted
  ```
* **Append-Only Flag (`+a`):** Restricts the file so data can only be appended to the end; existing data cannot be overwritten or truncated. Ideal for tamper-evident security audit logs (`/var/log/secure`).
  ```bash
  sudo chattr +a /var/log/audit.log
  ```
* **Inspection:** `lsattr /path/to/file` inspects active extended flags.

## 4. SELinux Fundamentals (Mandatory Access Control)

Standard permissions are **Discretionary Access Control (DAC)**: the file owner decides who gets access. **SELinux (Security-Enhanced Linux)** introduces **Mandatory Access Control (MAC)** enforced directly by the Linux kernel via security policies.

### Core Concepts:
* **Contexts:** Every process, user, and file gets an SELinux label formatted as `user:role:type:level`.
  ```bash
  ls -Z /var/www/html
  # Output: -rw-r--r--. root root unconfined_u:object_r:httpd_sys_content_t:s0 index.html
  ```
  If an NGINX process (`httpd_t`) is hijacked by an attacker, SELinux prevents it from reading `/home` or `/etc/shadow` even if file DAC permissions are `777`, because the type policy strictly denies it.
* **Modes:**
  * `Enforcing`: Policy is actively enforced and unauthorized actions are blocked and logged.
  * `Permissive`: Policy violations are logged (audit logs) but NOT blocked (used for debugging).
  * `Disabled`: SELinux kernel subsystem is completely shut off.
  ```bash
  getenforce            # Check current status
  sudo setenforce 0     # Temporarily switch to Permissive (for debugging only)
  sudo setenforce 1     # Restore to Enforcing
  ```

## 5. Deliverable: `acl_setup.sh`

I wrote and tested a defensive automation script that grants, audits, and revokes granular ACL permissions:

```bash
#!/bin/bash
# ==============================================================================
# acl_setup.sh
# Day 5/30 - Linux Mastery | Day 201/1000 - AI Cloud Infrastructure Journey
# Purpose: Demonstrate POSIX ACL provisioning, verification, and revocation.
# ==============================================================================

set -euo pipefail

LAB_DIR="/tmp/acl_lab"
TEST_FILE="${LAB_DIR}/dataset_registry.json"

echo "=== Initializing ACL Lab Environment ==="
mkdir -p "${LAB_DIR}"
echo '{"status": "active", "version": "1.0.0"}' > "${TEST_FILE}"
chmod 640 "${TEST_FILE}"

echo -e "\n[+] Baseline Permissions:"
ls -l "${TEST_FILE}"
getfacl "${TEST_FILE}"

# 1. Grant granular access to a specific user (e.g., student/guest)
echo -e "\n[+] Granting granular ACL to user..."
setfacl -m u:nobody:rw- "${TEST_FILE}"

echo -e "\n[+] Updated ACL Table (Notice the '+' on ls -l):"
ls -l "${TEST_FILE}"
getfacl "${TEST_FILE}"

# 2. Configure Default ACL for inheritance on directory
echo -e "\n[+] Configuring Directory Default ACLs for auto-inheritance..."
setfacl -d -m u:nobody:r-x "${LAB_DIR}"
touch "${LAB_DIR}/inherited_file.txt"
getfacl "${LAB_DIR}/inherited_file.txt"

# 3. Clean up and revoke ACLs
echo -e "\n[+] Revoking all extended ACLs..."
setfacl -b "${TEST_FILE}"
setfacl -b "${LAB_DIR}"

echo -e "\n[+] Final State after Revocation:"
ls -l "${TEST_FILE}"
getfacl "${TEST_FILE}"

echo -e "\n=== ACL Demonstration Completed Successfully ==="
```

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **Why do we need POSIX ACLs when we already have UGO permissions?**
   > Standard UGO limits access control to a single owner, a single group, and everyone else. POSIX ACLs allow assigning granular, multi-user, and multi-group permissions to a file without altering its primary ownership or creating unnecessary system groups.
2. **What does the `+` sign at the end of an `ls -l` permission string indicate?**
   > It indicates that the file or directory has an extended POSIX Access Control List (ACL) attached to its inode.
3. **What is the difference between `setfacl -m` and `setfacl -d`?**
   > `-m` (modify) applies ACL entries directly to an existing file or directory. `-d` (default) sets inherited ACL rules on a directory that automatically apply to newly created child items.
4. **How does `chattr +i` protect against accidental data loss even by the root user?**
   > The `+i` (immutable) attribute instructs the Linux filesystem driver (ext4/xfs) to reject all modifications, renames, truncations, and deletions at the kernel level, even when issued by UID 0 (`root`).
5. **What is the fundamental difference between DAC (Discretionary Access Control) and MAC (Mandatory Access Control/SELinux)?**
   > In DAC (UGO/ACLs), the resource owner dictates permissions. In MAC (SELinux), the system kernel enforces centralized security policies based on process and file context types (`httpd_t` accessing `httpd_sys_content_t`), preventing rogue processes from exceeding their bounded sandbox even with root privileges.
