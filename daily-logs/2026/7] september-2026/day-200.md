# 1. Linux UGO Permission Model

Linux permissions are divided into three categories:

```text
U → User / Owner
G → Group
O → Others
```

Example:

```text
-rwxr-xr--
```

Breakdown:

```text
- | rwx | r-x | r--
  |     |     |
  |     |     └── Others
  |     └──────── Group
  └────────────── User
```

The first character identifies the object type:

```text
-  → Regular file
d  → Directory
l  → Symbolic link
```

---

# 2. Permission Bits

Linux has three basic permission bits:

| Permission | Symbol | Numeric Value |
| ---------- | -----: | ------------: |
| Read       |    `r` |             4 |
| Write      |    `w` |             2 |
| Execute    |    `x` |             1 |

The values are added together.

### Examples

```text
rwx = 4 + 2 + 1 = 7
rw- = 4 + 2 + 0 = 6
r-x = 4 + 0 + 1 = 5
r-- = 4 + 0 + 0 = 4
-wx = 0 + 2 + 1 = 3
-w- = 0 + 2 + 0 = 2
--x = 0 + 0 + 1 = 1
--- = 0 + 0 + 0 = 0
```

### Permission Reference

```text
7 = rwx
6 = rw-
5 = r-x
4 = r--
3 = -wx
2 = -w-
1 = --x
0 = ---
```

# 3. Reading Numeric Permissions

A permission such as:

```text
755
```

contains three digits:

```text
7   5   5
│   │   │
U   G   O
```

Therefore:

```text
7 = rwx
5 = r-x
5 = r-x
```

Result:

```text
rwxr-xr-x
```

Meaning:

```text
User    → read + write + execute
Group   → read + execute
Others  → read + execute
```

---

# 4. Common Permission Modes

## 755

```bash
chmod 755 script.sh
```

Equivalent to:

```text
rwxr-xr-x
```

Owner has full access.

Group and others can read and execute.

Common for executable scripts and programs.

---

## 640

```bash
chmod 640 app.conf
```

Equivalent to:

```text
rw-r-----
```

Meaning:

```text
Owner    → read + write
Group    → read
Others   → no access
```

Useful for configuration or shared application data.

---

## 600

```bash
chmod 600 secret.txt
```

Equivalent to:

```text
rw-------
```

Meaning:

```text
Owner    → read + write
Group    → no access
Others   → no access
```

Useful for sensitive files and private credentials.

---

## 4755

```bash
chmod 4755 program
```

The first digit represents a special permission:

```text
4 → SUID
```

Therefore:

```text
4755
```

means:

```text
SUID + 755
```

---

# 5. `chmod`

`chmod` means:

> Change Mode

Basic syntax:

```bash
chmod MODE FILE
```

Examples:

```bash
chmod 755 script.sh
chmod 640 config.txt
chmod 600 secret.txt
chmod 4755 program
```

Verify permissions with:

```bash
ls -l
```

---

# 6. Symbolic chmod

Permissions can also be modified symbolically.

### Add execute permission to owner

```bash
chmod u+x script.sh
```

### Add write permission to group

```bash
chmod g+w file.txt
```

### Remove read permission from others

```bash
chmod o-r file.txt
```

### Set exact permissions

```bash
chmod u=rw,g=r,o= file.txt
```

Categories:

```text
u → User
g → Group
o → Others
a → All
```

# 7. File Permissions vs Directory Permissions

This is one of the most important concepts.

## Regular Files

```text
r → Read file contents
w → Modify file contents
x → Execute the file
```

## Directories

```text
r → List directory contents
w → Create/delete/rename directory entries
x → Traverse/access the directory
```

Directory execute permission is especially important.

A user generally needs `x` permission on a directory to access objects inside it.

# 10. `umask`

`umask` controls which permissions are removed from the default permissions of newly created files and directories.

Check the current umask:

```bash
umask
```

Example:

```text
0022
```

or:

```text
022
```

---

# 11. Default Permissions

A useful mental model is:

```text
Directories → 777
Regular files → 666
```

The `umask` removes permissions.

For example:

```text
777
-022
----
755
```

Therefore:

```bash
umask 022
```

typically produces:

```text
Directory → 755
File      → 644
```

---

# 12. umask 022

Set:

```bash
umask 022
```

Typical directory permissions:

```text
777
-022
----
755
```

Typical file permissions:

```text
666
-022
----
644
```

Result:

```text
Directory → rwxr-xr-x
File      → rw-r--r--
```

This is a common standard configuration.

---

# 13. umask 027

Set:

```bash
umask 027
```

Typical directory permissions:

```text
777
-027
----
750
```

Typical file permissions:

```text
666
-027
----
640
```

Result:

```text
Directory → rwxr-x---
File      → rw-r-----
```

This prevents access by Others.

It is useful when stronger default isolation is required.

---

# 14. Security Implications of umask

A restrictive `umask` can reduce accidental exposure of newly created files.

For example:

```text
umask 022
```

allows Others to read newly created regular files under the usual creation mode.

Whereas:

```text
umask 027
```

typically prevents Others from accessing them.

Important:

> `umask` provides a default restriction. It should not replace deliberate permission management for sensitive files.

# 15. Special Permissions

Linux has three important special permission bits:

| Special Permission | Numeric Value | Purpose                                        |
| ------------------ | ------------: | ---------------------------------------------- |
| SUID               |             4 | Execute with file owner's effective privileges |
| SGID               |             2 | Group-related privilege/inheritance behavior   |
| Sticky Bit         |             1 | Restrict deletion in shared directories        |

They appear before the normal UGO digits.

Examples:

```text
4755 → SUID + 755
2755 → SGID + 755
1777 → Sticky Bit + 777
```

---

# 16. SUID

SUID stands for:

> Set User ID

Numeric value:

```text
4
```

Example:

```bash
chmod 4755 program
```

SUID can cause an executable to run with the effective privileges associated with its file owner.

This makes SUID binaries security-sensitive.

SUID is not automatically malicious.

Many legitimate Linux utilities use it.

---

# 17. Finding SUID Files

Run:

```bash
find /usr/bin -perm -4000 -type f
```

This searches for regular files with the SUID bit.

For each result, consider:

```text
What program is this?
Who owns it?
Why does it need SUID?
Is it expected?
What privileges could it obtain?
```

This is useful for Linux security auditing.

---

# 18. SGID

SGID stands for:

> Set Group ID

Numeric value:

```text
2
```

Example:

```bash
chmod 2755 program
```

For directories, SGID has an important group-inheritance behavior.

A directory with SGID can cause newly created files/directories inside it to inherit the directory's group.

This is useful for:

* Shared development directories
* Application directories
* Team environments
* Build systems
* CI/CD environments

---

# 19. Finding SGID Files

Run:

```bash
find /usr/bin -perm -2000 -type f
```

This searches for files with the SGID bit.

The goal is to understand and audit the permissions rather than assuming every special-permission file is dangerous.

---

# 20. Sticky Bit

Sticky Bit has numeric value:

```text
1
```

A classic example is:

```text
/tmp
```

Check:

```bash
ls -ld /tmp
```

You may see:

```text
drwxrwxrwt
```

The final:

```text
t
```

represents the Sticky Bit.

---

# 21. Why Sticky Bit Exists

Consider a shared directory:

```text
/shared
```

Multiple users can create files:

```text
/shared/alice.txt
/shared/bob.txt
/shared/kevin.txt
```

Without appropriate restrictions, users with sufficient directory permissions could potentially delete other users' files.

Sticky Bit changes the deletion rules so that users generally cannot arbitrarily delete files belonging to other users.

This makes it suitable for shared temporary directories.

---

# 22. Create a Sticky Directory

Run:

```bash
mkdir shared
chmod 1777 shared
```

Check:

```bash
ls -ld shared
```

Expected:

```text
drwxrwxrwt
```

Breakdown:

```text
1 → Sticky Bit
7 → User: rwx
7 → Group: rwx
7 → Others: rwx
```

# --------------------------------------------------

#

#

#

# 4. Sensitive configuration
#
# 600 = rw-------
#
# Only the owner can read/write.
# --------------------------------------------------

chmod 600 secure-lab/private/config.txt

# --------------------------------------------------
# 5. Group-readable configuration
#
# 640 = rw-r-----
#
# Owner: read/write
# Group: read
# Others: no access
# --------------------------------------------------

touch secure-lab/shared/app.conf
chmod 640 secure-lab/shared/app.conf

# --------------------------------------------------
# 6. Executable script
#
# 755 = rwxr-xr-x
#
# Owner: read/write/execute
# Group: read/execute
# Others: read/execute
# --------------------------------------------------

touch secure-lab/shared/run.sh
chmod 755 secure-lab/shared/run.sh

# --------------------------------------------------
# 7. Sticky-bit directory
#
# 1777 = sticky + rwxrwxrwx
#
# Users can create files, while sticky-bit

chmod 1777 secure-lab/dropbox

# --------------------------------------------------
# 8. Display final permissions
# --------------------------------------------------

echo

ls -ld secure-lab/*
ls -l secure-lab/private
ls -l secure-lab/shared

# 27. Principle of Least Privilege

A major lesson from today's work:

> Give users and applications only the permissions they actually need.

Avoid blindly doing:

```bash
chmod 777 -R .
```

when you encounter:

```text
Permission denied
```

Instead investigate:

```text
Who is running the process?
What user owns the file?
What group does the process belong to?
Which permission is missing?
Which directory is blocking access?
Can the required permission be granted more narrowly?
```

This is the foundation of **least privilege**.

# 28. Cloud Infrastructure Connection ☁️

Linux permissions directly affect cloud infrastructure.

An application running on an EC2 instance might use:

```text
appuser
```

instead of:

```text
root
```

Application data might be stored in:

```text
/var/lib/myapp
```

Instead of:

```bash
chmod 777 /var/lib/myapp
```

we can use ownership and appropriate permissions:

```bash
chown -R appuser:appgroup /var/lib/myapp
chmod 750 /var/lib/myapp
```

This provides the application access without unnecessarily exposing the data to every local user.

The same concepts appear in:

* AWS EC2
* Linux servers
* Docker containers
* Kubernetes
* CI/CD runners
* Web servers
* Databases
* SSH
* Application deployments
