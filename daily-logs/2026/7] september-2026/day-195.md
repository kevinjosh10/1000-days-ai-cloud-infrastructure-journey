## 1. Bootstrapping with `helm create`

I started by generating a standard chart scaffold:

```bash
helm create my-flask-api
```

I explored the generated directory structure and discovered how modular Helm is:
* `Chart.yaml`: Contains the chart metadata, API version (`v2`), and application version.
* `values.yaml`: Houses all default values and parameter defaults.
* `templates/`: Contains Kubernetes manifests sprinkled with Go templating tags (`deployment.yaml`, `service.yaml`, `ingress.yaml`, `hpa.yaml`, `serviceaccount.yaml`).
* `templates/_helpers.tpl`: A partial template file for shared template definitions and functions.

## 2. Demystifying Go Templating in Helm

I dove into Helm's Go templating syntax to understand how static YAML becomes dynamic:

* **Value References:** `{{ .Values.replicaCount }}` extracts fields from `values.yaml`.
* **Built-in Objects:** `{{ .Release.Name }}` pulls the deployment release name; `{{ .Release.Namespace }}` injects the target namespace.
* **Control Structures (Conditionals):**
  ```yaml
  {{- if .Values.ingress.enabled }}
  apiVersion: networking.k8s.io/v1
  kind: Ingress
  ...
  {{- end }}
  ```
* **Pipelines & Functions:** `{{ .Values.image.tag | default .Chart.AppVersion | quote }}` applies fallback logic and formats output safely.

## 3. DRY Architecture: `_helpers.tpl` and `nindent`

In raw YAML, you repeat the same labels and selector blocks across Deployments, Services, and Ingresses. Helm solves this using **Named Templates** in `_helpers.tpl`.

I defined standard common labels in `_helpers.tpl`:

```gotemplate
{{/*
Common labels
*/}}
{{- define "my-flask-api.labels" -}}
helm.sh/chart: {{ include "my-flask-api.chart" . }}
{{ include "my-flask-api.selectorLabels" . }}
{{- if .Chart.AppVersion }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
{{- end }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}
```

And reused them in `templates/deployment.yaml` with clean indentation:

```yaml
metadata:
  name: {{ include "my-flask-api.fullname" . }}
  labels:
    {{- include "my-flask-api.labels" . | nindent 4 }}
```

The `| nindent 4` pipe function is a game-changer: it ensures that multiline helper templates are cleanly indented into the YAML without breaking whitespace rules.

## 4. Parameterizing `values.yaml` for Environment Flexibility

I customized `values.yaml` to make my Flask API fully configurable:

```yaml
replicaCount: 2

image:
  repository: 123456789012.dkr.ecr.us-east-1.amazonaws.com/flask-api
  pullPolicy: IfNotPresent
  tag: "1.0.0"

service:
  type: ClusterIP
  port: 5000

ingress:
  enabled: true
  className: "nginx"
  hosts:
    - host: flask.company.internal
      paths:
        - path: /
          pathType: Prefix

resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 100m
    memory: 128Mi

env:
  ENVIRONMENT: "production"
  LOG_LEVEL: "info"
```

## 5. The Helm Validation & Testing Pipeline

Before installing a newly authored chart into a live cluster, I ran the full 4-stage validation pipeline:

1. **Linting (Syntax Check):**
   ```bash
   helm lint ./my-flask-api
   ```
   *Result:* `1 chart(s) linted, 0 chart(s) failed` — no syntax or schema errors.
2. **Template Rendering (Dry Run Generation):**
   ```bash
   helm template test-release ./my-flask-api
   ```
   Renders the exact final Kubernetes YAML manifests to stdout for manual code review.
3. **Simulated Server-Side Install:**
   ```bash
   helm install test-release ./my-flask-api --dry-run
   ```
   Submits manifests to the Kubernetes API server for schema validation without actually creating resources.
4. **Real Deployment:**
   ```bash
   helm install my-flask-app ./my-flask-api --namespace development
   ```
   *Result:* Deployment, Service, and Ingress successfully created and running!

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is the purpose of `templates/_helpers.tpl` in a Helm chart?**
   > It stores reusable named template snippets (partials) like standardized labels, resource names, and selector blocks, adhering to DRY principles across all manifests.
2. **What does `nindent` do in Go templating?**
   > `nindent <N>` adds a newline followed by $N$ spaces of indentation, ensuring multiline partials are placed at the exact indentation level required by YAML syntax.
3. **What is the difference between `helm template` and `helm install --dry-run`?**
   > `helm template` renders YAML locally without connecting to a cluster. `helm install --dry-run` connects to the Kubernetes API server and performs live server-side validation against cluster schemas.
4. **How do you make a resource optional in a Helm chart?**
   > By wrapping the entire manifest in a conditional block, e.g., `{{- if .Values.ingress.enabled }} ... {{- end }}`.
5. **How does `{{ .Release.Name }}` help multi-tenant deployments?**
   > It dynamically prefixes resource names with the release name (e.g., `dev-flask-api` vs `prod-flask-api`), preventing naming collisions when deploying multiple instances into the same namespace.
