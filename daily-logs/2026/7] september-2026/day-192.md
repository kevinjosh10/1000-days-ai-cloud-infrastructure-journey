# 🚀 Day 192 — NetworkPolicies: Kubernetes Firewall & Zero Trust

**Date:** 09 September 2026  
**Duration:** ~2.5 Hours

---

On Day 190, I learned that Kubernetes enforces a completely flat network model where every Pod can reach every other Pod across all nodes by default. While this makes microservice discovery effortless, from a security standpoint, **it is a nightmare**. If an attacker compromises a single public-facing frontend Pod, they have an open path to directly scan, probe, and attack the backend database Pod.

Today, I closed this security hole by implementing **Kubernetes NetworkPolicies** to establish a strict Zero Trust network inside the cluster.

---

## 1. The Default Flat Network Threat

In an unconstrained Kubernetes cluster, there is no internal boundary:
* Frontend Pods can initiate connections directly to the Database on port `5432`.
* Any compromised test Pod can sniff internal cluster traffic.
* Pods can make unrestricted outbound connections to arbitrary public IPs on the internet (data exfiltration).

NetworkPolicies act as Layer 3 and Layer 4 firewalls for Pods, filtering traffic based on IP blocks (CIDRs), Port numbers, and crucially, **Kubernetes Labels**.

---

## 2. The Silent Gotcha: CNI Plugin Enforcement

I discovered a critical trap that trips up many Kubernetes administrators: **NetworkPolicies require a CNI plugin that actually supports policy enforcement.**

* Basic CNI plugins like standard Flannel or default Minikube networking **completely ignore** `NetworkPolicy` objects without throwing any errors. The YAML applies successfully, but no traffic is blocked!
* To actually enforce policies, I had to run a compatible CNI like **Calico** or **Cilium**:

```bash
minikube start --cni=calico
```

Calico programs native Linux `iptables` and IP sets on each node to enforce the packet filtering rules declared in the manifests.

---

## 3. Adopting Zero Trust: The Default-Deny Policy

The foundation of production Kubernetes security is **Zero Trust**: deny all traffic by default, then explicitly whitelist only what is required.

I created a cluster-wide default-deny manifest for my production namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {} # Selects ALL pods in the namespace
  policyTypes:
  - Ingress
  - Egress
```

The moment this was applied, all incoming and outgoing connections across all Pods in the `production` namespace were instantly severed.

---

## 4. Crafting Granular Allow Rules & The DNS Port 53 Lifeline

With everything blocked, I systematically opened only the necessary communication paths:

1. **Allow Frontend to Backend:**
   ```yaml
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: allow-frontend-to-backend
     namespace: production
   spec:
     podSelector:
       matchLabels:
         app: backend
     policyTypes:
     - Ingress
     - Egress
     ingress:
     - from:
       - podSelector:
           matchLabels:
             app: frontend
       ports:
       - protocol: TCP
         port: 8080
   ```

2. **Allow Backend to Database:**
   Allowed ingress into `app: database` strictly on TCP port `5432`, only when coming from `app: backend`.

3. **The Essential DNS Rule (Port 53):**
   When I first applied default-deny, my Pods could no longer resolve internal service names. I realized that internal DNS lookups via CoreDNS require explicit egress permission to `kube-dns` on UDP/TCP port 53 in the `kube-system` namespace. I created a dedicated policy allowing egress on port 53 to keep DNS functional.

---

## 5. Live Verification & Testing

I tested the firewall rules by deploying a full 3-tier application:

* **Direct database probe from Frontend:**
  ```bash
  kubectl exec -it frontend -n production -- curl --connect-timeout 3 database:5432
  ```
  *Result:* **Connection timed out.** Traffic dropped at the kernel level.
* **Database probe from Backend:**
  ```bash
  kubectl exec -it backend -n production -- nc -zv database 5432
  ```
  *Result:* **Connection open.** The whitelist rule matched successfully!

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is a Kubernetes NetworkPolicy?**
   > A native Kubernetes specification that defines how groups of Pods are allowed to communicate with each other and with other network endpoints at Layer 3 and Layer 4.
2. **Why might a NetworkPolicy appear to apply without actually blocking any traffic?**
   > If the underlying cluster CNI plugin (e.g., standard Flannel) does not support NetworkPolicy enforcement, the Kubernetes API accepts the manifest, but no filtering rules are executed.
3. **What does `podSelector: {}` mean in a NetworkPolicy?**
   > It matches all Pods in the namespace where the policy is deployed, commonly used to set up default-deny baseline policies.
4. **Why do Pods lose the ability to resolve domain names under a default-deny egress policy?**
   > Because default-deny egress blocks outgoing UDP/TCP port 53 traffic to the CoreDNS Pods in `kube-system`, preventing DNS resolution until an explicit egress allow rule is created.
5. **How does a NetworkPolicy differ from an AWS Security Group?**
   > Security Groups operate at the EC2 instance / ENI level (infrastructure layer). NetworkPolicies operate dynamically at the Pod level (container layer) using Kubernetes metadata and labels, regardless of which physical node the Pod is scheduled on.
