Today, I moved further into advanced operations, focusing entirely on **production patterns**. Yesterday was about resource safety; today was about reliability and operational security. 

If my Flask container is running in an EC2 instance and crashes at 3:00 AM, I cannot afford to SSH in and manually restart it. If a hacker breaches it, I cannot allow them to overwrite files. Today, I engineered solutions for these exact scenarios.

## 1. Native Docker Healthchecks

Previously, I used Compose to wait for a database. Today, I learned how to bake health awareness directly into the Dockerfile itself using the `HEALTHCHECK` instruction:
```dockerfile
HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
  CMD curl -f http://localhost:5000/health || exit 1
```
This is brilliant. Docker itself will now periodically ping the `/health` endpoint. If the application deadlocks (the container is "running" but the application is unresponsive), Docker marks the container as `unhealthy`, allowing orchestrators (like ECS or Docker Swarm) to automatically kill and replace it.

## 2. Automated Self-Healing (Restart Policies)

To ensure high availability, I learned how to configure restart policies. 
By running my containers with:
```bash
docker run --restart=unless-stopped flask-api
```
Docker guarantees that if the application crashes, or if the EC2 host physically reboots, the container will automatically start itself back up. I chose `unless-stopped` over `always` because if I manually stop the container, I want it to stay stopped.

## 3. Centralizing Logs with `awslogs`

By default, Docker stores logs locally on the host machine (`json-file`). In a production cluster of 50 EC2 instances, SSHing into individual machines to read logs is impossible. 

I learned how to bypass the local disk entirely and stream logs directly into AWS CloudWatch:
```bash
docker run \
  --log-driver=awslogs \
  --log-opt awslogs-region=us-east-1 \
  --log-opt awslogs-group=/myapp \
  flask-api
```
Now, my containers are stateless, and my logs are instantly centralized and searchable in AWS!

## 4. The Law of Container Immutability

I cemented a fundamental operational rule today: **Never SSH into a running container to fix something.**
* If there is a bug, I modify the code on my laptop.
* I rebuild the image.
* I push a new, strictly tagged image (e.g., `flask-api:v1.2` or using a Git SHA, *never* `latest`).
* I redeploy.

Containers are cattle, not pets. They are ephemeral and immutable.

## 5. Security: Read-Only Containers 🔐

Finally, I implemented a massive security upgrade. If a hacker exploits a vulnerability in my application, their next step is usually to download a malicious payload to the filesystem. 

I can physically prevent this by running the container with a read-only root filesystem:
```bash
docker run \
  --read-only \
  --tmpfs /tmp \
  flask-api
```
The entire application filesystem is completely locked down. The only writable space is `/tmp`, which I explicitly mounted into RAM (`tmpfs`). Even if the container is breached, the attacker cannot persist files or modify the application code!

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **How do you detect if a container is running but the app is deadlocked?**
   > By baking a `HEALTHCHECK` instruction into the Dockerfile that actively queries an application endpoint.
2. **How do you ensure containers survive a server reboot?**
   > By using the `--restart=unless-stopped` flag when running the container.
3. **Where should Docker logs go in an AWS production environment?**
   > They should be streamed directly to CloudWatch Logs using the `awslogs` logging driver.
4. **What is Container Immutability?**
   > The principle that containers are never patched live. Updates are always made by rebuilding and redeploying a new immutable image.
5. **How do you prevent attackers from writing files in a compromised container?**
   > By running the container with the `--read-only` flag and mapping necessary writable directories (like `/tmp`) into memory using `--tmpfs`.
