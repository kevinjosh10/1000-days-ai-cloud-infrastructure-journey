# Day 159 – Terraform Import & Refactoring Legacy Infrastructure

**Date:** 07 August 2026  
**Duration:** ~2 Hours  
**Focus:** Legacy Infrastructure Integration, State Manipulation, Declarative Refactoring, and Drift Auditing  

---

## 🎯 Objective

Understand how to safely bring manually created "ClickOps" infrastructure under Terraform's strict control without causing production downtime. 

Learn the critical difference between imperative state hacking and declarative refactoring, and master the tools required to detect unauthorized manual changes to live cloud environments.

---

## ✅ What I Completed

### 1️⃣ Mastered the `terraform import` Workflow

Studied the exact methodology for capturing live AWS resources into Terraform state.

Learned the 4-step production workflow:
1. **Write HCL:** Create an empty or best-guess resource block in `main.tf`
2. **Import:** Run `terraform import aws_instance.legacy i-1234567890abcdef0`
3. **Plan to Zero:** Iteratively run `terraform plan` and update the HCL code until Terraform reports exactly zero changes (fixing drift)
4. **Apply (No-Op):** Run `terraform apply` to finalize the mapping without actually modifying the AWS resource

Understood:
- Terraform cannot magically write the HCL code for you; import simply links the AWS ID to your code
- This is the only safe way to migrate legacy environments to IaC

---

### 2️⃣ Learned the Declarative `moved` Block

Studied how to reorganize Terraform code structures without destroying production resources.

Learned:
- Prior to Terraform v1.1, renaming a resource in code resulted in Terraform destroying the old resource and creating a new one (causing severe downtime)
- The `moved` block solves this by declaratively instructing Terraform that a resource has simply changed names or locations
- Syntax: `moved { from = aws_instance.web, to = module.web.aws_instance.this }`

Understood:
- This allows for massive code refactoring and modularization of older Terraform projects with zero impact on live infrastructure

---

### 3️⃣ Studied Large-Scale Import Strategies

Explored the complexity of importing massive architectural constructs like AWS VPCs.

Learned:
- A VPC is not a single resource in Terraform
- Bringing a manual VPC into code requires individually importing the `aws_vpc`, multiple `aws_subnet` blocks, `aws_internet_gateway`, `aws_route_table`, and `aws_security_group` resources
- This process is highly tedious and requires extreme attention to detail

Understood:
- Large enterprise migrations often rely on third-party tools (like Terraformer) to automate the generation of HCL code for massive imports

---

### 4️⃣ Compared `terraform state mv` vs `moved`

Analyzed the evolution of Terraform state management.

Learned:
- **`terraform state mv`:** An older, imperative CLI command used to rename resources directly in the state file
- **`moved` block:** A newer, declarative HCL block that lives in the source code

Understood:
- Imperative CLI commands are dangerous because they are not version-controlled and bypass Code Review (Pull Requests)
- Declarative `moved` blocks are peer-reviewed, tracked in Git, and executed predictably by CI/CD pipelines
- Always prefer the declarative `moved` approach

---

### 5️⃣ Audited Configuration Drift (`-refresh-only`)

Practiced detecting unauthorized manual changes made to infrastructure outside of Terraform.

Command studied:
    terraform plan -refresh-only

Learned:
- This command forces Terraform to check the live AWS environment against the current state file, without proposing any destructive actions
- It reveals "Configuration Drift" (e.g., a junior engineer manually opening Port 22 in the AWS Console)

Understood:
- Drift detection is a critical security auditing tool
- Once drift is found, engineers must decide whether to revert the manual change (by running standard `apply`) or encode the change into the HCL to permanently adopt it
