## 1. The Core Brain: API Server & etcd

I learned that Kubernetes is fundamentally an API-driven system. 
* **`kube-apiserver`**: This is the front door. Every single command I run via `kubectl` goes directly to the API server. It validates requests, handles authentication, and acts as the central communication hub.
* **`etcd`**: The API server is stateless. All the actual cluster state (what pods exist, what secrets are stored) is saved in `etcd`, a highly available distributed key-value store. I learned a critical operational rule: *If etcd dies, the entire cluster becomes amnesiac and blind.* It is the absolute source of truth.

## 2. The Matchmaker: `kube-scheduler`

Next, I studied the **Scheduler**. I used to think the scheduler *ran* the pods. I was wrong.
The scheduler simply watches the API server for newly created Pods that don't have a Node assigned yet. It evaluates the CPU/RAM requirements of the Pod, checks which worker nodes have capacity, evaluates affinity/taint rules, and then *assigns* the Pod to a Node. It doesn't execute the container; it's purely a matchmaking service.

## 3. The Reconcilers: `kube-controller-manager`

Kubernetes works on a declarative "desired state vs. actual state" model. The **Controller Manager** is the engine that drives this.
It runs continuous loops (Controllers) in the background:
* **Node Controller:** Watches if an EC2 instance goes down.
* **Replication Controller:** If I ask for 3 Pods and one dies, this controller notices the actual state (2) doesn't match the desired state (3) and tells the API server to create a new one.
* **Endpoints Controller:** Links Services to Pods.

## 4. The Cloud Bridge: `cloud-controller-manager`

Because I am focused on AWS, the **Cloud Controller Manager (CCM)** is incredibly important. This component translates generic Kubernetes commands into specific AWS API calls.
* If I create a Kubernetes `Service` of type `LoadBalancer`, the CCM talks to AWS to provision a real Elastic Load Balancer (ELB).
* If I request persistent storage, it provisions EBS volumes.
* It dynamically registers new EC2 instances as Kubernetes Worker Nodes.

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What happens if etcd goes down?**
   > The cluster loses its source of truth. The API server cannot read or write state, meaning no new pods can be scheduled and no existing configurations can be modified.
2. **Does the kube-scheduler run containers?**
   > No, it only binds unscheduled Pods to suitable Nodes based on resource requirements and constraints. The local `kubelet` on the Node actually runs the container.
3. **What is the function of the kube-apiserver?**
   > It is the single entry point for all control plane communication, exposing the Kubernetes REST API and acting as the middleman between all other components and `etcd`.
4. **How does Kubernetes know to replace a dead Pod?**
   > The `kube-controller-manager` runs continuous reconciliation loops that detect when the actual state drifts from the desired state, immediately requesting a new Pod to correct the drift.
5. **How does Kubernetes provision an AWS Load Balancer?**
   > Through the `cloud-controller-manager`, which bridges Kubernetes abstractions with native AWS APIs.
