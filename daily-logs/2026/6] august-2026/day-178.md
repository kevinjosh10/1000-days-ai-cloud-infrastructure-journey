## 1. What is a Pod?

A Pod is a wrapper. It can hold one container, or it can hold multiple containers (like an API and a sidecar logging proxy). 
The defining feature of a Pod is that all containers inside it share the exact same **Network Namespace** and can share **Volumes**. 

If I put a Flask API and a Redis cache in the same Pod, the Flask API can connect to Redis simply by calling `localhost:6379`. They are inseparable and are always scheduled onto the exact same EC2 worker node.

## 2. Writing Kubernetes YAML from Scratch

I wrote my very first native Kubernetes manifest (`pod.yaml`). No more `docker run` commands!

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-pod
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
```
This declarative YAML is the language of cloud orchestration. I am declaring my *desired state*.

## 3. Applying and Inspecting State

I handed my desired state to the API Server:
```bash
kubectl apply -f pod.yaml
```

Then, I interrogated the cluster to see what the Scheduler and `kubelet` did:
* `kubectl get pod web-pod -o wide`: Showed me exactly which worker node the Pod was assigned to and its internal IP address.
* `kubectl describe pod web-pod`: This is a goldmine. It showed me the exact timeline of events—from the Scheduler finding a node, to the `kubelet` pulling the image, to the container starting.
* `kubectl logs web-pod`: Streamed the standard output of the container, just like Docker.

## 4. Infiltrating the Pod (`kubectl exec`)

To debug issues inside a running Pod, I learned how to use `kubectl exec` to establish an interactive shell directly into the running container:
```bash
kubectl exec -it web-pod -- bash
```
I also learned how to execute a single, one-off command without dropping into a shell:
```bash
kubectl exec web-pod -- curl localhost
```
This is my primary troubleshooting weapon when a deployment goes sideways.

## 5. The Golden Rule of Bare Pods

I ended the day with a massive operational realization: **I must never run bare Pods in production.**

If I deploy `pod.yaml` and the EC2 instance hosting it crashes... that Pod is dead and gone forever. The Kubernetes Control Plane will *not* reschedule a bare Pod. 

To achieve self-healing, a Pod must be managed by a higher-level Controller (like a **Deployment**, StatefulSet, or DaemonSet). A Deployment ensures that if a Pod dies, a replacement is automatically stamped out. Bare Pods are for testing; Deployments are for production.

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is a Pod?**
   > The smallest, atomic deployable unit in Kubernetes, wrapping one or more containers that share storage and a network namespace.
2. **How do multiple containers in the same Pod communicate?**
   > Over `localhost`, because they share the exact same network namespace.
3. **What command gives you the complete lifecycle event history of a Pod?**
   > `kubectl describe pod <pod-name>`. It shows the scheduling, image pulling, and container startup events.
4. **How do you run a shell inside a Kubernetes container?**
   > `kubectl exec -it <pod-name> -- bash` (or `sh`).
5. **Why are bare Pods never used in production?**
   > Bare Pods have no self-healing capabilities. If their host node dies, they are not rescheduled. They must be managed by a Controller like a Deployment.
