# Day 156 – Terragrunt & DRY Terraform at Scale

**Date:** 04 August 2026  
**Duration:** ~2 Hours  
**Focus:** Enterprise Infrastructure Orchestration, DRY Backends, Module Dependencies, and Terragrunt `run-all`  

---

## 🎯 Objective

Understand how Terragrunt solves native Terraform's limitations in multi-environment, multi-region setups by keeping backend and provider configurations completely DRY (Don't Repeat Yourself).

Learn how to inherit root configurations, pass outputs between isolated modules seamlessly using dependency blocks, and orchestrate complex, multi-tiered deployments with a single command.

---

## ✅ What I Completed

### 1️⃣ Installed Terragrunt & Understood the DRY Problem

Installed Terragrunt using Homebrew (`brew install terragrunt`).

Learned:
- Native Terraform forces you to repeat `backend` configurations in every single module folder
- In multi-environment setups (Dev, Staging, Prod), this leads to massive code duplication
- Terragrunt acts as a thin wrapper that orchestrates Terraform and eliminates this repetition

Understood:
- Boilerplate code is the enemy of scalable infrastructure
- Managing 50 microservices requires a centralized configuration tool

---

### 2️⃣ Created Root `terragrunt.hcl` for DRY Backends

Studied how to define backend configuration exactly ONCE.

Learned:
- Created a root `terragrunt.hcl` file containing the `remote_state` block
- Used the built-in function `${path_relative_to_include()}/terraform.tfstate`
- Terragrunt dynamically generates the `backend.tf` file for every child module automatically

Understood:
- State files are automatically isolated into S3 subfolders based on the directory structure
- Updating the S3 bucket name now only requires changing one single file, not 150

---

### 3️⃣ Learned Child Inheritance (`include`)

Studied how child directories inherit configurations from the root file.

Learned:
- Child modules use an `include "root"` block
- Used the `find_in_parent_folders()` function to dynamically locate the root `terragrunt.hcl` file
- Specific settings can be overridden in the child module using the `merge()` function if necessary

Understood:
- Inheritance keeps child modules incredibly clean and focused only on their specific inputs
- Directory hierarchy becomes deeply important to the architecture

---

### 4️⃣ Mastered Module Dependencies (`dependency`)

Studied how to pass outputs from one module to another without hardcoding or using clunky data sources.

Learned:
- Used `dependency "vpc" { config_path = "../vpc" }` inside the RDS configuration
- Passed data directly: `inputs = { vpc_id = dependency.vpc.outputs.vpc_id }`
- Terragrunt automatically forces the VPC to deploy before the RDS database

Understood:
- The `dependency` block replaces `terraform_remote_state`
- It creates a strict, mathematically sound dependency graph for deployment

---

### 5️⃣ Orchestrated Deployments at Scale (`run-all`)

Practiced executing massive architectural changes with a single command.

Command studied:
    terragrunt run-all apply

Learned:
- Navigating to the `live/prod/us-east-1/` folder and running `run-all` deploys everything
- Terragrunt reads the dependency graph and executes modules in the correct order (e.g., VPC first, ALB and RDS in parallel)
- `run-all destroy` safely tears down the architecture in reverse dependency order

Understood:
- This is how true Enterprise Cloud Engineers deploy infrastructure
- It eliminates the manual, error-prone process of navigating into dozens of folders sequentially
