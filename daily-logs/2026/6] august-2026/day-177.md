## 1. The Captain of the Node: `kubelet`

I learned that every single worker node runs an agent called the `kubelet`. 
The `kubelet` has two primary jobs:
1. It registers the EC2 instance with the API Server so the cluster knows the node exists.
2. It constantly watches the API Server for new Pod assignments. When the Scheduler assigns a Pod to its node, the `kubelet` physically starts the containers inside that Pod and reports their health status back to the API Server.

## 2. The Great Docker Deprecation (CRI)

Here is a massive plot twist I discovered today: **Kubernetes does not run Docker.**

In fact, Kubernetes removed Docker as its default runtime in version 1.24. Instead, Kubernetes communicates with a **Container Runtime Interface (CRI)**. The `kubelet` simply says, *"Hey CRI, start this container."* 

Today, the modern enterprise standards for CRI are **containerd** (which actually runs under the hood of Docker anyway) or **CRI-O**. Understanding this distinction is crucial for modern cloud architecture interviews.

## 3. The Networking Enforcer: `kube-proxy`

If `kubelet` runs the compute, `kube-proxy` runs the network.
Running on every node, `kube-proxy` maintains the complex network rules (usually via Linux `iptables` or `IPVS`). When my API tries to talk to my Database using a ClusterIP, it's actually `kube-proxy`'s iptables rules intercepting that traffic and physically routing it to the exact backend Pod IP address.

## 4. The Lifecycle of a Pod

I memorized the 5 distinct phases of a Pod's life:
1. **Pending:** The API server accepted the Pod, but it is waiting to be scheduled or waiting for the container image to download.
2. **Running:** The Pod has been bound to a node, and at least one container is executing.
3. **Succeeded:** All containers in the Pod executed successfully and terminated (exit code `0`).
4. **Failed:** At least one container terminated in failure (exit code non-zero).
5. **Unknown:** The API server lost communication with the node's `kubelet`.

## 5. Spinning Up a Multi-Node Cluster

To put this all into practice, I didn't just read about nodes; I built a multi-node cluster locally using Minikube:
```bash
minikube start --driver=docker --nodes=2 --cpus=2 --memory=4g
```

I verified the muscle of my cluster:
```bash
kubectl get nodes
```
And then I ran `kubectl describe node minikube-m02` to inspect exactly how much CPU and memory the node had, and what specific Pods the `kubelet` was currently managing on it.

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **What is the `kubelet`?**
   > The primary node agent. It registers the node with the cluster, watches for Pod assignments from the API server, and ensures the containers are running and healthy.
2. **Does Kubernetes use Docker?**
   > No, Kubernetes deprecated Docker as a runtime (Dockershim) in v1.24. It now uses the Container Runtime Interface (CRI) to talk directly to runtimes like `containerd` or `CRI-O`.
3. **How does traffic route to the correct Pod when hitting a Service?**
   > `kube-proxy` maintains `iptables` or `IPVS` rules on every node that intercept the Service IP and transparently load-balance the traffic to the backend Pod IPs.
4. **What does it mean if a Pod is stuck in `Pending`?**
   > It usually means the Scheduler cannot find a node with enough available CPU/RAM to host it, or it is struggling to pull the Docker image.
5. **What is the difference between Control Plane and Worker Nodes?**
   > The Control Plane makes global decisions (scheduling, cluster state). The Worker Nodes execute the actual container workloads and maintain local networking.
