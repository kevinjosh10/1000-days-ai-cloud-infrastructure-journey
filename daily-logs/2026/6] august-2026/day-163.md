# Day 163/1000 — Writing Production Dockerfiles 🐳

Today is important because you're moving from **“I know Docker commands” → “I can package an application properly.”**

Your goal today is to understand **how a Dockerfile turns source code into a portable application image**, and then build, run, test, tag, and push it.

---

# 1. First: What is a Dockerfile?

A **Dockerfile is a recipe for building a Docker image.**

Think of it like:

```text
Your application
      ↓
   Dockerfile
      ↓
 docker build
      ↓
 Docker Image
      ↓
 docker run
      ↓
Running Container
```

For example:

```text
Flask application
       +
Python
       +
Dependencies
       ↓
   Docker Image
       ↓
   Container
```

The important distinction:

> **Dockerfile = instructions**
>
> **Image = packaged application**
>
> **Container = running instance of that image**

---

# 2. The Dockerfile instructions you need to know

Today you need to understand these:

```dockerfile
FROM
WORKDIR
COPY
ADD
RUN
ENV
EXPOSE
CMD
ENTRYPOINT
```

Let's go one by one.

---

# 3. FROM — Choose the base image

```dockerfile
FROM python:3.12-slim
```

This tells Docker:

> "Start my image using Python 3.12 slim."

Think:

```text
FROM = Starting point
```

Instead of installing Python yourself, Docker gives you an image that already contains Python.

### Why `slim`?

Compare:

```text
python:3.12
python:3.12-slim
```

The normal image contains more OS packages.

The slim image contains fewer unnecessary components.

Therefore:

```text
smaller image
      ↓
less storage
      ↓
faster downloads
      ↓
faster deployments
```

For production, smaller images are generally preferable when they still contain everything your application needs.

---

# 4. WORKDIR — Where should we work?

```dockerfile
WORKDIR /app
```

This creates/sets:

```text
/app
```

and subsequent commands operate from there.

Without `WORKDIR`, you might have to do things like:

```dockerfile
RUN cd /app
```

But that doesn't persist between Dockerfile instructions the way beginners often expect.

Instead:

```dockerfile
WORKDIR /app
```

Then:

```dockerfile
COPY . .
```

means:

```text
Copy current project → /app
```

---

# 5. COPY — Copy files into the image

Example:

```dockerfile
COPY requirements.txt .
```

Because our `WORKDIR` is:

```dockerfile
/app
```

this means:

```text
Host:
requirements.txt

        ↓ COPY

Container:
/app/requirements.txt
```

Then:

```dockerfile
COPY . .
```

means:

```text
Current directory
      ↓
/app
```

So your project might become:

```text
/app
├── app.py
├── requirements.txt
└── ...
```

---

# 6. ADD — Similar to COPY, but more features

You should understand:

```dockerfile
ADD
```

can do things that `COPY` doesn't normally do, such as automatically extracting certain local archives.

Example:

```dockerfile
ADD app.tar.gz /app/
```

But here's the production rule:

> **Prefer `COPY` unless you specifically need `ADD` functionality.**

Why?

Because `COPY` is simpler and more predictable.

So generally:

```dockerfile
COPY requirements.txt .
COPY . .
```

rather than:

```dockerfile
ADD requirements.txt .
ADD . .
```

---

# 7. RUN — Execute something while BUILDING

This distinction is extremely important.

```dockerfile
RUN pip install -r requirements.txt
```

`RUN` happens during:

```bash
docker build
```

Not when the container starts.

Think:

```text
Dockerfile
   ↓
docker build
   ↓
RUN commands execute
   ↓
Image created
```

For example:

```dockerfile
RUN pip install -r requirements.txt --no-cache-dir
```

Docker installs Flask and other dependencies **into the image**.

---

# 8. ENV — Environment variables

You can define environment variables:

```dockerfile
ENV APP_ENV=production
```

Inside the container:

```bash
echo $APP_ENV
```

would produce:

```text
production
```

Your application can also access it.

For Python:

```python
import os

environment = os.getenv("APP_ENV")
```

### Important production rule

Don't put secrets into the Dockerfile.

❌ Bad:

```dockerfile
ENV AWS_SECRET_ACCESS_KEY=super-secret-key
```

Anyone who can inspect the image/history may potentially discover it.

Instead, pass secrets at runtime using appropriate secret-management mechanisms.

---

# 9. EXPOSE — Document the port

For Flask:

```dockerfile
EXPOSE 5000
```

This tells people/tools:

> "This application is intended to listen on port 5000."

But here's the common beginner mistake:

### `EXPOSE` does NOT publish the port.

This:

```dockerfile
EXPOSE 5000
```

doesn't make your application accessible from your host.

You still need:

```bash
docker run -p 5000:5000 my-flask-api:1.0
```

Think:

```text
EXPOSE
   ↓
Documentation / metadata

-p
   ↓
Actually publishes the port
```

---

# 10. CMD — Default command

Example:

```dockerfile
CMD ["python3", "app.py"]
```

This says:

> "When the container starts, run this by default."

So:

```bash
docker run my-flask-api:1.0
```

runs approximately:

```bash
python3 app.py
```

---

# 11. ENTRYPOINT — The main executable

Example:

```dockerfile
ENTRYPOINT ["python3", "app.py"]
```

This establishes the main executable for the container.

The easiest mental model:

```text
ENTRYPOINT = What the container IS
CMD        = Default arguments
```

For example:

```dockerfile
ENTRYPOINT ["python3", "app.py"]
CMD ["--port", "5000"]
```

Conceptually:

```text
python3 app.py --port 5000
```

You can override the default CMD arguments.

---

# 12. CMD vs ENTRYPOINT — Remember this

This is interview-important.

### CMD

```dockerfile
CMD ["python3", "app.py"]
```

Can easily be overridden:

```bash
docker run image python3 another.py
```

### ENTRYPOINT

```dockerfile
ENTRYPOINT ["python3", "app.py"]
```

is intended to remain the main executable.

A common pattern is:

```dockerfile
ENTRYPOINT ["python3", "app.py"]
CMD ["--port", "5000"]
```

Then:

```bash
docker run image
```

means:

```text
python3 app.py --port 5000
```

while:

```bash
docker run image --port 8080
```

means:

```text
python3 app.py --port 8080
```

### Memory trick

> **ENTRYPOINT = executable**
>
> **CMD = defaults**

# 13. Your first real Dockerfile

Let's build a Flask API.

Project:

```text
my-flask-api/
│
├── app.py
├── requirements.txt
└── Dockerfile
```

### `app.py`

```python
from flask import Flask

app = Flask(__name__)

@app.route("/health")
def health():
    return {"status": "healthy"}

@app.route("/")
def home():
    return {"message": "Hello from Docker!"}

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
```

Notice:

```python
host="0.0.0.0"
```

This matters.

Inside a container, binding only to:

```text
127.0.0.1
```

can prevent the application from being reachable through the container's network interface.

For a containerized web server, you generally want it listening on:

```text
0.0.0.0
```

# 14. requirements.txt

Create:

```text
Flask
```

You could pin a specific version in a real project for reproducibility.

# 15. Now write the Dockerfile

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt --no-cache-dir

COPY . .

EXPOSE 5000

CMD ["python3", "app.py"]
```

Now let's understand the entire thing:

```text
FROM python:3.12-slim
        ↓
Get Python

WORKDIR /app
        ↓
Work inside /app

COPY requirements.txt .
        ↓
Copy dependency file

RUN pip install...
        ↓
Install dependencies

COPY . .
        ↓
Copy application

EXPOSE 5000
        ↓
Document application port

CMD ["python3", "app.py"]
        ↓
Start Flask
```

---

# 16. Why do we copy requirements FIRST?

This is actually a **very important Docker concept**.

You might wonder why we don't simply do:

```dockerfile
COPY . .

RUN pip install -r requirements.txt
```

Instead we do:

```dockerfile
COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .
```

The reason is **Docker layer caching**.

Imagine:

```text
requirements.txt
app.py
```

You modify only:

```text
app.py
```

Your dependencies haven't changed.

Docker can reuse the layer where dependencies were installed.

So:

```text
COPY requirements.txt
        ↓
RUN pip install
        ↓
CACHE
        ↓
COPY application
```

If only `app.py` changes, Docker doesn't necessarily need to reinstall all Python dependencies.

This makes builds much faster.

### This is one of today's most important production concepts.

# 17. Build the image

Inside your project:

```bash
docker build -t my-flask-api:1.0 .
```

Break it down:

```text
docker build
```

Build an image.

```text
-t my-flask-api:1.0
```

Give it a name and tag.

```text
.
```

Use the current directory as the build context.

You'll see Docker executing your Dockerfile instructions.

```bash
docker images
```

You should see something like:

```text

```

Your image now exists.

# 19. Run the container

```bash
docker run -d -p 5000:5000 my-flask-api:1.0
```

Break this down:

```text
docker run
```

Create and start a container.

```text
-d
```

Detached mode.

Meaning:

> Run in the background.

Then:

```text
-p 5000:5000
```

Port mapping.

The format is:

```text
HOST:CONTAINER
```

So:

```text
5000:5000
```

means:

```text
Your computer:5000
        ↓
Container:5000
```

---

# 20. Check running containers

```bash
docker ps
```

You should see your container.

For example:

```text
CONTAINER ID
IMAGE
STATUS
PORTS
NAMES
```

You can also give it a name:

```bash
docker run -d \
  --name flask-api \
  -p 5000:5000 \
  my-flask-api:1.0
```

Now:

```bash
docker ps
```

will show:

```text
flask-api
```

# 24. Tag the image for Docker Hub

Suppose your Docker Hub username is:

```text
yourusername
```

You currently have:

```text
my-flask-api:1.0
```

Tag it:

```bash
docker tag my-flask-api:1.0 yourusername/flask-api:1.0
```

Now conceptually:

```text
my-flask-api:1.0
        ↓
yourusername/flask-api:1.0
```

The tag tells Docker where the image belongs.

---

# 25. Login to Docker Hub

```bash
docker login
```

Then authenticate with your Docker Hub credentials.

After that:

```bash
docker push yourusername/flask-api:1.0
```

Docker uploads the image.

---

# 26. Pull it somewhere else

On another machine:

```bash
docker pull yourusername/flask-api:1.0
```

Then:

```bash
docker run -d \
  --name flask-api \
  -p 5000:5000 \
  yourusername/flask-api:1.0
```

Test:

```bash
curl localhost:5000/health
```

If it works:

**You've demonstrated portability.**

The second machine doesn't need your Python environment or Flask installation.

It just needs Docker.

# 28. Production mindset 🧠

You're not just learning syntax.

As an **AI Cloud Infrastructure Engineer**, you need to understand *why* these practices matter.

### Bad Dockerfile thinking

```text
Install everything
Copy everything
Make huge image
Hardcode secrets
Run as root
Ignore caching
```

### Better Dockerfile thinking

```text
Small base image
        ↓
Efficient layer ordering
        ↓
Dependency caching
        ↓
No secrets in image
        ↓
Minimal unnecessary packages
        ↓
Predictable builds
        ↓
Portable application
```

We'll go deeper into **multi-stage builds, non-root users, `.dockerignore`, image security, and image optimization** as you progress.
