## ✅ What I Completed

### 1️⃣ Mastered Dockerfile Instructions

Studied the fundamental syntax used to construct container images layer-by-layer.

Learned:
- `FROM`: Defines the base OS/runtime (e.g., `FROM python:3.12-slim`). Must be the first line.
- `WORKDIR`: Sets the internal working directory for all subsequent commands.
- `COPY`: Moves files from the host laptop into the container's filesystem.
- `ADD`: Similar to `COPY`, but can extract `.tar` archives and fetch URLs. (Best practice is to use `COPY` unless extraction is strictly necessary).
- `RUN`: Executes Linux commands *during the build process* (e.g., `RUN pip install -r requirements.txt`).
- `ENV`: Hardcodes environment variables into the image.
- `EXPOSE`: Documents the listening port for the application. (Note: Does not actually publish the port; it acts as documentation for other engineers).

---

### 2️⃣ Deconstructed `CMD` vs `ENTRYPOINT`

Resolved one of the most common points of confusion in Docker.

Learned:
- **`ENTRYPOINT`**: Defines the fixed, hardcoded executable that *must* run when the container starts (e.g., `["python3", "app.py"]`).
- **`CMD`**: Provides default arguments to that executable, which can be easily overridden by the user at runtime.

Understood:
- If a container is designed to run a specific application (like a web server), use `ENTRYPOINT`. 
- If you use both: `ENTRYPOINT ["ping"]` combined with `CMD ["google.com"]` means `docker run my-image amazon.com` will overwrite the `CMD` and execute `ping amazon.com`.

---

### 3️⃣ Engineered a Production Python API Image

Built a highly optimized, multi-layered Dockerfile for a Flask application.

The exact blueprint:
```dockerfile
FROM python:3.12-slim
WORKDIR /app
# COPY requirements FIRST to leverage layer caching!
COPY requirements.txt .
RUN pip install -r requirements.txt --no-cache-dir
# COPY the rest of the source code AFTER dependencies are installed
COPY . .
EXPOSE 5000
CMD ["python3", "app.py"]
```

Understood:
- Docker caches layers. By copying `requirements.txt` *before* the application source code, we prevent Docker from reinstalling Python packages every time we change a single line of application code. This drastically speeds up build times.

---

### 4️⃣ Executed the Build-and-Run Pipeline

Compiled the Dockerfile into a functional image and tested it locally.

Workflow:
1. `docker build -t my-flask-api:1.0 .` (Told Docker to read the current directory `.` and tag the resulting image).
2. `docker run -d -p 5000:5000 my-flask-api:1.0` (Spun up the container, mapping the host port to the container port).
3. `curl localhost:5000/health` (Verified the application was serving HTTP requests successfully).

---

### 5️⃣ Distributed to Docker Hub

Pushed the local artifact to a public cloud registry for global distribution.

Workflow:
1. `docker tag my-flask-api:1.0 yourusername/flask-api:1.0` (Renamed the local image to match the Docker Hub repository format).
2. `docker push yourusername/flask-api:1.0` (Uploaded the image layers to the cloud).

Understood:
- The image is now highly portable. Any server, anywhere in the world, can run `docker pull yourusername/flask-api:1.0` and immediately execute the application without needing to install Python.
