# 1. Containerize your Python applications

You already have Python tools such as:

* AWS Resource Inventory
* EC2 Lifecycle Manager
* S3 Backup Tool

Instead of running:

```bash
python3 s3_backup.py
```

you want:

```bash
docker run s3-backup
```

The application becomes portable.

### Why?

Without Docker:

```text
Your computer
├── Python 3.12
├── boto3 version X
├── dependencies
├── OS libraries
└── environment variables
```

Someone else's computer:

```text
Different Python
Different boto3
Different OS
Different dependencies
```

💥 Problems.

With Docker:

```text
Docker Image
├── Python
├── dependencies
├── application
└── runtime environment
```

Same image → predictable environment.

# 2. Your first production-style Dockerfile

For example, imagine:

```text
s3-backup/
├── app.py
├── requirements.txt
└── Dockerfile
```

A basic Dockerfile:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

CMD ["python", "app.py"]
```

This works.

But **today you're learning to make it better.**

---

# 3. Multi-stage builds

You've already learned this on Day 164.

The idea:

```text
Builder Stage
     ↓
install/build dependencies
     ↓
production artifact
     ↓
Runtime Stage
     ↓
only what application needs
```

Why?

Smaller image.

Smaller image means:

* faster downloads
* faster deployments
* smaller attack surface
* less storage
* faster CI/CD

For a Python application, however, don't blindly use multi-stage builds just because they're trendy. If your application has no compilation/build step, a simple slim runtime image may already be appropriate.

The principle you should remember is:

> **Build environment ≠ runtime environment.**

---

# 4. Non-root users 🔐

This is extremely important.

By default, some containers run as:

```text
root
```

That's dangerous.

Suppose an attacker somehow exploits your application.

If your process is root:

```text
Application compromise
        ↓
root privileges
        ↓
potentially more damage
```

Instead:

```text
Application
    ↓
non-root user
    ↓
limited permissions
```

Example:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

RUN useradd --create-home appuser

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

RUN chown -R appuser:appuser /app

USER appuser

CMD ["python", "app.py"]
```

The key line:

```dockerfile
USER appuser
```

Remember that.

---

# 5. `.dockerignore`

This is another important production habit.

Create:

```text
.dockerignore
```

Example:

```text
.git
.github
__pycache__
*.pyc
.env
.venv
venv
README.md
```

Why?

Without `.dockerignore`, you might accidentally send:

```text
.env
AWS credentials
Git history
virtual environments
cache files
```

to the Docker build context.

### VERY IMPORTANT

Never put:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

inside your Dockerfile.

Never:

```dockerfile
ENV AWS_SECRET_ACCESS_KEY=...
```

Credentials should come from the environment/role/secret mechanism at runtime.

# 7. Docker Compose + LocalStack

Now we get to the **cool part of Day 168.**

Normally your S3 backup application talks to:

```text
Python
   ↓
AWS
   ↓
S3
```

That means your local testing could accidentally interact with real AWS.

Instead:

```text

      ↓

      ↓

```

You can test locally.

# 8. What is LocalStack?

Think of LocalStack as:

> **A local AWS-like environment for development and testing.**

Instead of:

```text
boto3 → AWS S3
```

you can have:

```text
boto3 → LocalStack S3
```

Your code can therefore be tested without constantly touching your real AWS account.

---

# 9. Compose architecture

Your `compose.yml` might conceptually look like:

```yaml
services:

  app:
    build: .
    depends_on:
      - localstack

  localstack:
    image: localstack/localstack
    ports:
      - "4566:4566"
```

Now:

```bash
docker compose up
```

starts:

```text
┌──────────────────────────────┐
│ Docker Compose               │
│                              │
│  ┌────────────┐              │
│  │ Python App │              │
│  └─────┬──────┘              │
│        │                     │
│        ▼                     │
│  ┌────────────┐              │
│  │ LocalStack │              │
│  └────────────┘              │
│                              │
└──────────────────────────────┘
```

---

# 10. Important Docker networking concept

Notice something interesting.

Your Python container shouldn't connect to:

```text
localhost:4566
```

to reach LocalStack.

Inside the Compose network, use the **service name**:

```text
localstack:4566
```

Why?

Docker Compose provides internal DNS.

So:

```text
app
 ↓
localstack
 ↓
port 4566
```

This connects directly to the LocalStack container.

This is exactly the Docker networking concept you learned earlier.

# 11. Environment variables

Your application could use something like:

```text
AWS_ENDPOINT_URL=http://localstack:4566
```

Then your Python code can use that endpoint when running locally.

Conceptually:

```python
import boto3
import os

endpoint = os.getenv("AWS_ENDPOINT_URL")

s3 = boto3.client(
    "s3",
    endpoint_url=endpoint
)
```

Then:

### Local

```text
AWS_ENDPOINT_URL=http://localstack:4566
```

### Production

Don't set the LocalStack endpoint.

Your application talks to real AWS.

This gives you:

```text
Same application
       │
       ├── Development → LocalStack
       │
       └── Production  → AWS
```

That's a **very useful cloud engineering pattern.**

# 13. What is Amazon ECR?

ECR = **Elastic Container Registry**

Think:

```text
GitHub
   ↓
source code

ECR
   ↓
Docker images
```

For example:

```text
123456789012.dkr.ecr.ap-south-1.amazonaws.com/s3-backup
```

could contain:

```text
s3-backup:1.0
s3-backup:1.1
s3-backup:latest
```

Your deployment system can later pull the image from ECR.

---

# 14. Docker login to ECR

The command you listed is important:

```bash
aws ecr get-login-password --region ap-south-1 \
| docker login \
--username AWS \
--password-stdin ACCOUNT.dkr.ecr.ap-south-1.amazonaws.com
```

Understand what is happening:

```text
AWS CLI
   ↓
get temporary authentication token
   ↓
pipe |
   ↓
docker login
   ↓
ECR
```

Then:

```bash
docker tag s3-backup:1.0 \
ACCOUNT.dkr.ecr.ap-south-1.amazonaws.com/s3-backup:1.0
```

And:

```bash
docker push \
ACCOUNT.dkr.ecr.ap-south-1.amazonaws.com/s3-backup:1.0
```

# 15. GitHub Actions pipeline

Your workflow concept:

```yaml
name: Docker CI/CD

on:
  push:
    branches:
      - main

jobs:
  build-scan-push:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout
        uses: actions/checkout@v4

      - name: Build image
        run: |
          docker build -t s3-backup:${{ github.sha }} .

      - name: Scan image
        run: |
          trivy image --severity HIGH,CRITICAL \
            s3-backup:${{ github.sha }}

      # authenticate to AWS

      # login to ECR

      # tag image

      # push image
```

Notice:

```text
${{ github.sha }}
```

This gives your image a unique identifier based on the Git commit.

That's better than relying exclusively on:

```text
latest
```

because you can trace:

```text
Docker image
     ↓
Git commit
     ↓
exact source code
```

That's an excellent production habit.

# 16. Trivy 🔍

Now security.

Install/use Trivy and scan:

```bash
trivy image s3-backup:1.0
```

You'll see vulnerabilities such as:

```text
CRITICAL
HIGH
MEDIUM
LOW
```

Your target today:

> **Understand and fix CRITICAL and HIGH vulnerabilities rather than simply ignoring them.**

Common fixes:

### Problem 1 — old base image

```dockerfile
FROM python:3.9
```

Try a currently supported Python release and a maintained slim base.

### Problem 2 — vulnerable Python dependency

Your:

```text
requirements.txt
```

might contain an old package.

Update it.

### Problem 3 — OS package vulnerability

Your base image may contain an outdated system package.

Updating the base image can often resolve it.

---

# 17. Don't blindly do this ❌

You might see:

```bash
trivy image --ignore-unfixed ...
```

and think:

> "Great, vulnerability gone."

No.

You didn't fix the vulnerability.

You merely hid it.

The engineering mindset is:

```text
Vulnerability
      ↓
Understand why
      ↓
Update dependency/base image
      ↓
Rebuild
      ↓
Scan again
```

# 19. Docker Best Practices — your mental cheat sheet

You need to remember these:

| Practice              | Why                            |
| --------------------- | ------------------------------ |
| Small base image      | Smaller attack surface         |
| Multi-stage build     | Smaller production image       |
| `.dockerignore`       | Don't send unnecessary/secrets |
| Non-root user         | Reduce privilege               |
| Pin dependencies      | Reproducibility                |
| Layer caching         | Faster builds                  |
| Health checks         | Detect unhealthy containers    |
| Environment variables | Configuration outside image    |
| Never bake secrets    | Prevent credential leaks       |
| Scan images           | Find vulnerabilities           |
| Use immutable tags    | Trace deployments              |
| Resource limits       | Prevent runaway containers     |
| Keep images updated   | Security patches               |

**Why containerize?**

### 2.

**What is an image?**

**What is a container?**

**Why non-root?**

> Reduce the impact of a container compromise.

**Why LocalStack?**

> Test AWS-integrated applications locally without relying on real AWS resources.

**Why Compose?**

> Define and run multiple related containers as one application stack.

**Why Trivy?**

> Detect vulnerabilities in container images.

### 9.

**Why ECR?**

> Store and distribute Docker images within AWS.

### 10.

**Why GitHub Actions?**

> Automatically build, test, scan, and publish images whenever code changes.
