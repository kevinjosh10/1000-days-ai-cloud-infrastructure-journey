# 🚀 Day 162 — Docker Architecture & Core Concepts

Today is Day 162 / 1000 of your journey toward becoming an AI Cloud Infrastructure Engineer.

Today’s goal is simple:
Understand what Docker actually is, how it works, and become comfortable running/managing containers from the CLI.

Since you're new to Docker, I'll teach this from zero, but connect everything to AWS/cloud concepts you already know.

### 1. Why Docker?
Before Docker, imagine you build a Python application.
Your application needs:
* Python 3.12
* Flask
* Requests
* Some system libraries
* Environment variables
* Configuration

It works perfectly on your laptop.
Then you give it to another developer.
They run:
`python app.py`

And get:
* ModuleNotFoundError
* Python version mismatch
* Library version mismatch

This is the classic:
*"It works on my machine."*
problem.

Docker solves this by packaging your application together with its environment.

```text
┌─────────────────────────────┐
│ Docker Container            │
│                             │
│  Your Application           │
│  Python 3.12                │
│  Dependencies               │
│  Configuration              │
│                             │
└─────────────────────────────┘
```

Now the same container can run on:
Your laptop ↓ AWS EC2 ↓ AWS ECS ↓ AWS Fargate ↓ Kubernetes

This is why Docker is extremely important for cloud engineering.

### 2. VM vs Container
You already know AWS EC2.
Think about an EC2 VM:
```text
Physical Server
       │
       ▼
   Hypervisor
       │
 ┌─────┴─────┐
 ▼           ▼
EC2 VM      EC2 VM
 │           │
 OS          OS
 │           │
App         App
```
Each VM contains a full operating system.

Containers work differently:
```text
Physical Server
       │
       ▼
     Linux
       │
     Docker
 ┌─────┼─────┐
 ▼     ▼     ▼
App1  App2  App3
```
Containers share the host's kernel.
That's one reason containers are generally:
* faster to start
* lighter than VMs
* more portable
* easier to scale

**Important distinction**
* **VM**: Virtualizes hardware.
* **Container**: Isolates applications/processes at the OS level.

### 3. Docker Architecture
This is one of the most important things to understand today.
Docker has several components:
```text
   Docker CLI
       │
  commands
       ▼
 Docker Daemon
    dockerd
       │
 ┌────────┴────────┐
 ▼                 ▼
Containers       Images
       │
       ▼
   containerd
       │
       ▼
 Container Runtime
```
Let's break it down.

### 4. Docker CLI
When you type:
`docker run nginx`
you're using the:
**Docker CLI**
CLI = Command Line Interface.
The CLI doesn't actually run the container itself.
It communicates with the Docker daemon.

Think:
```text
   You
    │
 docker run nginx
    ▼
Docker CLI
    │
 request
    ▼
Docker Daemon
```

### 5. Docker Daemon — dockerd
The Docker daemon is the background service responsible for managing Docker objects.
It manages:
* Images
* Containers
* Networks
* Volumes

The daemon is called:
`dockerd`

So remember:
**CLI asks. Daemon does.**
Example:
`docker run nginx`
The CLI sends the request.
`dockerd` handles the actual work.

### 6. containerd
You don't need to become an expert in containerd today.
Just understand its position.
Docker uses containerd as a lower-level container runtime component.

Simplified:
Docker CLI ↓ dockerd ↓ containerd ↓ container runtime ↓ Container
You will encounter containerd frequently when working with cloud infrastructure and Kubernetes later.

For today:
`containerd` = low-level component responsible for managing container lifecycle/runtime operations.

### 7. Docker Hub
Now imagine you want an Nginx container.
You don't need to build Nginx yourself.
You can download the official image:
`docker pull nginx`

Docker searches a registry.
The most common public registry is:
**Docker Hub**

Think of Docker Hub like:
```text
Docker Hub
 │
 ├── nginx
 ├── ubuntu
 ├── python
 ├── redis
 ├── node
 └── postgres
```
You can explore images on [Docker Hub](https://hub.docker.com/?utm_source=chatgpt.com).

### 8. Image vs Container
This distinction is VERY IMPORTANT.

**Image**
An image is a:
Read-only template used to create containers.
Example:
nginx image

You can create multiple containers from it:
```text
   nginx IMAGE
        │
  ┌────────┼────────┐
  ▼        ▼        ▼
web01    web02    web03
container container container
```

**Container**
A container is:
A running instance of an image.

Think about AWS:
AMI → EC2 instance
Docker:
Image → Container
That's a useful mental model.

### 9. Docker Layers
Docker images aren't just one giant file.
They're composed of layers.
For example:
```dockerfile
FROM python:3.12
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY app.py .
```

Conceptually:
```text
┌─────────────────────┐
│ COPY app.py         │ ← Layer
├─────────────────────┤
│ pip install         │ ← Layer
├─────────────────────┤
│ requirements.txt    │ ← Layer
├─────────────────────┤
│ Python base image   │ ← Layer
└─────────────────────┘
```
Why is this useful?
Because Docker can cache layers.
Suppose you change:
`app.py`
Docker doesn't necessarily need to rebuild everything from scratch.
It can reuse unchanged layers.
This becomes extremely important when we learn:
**Dockerfile optimization**
later this week.

### 10. Your First Docker Commands
Let's get practical.
First verify Docker:
`docker --version`
Then:
`docker info`
If Docker is running, you'll see information about the Docker environment.

### 11. Pull an Image
Let's download Nginx.
`docker pull nginx`
Then:
`docker images`
You should see something similar to:
`REPOSITORY   TAG       IMAGE ID       SIZE`
`nginx        latest    xxxxxxxx       xxxMB`
You've downloaded an image.
Nothing is running yet.

### 12. Run Your First Container
Run:
`docker run nginx`
Docker will:
Check local images ↓ nginx exists? ↓ Create container ↓ Start nginx
But there's an issue.
The terminal will be attached to the container.
Press:
`Ctrl + C`
to stop it.

### 13. Run in Background
Use:
`docker run -d nginx`
`-d` means:
**detached mode**
The container runs in the background.
Check:
`docker ps`
You'll see something like:
`CONTAINER ID   IMAGE   STATUS       NAMES`
`abc123         nginx   Up 10 sec    ...`

### 14. docker ps vs docker ps -a
This is something you should memorize.
Running containers
`docker ps`
Shows:
RUNNING containers

All containers
`docker ps -a`
Shows:
RUNNING + STOPPED

So:
`docker ps` ↓ "What is running?"
`docker ps -a` ↓ "Show me everything."

### 15. Naming Containers
Instead of getting a random container name:
`docker run -d --name web01 nginx`
Now:
`docker ps`
will show:
NAME
`web01`
You can then refer to it easily:
`docker stop web01`
instead of using the container ID.

### 16. Port Mapping
This is very important for cloud engineering.
Suppose Nginx listens inside the container on:
Port 80
But you want to access it from your laptop through:
localhost:8080
Use:
`docker run -d --name web01 -p 8080:80 nginx`
The syntax is:
`-p HOST_PORT:CONTAINER_PORT`
Therefore:
`8080:80`
means:
```text
Your laptop localhost:8080
       │
       ▼
     Docker
       │
       ▼
Container port 80
       │
       ▼
     Nginx
```
Open:
`http://localhost:8080`
You should see the Nginx welcome page.

### 17. Why Port Mapping Matters
Imagine AWS ECS running your container.
Your application might listen inside the container:
Port 8000
But traffic might enter through:
Load Balancer :443
The infrastructure connects these pieces.

Docker port mapping gives you the fundamental mental model:
External traffic ↓ Host port ↓ Container port ↓ Application
You'll use this concept heavily with:
* ECS
* Fargate
* Load Balancers
* Docker Compose
* Kubernetes later

### 18. Environment Variables
You can provide configuration to containers.
Example:
```bash
docker run -d \
  --name web01 \
  -e APP_ENV=production \
  nginx
```
Now the container receives:
`APP_ENV=production`

You can have multiple variables:
```bash
docker run -d \
  --name app \
  -e APP_ENV=production \
  -e PORT=8080 \
  nginx
```
Environment variables are extremely common in cloud deployments.

### 19. --rm
Normally, when a container stops, the container still exists.
Example:
`docker run nginx`
Stop it:
`docker ps -a`
You'll still see the stopped container.

If you don't want that:
`docker run --rm nginx`
When it exits:
Container stops ↓ Container automatically removed
Useful for temporary containers.

### 20. docker exec
This is one of your most useful commands.
Suppose:
`docker run -d --name web01 nginx`
You want to enter the running container.
Try:
`docker exec -it web01 bash`
Meaning:
`docker exec` ↓ Execute command inside container
`-it` ↓ Interactive terminal
`web01` ↓ Target container
`bash` ↓ Shell to launch
You'll get something like:
`root@abc123:/#`
Now you're inside the container.

### 21. Explore the Container
Inside:
`ls`
Try:
`cat /etc/os-release`
Try:
`ps`
Try:
`env`
Then:
`exit`
You're back on your host.

### 22. Container Lifecycle
Think of containers as having a lifecycle:
```text
   Image
     │
     ▼
docker run
     │
     ▼
  Created
     │
     ▼
  Running
     │
     ▼
docker stop
     │
     ▼
  Stopped
     │
     ▼
docker start
     │
     ▼
Running again
     │
     ▼
docker rm
     │
     ▼
  Deleted
```

Very important distinction:
Stop
`docker stop web01`
Stops the container.

Start
`docker start web01`
Starts an existing stopped container.

Remove
`docker rm web01`
Deletes the container.

### 23. Image vs Container Removal
Don't confuse these.
Remove container
`docker rm web01`
Remove image
`docker rmi nginx`

Relationship:
```text
IMAGE
 │
 ├── Container 1
 ├── Container 2
 └── Container 3
```
You generally can't remove an image while containers still depend on it.

`cat /etc/os-release`

`ls`

`exit`

`docker ps -a`

Start it again:
`docker start ubuntu01`
Check:
`docker ps`
Interesting, right?
It starts and immediately stops again because its main process (bash) isn't attached.
That's a very important container concept:
**A container lives as long as its main process is running.**

### 29. Clean Everything
Stop:
`docker stop web01 redis01`

`docker rm web01 redis01 ubuntu01 python01`

`docker ps -a`

Your images should still exist:
`docker images`
That's because:
**Removing a container does NOT automatically remove its image.**
