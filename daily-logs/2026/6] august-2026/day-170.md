Today, I moved from *"I can run containers"* to **"I can run containers safely in production."**

I learned that assuming a container will behave nicely is a massive operational mistake. If a rogue worker container consumes all the RAM on an EC2 instance, it will suffocate the database and API running next to it. Today was all about enforcing strict resource boundaries to make my cloud infrastructure predictable.

## 1. Controlling CPU Execution

I learned the difference between hard limits and relative priority:
* **Hard Limits (`--cpus="0.5"`):** This restricts the container to exactly 50% of a single CPU core's processing time. If the container tries to exceed this, Docker physically throttles the process. It gets slower, but it doesn't crash.
* **Relative Priority (`--cpu-shares=512`):** This doesn't set a hard ceiling. Instead, it tells Docker how to prioritize this container *only when multiple containers are fighting for the same CPU*.

For my Flask API, I enforced a hard ceiling:
```bash
docker run -d --name flask-api --cpus="0.25" flask-api
```

## 2. Controlling Memory (And the Danger of OOM)

Memory behaves entirely differently than CPU. 

If a container hits a CPU limit, it is throttled. If a container hits a **Memory limit**, it can be violently killed by the Linux Kernel.

I enforced memory limits like this:
```bash
docker run -d \
  --name flask-api \
  --memory="128m" \
  --memory-swap="128m" \
  flask-api
```
*Note: Setting `--memory-swap` exactly equal to `--memory` ensures the container gets absolutely zero additional swap space.*

If my Flask API tries to consume 129 MB of RAM, the Linux **OOM (Out Of Memory) Killer** steps in and terminates the container. I can physically verify this by running `docker inspect flask-api` and looking for the terrifying `"OOMKilled": true` flag.

## 3. Observability with `docker stats`

To actually engineer limits, I cannot just guess. I have to measure.

I learned to use `docker stats`—which is effectively the `top` command for containers. It gives me a live, streaming view of:
* CPU %
* MEM USAGE / LIMIT
* Network I/O
* Block I/O

I opened two terminals. In Terminal 1, I ran `docker stats flask-api`. In Terminal 2, I hit my container with ApacheBench (`ab -n 1000 -c 50 http://localhost:5000/`) to simulate 50 concurrent users making 1000 requests. 

Watching the CPU spike exactly to my `0.25` limit and flatten out—while memory climbed steadily toward `128MiB`—was an incredible visualization of infrastructure physics.

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **Why do containers need resource limits?**
   > To prevent a single rogue or heavily-loaded container from exhausting host resources (CPU/RAM) and starving other critical workloads.
2. **What happens when a container exceeds its CPU limit?**
   > It is throttled by the Docker daemon. Execution slows down, but the process generally does not crash.
3. **What happens when a container exceeds its Memory limit?**
   > It triggers an OOM (Out Of Memory) condition, and the Linux kernel will likely kill the process (`OOMKilled: true`).
4. **How do you observe live container resource consumption?**
   > Using the `docker stats` CLI command.
5. **How does this translate to Kubernetes?**
   > Docker's `--cpus` and `--memory` flags are the foundational concepts behind Kubernetes `resources.limits` and `resources.requests` in a Pod specification.
