## 1. Dropping Linux Capabilities (The Principle of Least Privilege)

By default, Docker drops some Linux capabilities, but it still grants containers significant privileges. I learned how to enforce absolute least privilege using the `--cap-drop` flag.

Instead of trying to figure out what to remove, the most secure pattern is to drop *everything* and only add back exactly what the application needs:
```bash
docker run \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  flask-api
```
In this example, I stripped the container of all system privileges, only allowing it the specific ability to bind to network ports. If an attacker breaches this container, they are trapped in a powerless environment.

## 2. Managing Secrets Securely

I discovered a terrifying fact today: **Environment variables are terrible for storing secrets.** They can be easily leaked via `docker inspect`, application crash logs, or spawned child processes.

Instead, I learned the Docker Swarm secrets pattern:
```bash
docker secret create db_password -
docker service create --secret db_password my-app
```
Rather than passing the password as an `ENV`, Docker securely mounts the secret directly into memory as a temporary file at `/run/secrets/db_password`. The application reads the file once at startup. If the container crashes, the secret vanishes from memory. 

## 3. The Security Defense-in-Depth Model

I mapped out the mental model for how Docker actually secures a container using Linux kernel features:
* **Namespaces:** Isolate what a container can *see* (its own PIDs, networks, mount points).
* **Cgroups:** Isolate what a container can *use* (CPU, Memory limits).
* **Seccomp:** Filters what System Calls the container can make to the Linux Kernel.
* **AppArmor/SELinux:** Applies strict Mandatory Access Control profiles.
* **Capabilities:** Granularly limits root privileges.

## 4. Trivy: CI/CD Security Gating

I practiced running vulnerability scans again using Trivy, but this time focusing on CI/CD pipeline integration:
```bash
trivy image --severity CRITICAL,HIGH my-app:1.0
```
I learned how to interpret CVE (Common Vulnerabilities and Exposures) scores, identify affected packages, and find fix versions. The key takeaway: Trivy isn't just an auditing tool; it should be used as a hard gate in GitHub Actions. If a `CRITICAL` vulnerability is detected, the pipeline must fail immediately, blocking the image from ever reaching ECR.

## 5. Preventing Supply Chain Attacks (Docker Content Trust)

Finally, I tackled image provenance. How do I know the `nginx:alpine` image I just pulled wasn't secretly modified by a hacker sitting in a coffee shop via a Man-in-the-Middle attack?

Enter **Docker Content Trust (DCT)**. 
By running:
```bash
export DOCKER_CONTENT_TRUST=1
```
Docker will only pull and push *cryptographically signed* images (using Notary). If an attacker tampers with the image registry, DCT will instantly reject the image because the cryptographic signature will fail validation. This is an essential guardrail against supply chain attacks in production!

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **Why is it dangerous to pass passwords via environment variables?**
   > Environment variables can easily leak into crash logs, child processes, or be read directly via `docker inspect`.
2. **How do Docker Secrets work?**
   > They are securely distributed and mounted as in-memory files (tmpfs) inside the container at `/run/secrets/`, rather than baked into the environment.
3. **What is the most secure way to manage Linux Capabilities?**
   > Drop all capabilities (`--cap-drop=ALL`) and explicitly whitelist only the ones required (`--cap-add=...`).
4. **How do you prevent a Man-in-the-Middle or Supply Chain attack on Docker images?**
   > Enable Docker Content Trust (`DOCKER_CONTENT_TRUST=1`) to mathematically guarantee you are only interacting with cryptographically signed images.
5. **What is Seccomp?**
   > A Linux kernel feature used by Docker to filter and restrict the specific system calls a container can make to the host OS.
