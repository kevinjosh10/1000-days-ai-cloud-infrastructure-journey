My first problem of the week: **How do I configure my application without rebuilding my Docker image every time I move from Dev to Staging to Production?** 

If my database URL is baked into my Docker image, I have to build three separate images. That violates the core principle of containerization. Today, I solved this by decoupling configuration using **ConfigMaps**.

## 1. The Power of ConfigMaps

A ConfigMap is a Kubernetes object used to store non-sensitive configuration data (like database URLs, feature flags, or application settings) as key-value pairs. 

By pulling this data out of the image and into the cluster, I make my Docker images completely **environment-agnostic**. The exact same image can be deployed to Dev and Prod; only the ConfigMap it reads from changes.

## 2. Creating ConfigMaps

I practiced creating ConfigMaps in three different ways:

**1. From Literals (CLI):**
```bash
kubectl create configmap app-config \
  --from-literal=DB_HOST=postgres \
  --from-literal=APP_ENV=production
```

**2. From a File:**
```bash
kubectl create configmap app-config --from-file=config.properties
```

**3. From Declarative YAML (Best Practice):**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: postgres
  APP_ENV: production
```

## 3. Injecting Configuration (Method 1: ENV Vars)

The most common way to consume a ConfigMap is by injecting its values into the Pod as Environment Variables. 

I can map specific keys individually:
```yaml
env:
  - name: DATABASE_HOST
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: DB_HOST
```
Or, if I have 20 variables, I can inject the entire ConfigMap at once:
```yaml
envFrom:
  - configMapRef:
      name: app-config
```

## 4. Injecting Configuration (Method 2: Volume Mounts)

What if my application doesn't read environment variables? What if it requires a physical configuration file (like `nginx.conf` or `application.properties`)?

I learned that Kubernetes can mount a ConfigMap as a **Volume**.
* The ConfigMap `data` keys become physical filenames.
* The ConfigMap `data` values become the file contents.

## 5. Hands-On Nginx Practice (Hot Reloading)

I put this into practice by overriding the default Nginx configuration:
1. I created a ConfigMap containing a custom `nginx.conf` text block.
2. I mounted it into my Pod at `/etc/nginx/conf.d/`.
3. I verified Nginx successfully loaded my custom configuration.

**The coolest discovery of the day:** I updated the ConfigMap YAML and re-applied it. Without me restarting the Pod, Kubernetes automatically updated the physical file mounted inside the container within about 60 seconds! 

*(Note: Applications like Nginx might still need a reload command triggered to actually read the new file, but the file itself updates dynamically on disk!)*

## 🧠 The 5 things I can confidently explain today

If asked in an interview, I can now articulate:

1. **Why do we use ConfigMaps?**
   > To decouple configuration data from container images, keeping the images strictly environment-agnostic so the same image can be promoted through Dev, Staging, and Production.
2. **What are the two primary ways a Pod can consume a ConfigMap?**
   > As Environment Variables, or as physical files mounted via a Volume.
3. **How do you inject an entire ConfigMap into a Pod as environment variables?**
   > Using the `envFrom` array and referencing the ConfigMap name.
4. **What happens if you update a ConfigMap that is mounted as a Volume?**
   > Kubernetes will automatically update the mounted file inside the running container within a minute or so.
5. **Should I store database passwords in a ConfigMap?**
   > No! ConfigMaps are for non-sensitive data. Passwords must be stored in Kubernetes Secrets.
