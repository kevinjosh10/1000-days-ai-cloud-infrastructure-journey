# 2. Architectural Overview of `grep`

The name `grep` derives from the classic `ed` line editor command:
$$\text{g/re/p} \implies \text{Global} \; / \; \text{Regular Expression} \; / \; \text{Print}$$

`grep` processes text streams sequentially:
1. It ingests an input stream line-by-line.
2. It compiles the specified regular expression into a deterministic finite automaton (DFA) or non-deterministic finite automaton (NFA).
3. If a line matches the pattern, `grep` emits it to `stdout` (or counts it, or extracts matching tokens).
4. If no match occurs, the line is silently discarded.
5. Exit statuses strictly communicate outcomes: `0` (at least one match found), `1` (zero matches found), `2` (syntax error or missing file).

```text
                           The grep Pipeline Engine
                           
               [ Raw Text Stream / Inode Input ]
                               │
                               ▼
        ┌──────────────────────────────────────────────┐
        │ Regex Pattern Compilation (DFA / NFA Engine) │
        └──────────────────────┬───────────────────────┘
                               │
                Match Evaluator per Line
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
      [ MATCH FOUND ]                   [ NO MATCH ]
              │                                 │
              ▼                                 ▼
    Emit line / token to stdout         Silently discard
    Set Exit Status = 0                 Set Exit Status = 1
```

# 3. Regular Expression Flavors (BRE vs. ERE vs. PCRE)

One of the most frequent sources of confusion in Linux scripting is the divergence between regex flavors:

```text
                    Regex Flavor Complexity Hierarchy
                    
  BRE (Basic)                ERE (Extended)               PCRE (Perl-Compatible)
  grep "pat"                 grep -E "pat"                grep -P "pat"
  ──────────────────────────────────────────────────────────────────────────────
  • Default POSIX standard   • Modern POSIX standard      • Perl regular expressions
  • Metacharacters require   • Clean metacharacters       • Advanced tokens: \d, \w
    backslashes: \+, \?, \|    +, ?, |, (), {}              lookarounds (?=...), (?!...)
  • Harder to read           • Highly portable & clean    • Not universally available
```

| Feature | Basic Regex (BRE) `grep` | Extended Regex (ERE) `grep -E` | Perl Compatible (PCRE) `grep -P` |
|---|---|---|---|
| **Alternation (OR)** | `foo\|bar` | `foo|bar` | `foo|bar` |
| **One or More (+)** | `[0-9]\+` | `[0-9]+` | `\d+` or `[0-9]+` |
| **Zero or One (?)** | `https\?` | `https?` | `https?` |
| **Interval Bounds** | `[0-9]\{3\}` | `[0-9]{3}` | `\d{3}` |
| **Grouping** | `\(abc\)` | `(abc)` | `(abc)` |
| **Digit Shorthand** | `[0-9]` or `[[:digit:]]` | `[0-9]` or `[[:digit:]]` | `\d` |
| **Lookahead/Lookbehind** | Unsupported | Unsupported | `(?<=from )[0-9.]+` |

**Enterprise Recommendation:** Standardize on **`grep -E` (Extended Regular Expressions)** for cloud infrastructure scripts. It provides clean syntax without cumbersome backslash escaping and is universally available across Linux distributions, BusyBox, and macOS.

# 4. Essential `grep` Operational Flags

| Flag | Purpose | Operational Cloud Infrastructure Use Case |
|---|---|---|
| **`-E`** | Extended Regex mode | Complex pattern matching without escaping (`error|fail|critical`) |
| **`-v`** | Invert match | Stripping comments and blank lines: `grep -vE '^\s*#|^\s*$' /etc/app.conf` |
| **`-c`** | Count matching lines | Quantifying incident severity: `FAILED=$(grep -c "Failed password" auth.log)` |
| **`-n`** | Line numbering | Correlating log anomalies with trace lines for post-mortem timelines |
| **`-o`** | Only matching text | Extracting isolated tokens (IPs, UUIDs, hashes, email addresses) |
| **`-q`** | Quiet / Silent mode | Conditional evaluation in scripts: `if grep -q "CRITICAL" app.log; then ...` |
| **`-H`** | Print filename header | Multi-file searching across directory globs (`grep -H "404" /var/log/nginx/*.log`) |
| **`-i`** | Case-insensitive | Auditing user input or unstructured logs where casing varies |
| **`-F`** | Fixed-string search | Ultra-fast exact literal matching bypassing regex compilation entirely |
| **`-w`** | Whole-word matching | Preventing partial matches (e.g. matching `root` but not `chroot` or `rootfs`) |
| **`-r` / `-R`** | Recursive traversal | Searching entire directory trees (`grep -rn "API_KEY" /opt/code/`) |

# 5. Contextual Inspection (`-A`, `-B`, `-C`)

When investigating security breaches or application panics, the matching line alone rarely tells the entire story. The root cause usually occurs milliseconds before or after the failure:

```text
                        Contextual Window Mechanics
                        
        Line 40: Accepted password for dev from 10.0.0.5  ▲
        Line 41: pam_unix(sshd:session): session opened    │  -B 2 (Before)
        ─────────────────────────────────────────────────  ┴
  ──►   Line 42: Failed password for root from 203.0.113.10  [MATCH]
        ─────────────────────────────────────────────────  ┬
        Line 43: Connection closed by 203.0.113.10 port 22 │  -A 2 (After)
        Line 44: pam_unix(sshd:auth): check pass; user unk ▲
        
        Using: grep -C 2 "Failed password for root" auth.log
```

- **`-A NUM` (After):** Displays $NUM$ lines following the match.
- **`-B NUM` (Before):** Displays $NUM$ lines preceding the match.
- **`-C NUM` (Both Context):** Displays $NUM$ lines before and after the match.

# 6. Regular Expression Building Blocks

### A. Anchors (Line Boundaries)
- `^` asserts the start of a line: `grep '^Nov 27' auth.log`
- `$` asserts the end of a line: `grep 'ssh2$' auth.log`
- `^$` matches an empty line; `^\s*$` matches a line containing only whitespace.

### B. POSIX Character Classes
POSIX character classes guarantee locale-independent behavior:
- `[[:digit:]]` $\iff [0-9]$
- `[[:alpha:]]` $\iff [a-zA-Z]$
- `[[:alnum:]]` $\iff [a-zA-Z0-9]$
- `[[:space:]]` $\iff$ Whitespace characters (spaces, tabs, newlines)
- `[[:punct:]]` $\iff$ Punctuation characters (`! " # $ % & ' ( ) * + , - . / : ; < = > ? @ [ \ ] ^ _ \` { \| } ~`)

### C. IPv4 Extraction Regular Expression
Matching IPv4 addresses in unstructured text:
```bash
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' auth.log
```
*Breakdown:*
1. `[0-9]{1,3}\.`: Matches 1 to 3 digits followed by a literal dot (`.`).
2. `(...){3}`: Repeats that octet-and-dot grouping exactly three times (e.g. `192.168.1.`).
3. `[0-9]{1,3}`: Matches the final 1 to 3 digits of the host octet (e.g. `50`).

# 7. Threat Intelligence: Pipeline Frequency Distribution

A single failed login is routine operational noise (a user mistyping a password). One thousand failed logins from the same IP address across 60 seconds is a **brute-force attack**.

To identify suspicious threat actors, we chain `grep`, `sort`, and `uniq` into a frequency analysis pipeline:

```text
                  Threat Intelligence Pipeline Architecture
                  
    [ auth.log ]
         │
         ▼
    grep -E "Failed password|Invalid user"    ──► Isolate security failure events
         │
         ▼
    grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}'   ──► Extract pure IP address tokens
         │
         ▼
    sort                                      ──► Group identical IPs consecutively
         │
         ▼
    uniq -c                                   ──► Deduplicate and prefix occurrence count
         │
         ▼
    sort -nr                                  ──► Rank numerically descending (Top attackers)
```

```bash
grep -E "Failed password|Invalid user" /var/log/auth.log | \
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | \
sort | \
uniq -c | \
sort -nr | \
head -n 10
```

### Full Source Code: `linux-mastery/scripts/15_security_audit_grep.sh`

```bash
#!/usr/bin/env bash

# ==============================================================================
# PROJECT  : 15_security_audit_grep.sh
# TRACK    : Linux & Shell Scripting — Day 15/30 (Week 11 Kickoff)
# JOURNEY  : Day 271 / 1000
# PURPOSE  : Advanced grep, Regex & SSH Authentication Security Log Auditor
# USAGE    : ./15_security_audit_grep.sh [custom_auth_log]
# ==============================================================================

# Defensive strict mode
set -uo pipefail

# ------------------------------------------------------------------------------
# 1. COLOR & FORMATTING CONSTANTS
# ------------------------------------------------------------------------------
RED='\033[0;31m'
GREEN='\033[0;32m'
YELLOW='\033[1;33m'
BLUE='\033[0;34m'
CYAN='\033[0;36m'
BOLD='\033[1m'
RESET='\033[0m'

# ------------------------------------------------------------------------------
# 2. RESOLVE LOG SOURCE & TEMPORARY STAGING
# ------------------------------------------------------------------------------
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
SCRIPT_NAME="${0##*/}"

show_help() {
    cat << EOF
Usage: ${SCRIPT_NAME} [LOG_FILE]

Security Log Auditing Utility using Advanced grep and Regular Expressions.

Arguments:
  LOG_FILE               Path to authentication log file (optional)

If no LOG_FILE is specified, the script automatically searches for:
  1. Local sample_auth.log in script directory
  2. /var/log/auth.log (Debian/Ubuntu)
  3. /var/log/secure (RHEL/CentOS/Rocky/Alma)
  4. Systemd journal via journalctl

Exit Codes:
  0 : Audit completed with low or normal findings
  1 : Security warning: High volume of failed authentication events detected
  2 : Missing or unreadable authentication logs
EOF
}

if [[ $# -ge 1 && ( "$1" == "-h" || "$1" == "--help" ) ]]; then
    show_help
    exit 0
fi

# Create a secure temporary file for normalized log analysis
TEMP_LOG=$(mktemp)
cleanup() {
    rm -f "$TEMP_LOG"
}
trap cleanup EXIT

# Determine log source
INPUT_ARG="${1:-}"

if [[ -n "$INPUT_ARG" ]]; then
    if [[ -r "$INPUT_ARG" ]]; then
        cp "$INPUT_ARG" "$TEMP_LOG"
        LOG_SOURCE="$INPUT_ARG"
    else
        echo -e "${RED}[ERROR] Specified log file not readable: ${INPUT_ARG}${RESET}" >&2
        exit 2
    fi
elif [[ -r "${SCRIPT_DIR}/sample_auth.log" ]]; then
    cp "${SCRIPT_DIR}/sample_auth.log" "$TEMP_LOG"
    LOG_SOURCE="${SCRIPT_DIR}/sample_auth.log (Local Sample)"
elif [[ -r "sample_auth.log" ]]; then
    cp "sample_auth.log" "$TEMP_LOG"
    LOG_SOURCE="sample_auth.log (Current Directory)"
elif [[ -r "/var/log/auth.log" ]]; then
    cp "/var/log/auth.log" "$TEMP_LOG"
    LOG_SOURCE="/var/log/auth.log (System Log)"
elif [[ -r "/var/log/secure" ]]; then
    cp "/var/log/secure" "$TEMP_LOG"
    LOG_SOURCE="/var/log/secure (System Log)"
elif command -v journalctl &>/dev/null; then
    if journalctl -u ssh -u sshd --no-pager -o cat > "$TEMP_LOG" 2>/dev/null; then
        LOG_SOURCE="systemd journal (ssh/sshd)"
    else
        echo -e "${RED}[ERROR] journalctl present but cannot read ssh logs (check permissions).${RESET}" >&2
        exit 2
    fi
else
    echo -e "${RED}[ERROR] No readable authentication logs found on system.${RESET}" >&2
    echo "Provide a target log path: ./${SCRIPT_NAME} <path_to_auth.log>" >&2
    exit 2
fi

# ------------------------------------------------------------------------------
# 3. HEADER & AUDIT INITIATION
# ------------------------------------------------------------------------------
echo -e "${CYAN}====================================================${RESET}"
echo -e "${BOLD}${CYAN}         SSH SECURITY LOG AUDITOR v1.0              ${RESET}"
echo -e "${CYAN}====================================================${RESET}"
echo -e "Log Source : ${GREEN}${LOG_SOURCE}${RESET}"
echo -e "Analyzed At: $(date '+%Y-%m-%d %H:%M:%S')"
echo -e "${CYAN}----------------------------------------------------${RESET}"

# ------------------------------------------------------------------------------
# 4. FAILED AUTHENTICATION DETECTION
# ------------------------------------------------------------------------------
echo
echo -e "${BOLD}${BLUE}========== FAILED AUTHENTICATION EVENTS ============${RESET}"

# Display matching lines with line numbers
grep -nE "Failed password|authentication failure" "$TEMP_LOG" || true

FAILED_COUNT=$(grep -cE "Failed password|authentication failure" "$TEMP_LOG" || true)

echo -e "----------------------------------------------------"
echo -e "Total Failed Authentication Events: ${BOLD}${RED}${FAILED_COUNT}${RESET}"

# ------------------------------------------------------------------------------
# 5. INVALID USER DETECTION
# ------------------------------------------------------------------------------
echo
echo -e "${BOLD}${BLUE}============== INVALID USER EVENTS =================${RESET}"

grep -nE "Invalid user" "$TEMP_LOG" || true

INVALID_COUNT=$(grep -cE "Invalid user" "$TEMP_LOG" || true)

echo -e "----------------------------------------------------"
echo -e "Total Invalid User Account Events : ${BOLD}${YELLOW}${INVALID_COUNT}${RESET}"

# ------------------------------------------------------------------------------
# 6. SOURCE IP EXTRACTION & FREQUENCY DISTRIBUTION
# ------------------------------------------------------------------------------
echo
echo -e "${BOLD}${BLUE}=========== ATTACKING SOURCE IP RANKING ============${RESET}"
printf "%-10s %-20s\n" "ATTEMPTS" "IP ADDRESS"
echo "----------------------------------------------------"

# Pipeline:
# 1. Filter lines with failed or invalid user events
# 2. Extract only IPv4 address strings using -oE
# 3. Sort identical IP addresses together
# 4. Count repetitions via uniq -c
# 5. Sort numerically in descending order
grep -E "Failed password|Invalid user|authentication failure" "$TEMP_LOG" | \
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | \
sort | \
uniq -c | \
sort -nr || true

# Count distinct unique attacking IPs
UNIQUE_IPS=$(grep -E "Failed password|Invalid user|authentication failure" "$TEMP_LOG" | \
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' | sort -u | wc -l | tr -d ' ')

# ------------------------------------------------------------------------------
# 7. SUCCESSFUL AUTHENTICATIONS (BASELINE COMPARISON)
# ------------------------------------------------------------------------------
echo
echo -e "${BOLD}${BLUE}========== SUCCESSFUL AUTHENTICATIONS ==============${RESET}"

grep -nE "Accepted password|Accepted publickey" "$TEMP_LOG" || true

ACCEPTED_COUNT=$(grep -cE "Accepted password|Accepted publickey" "$TEMP_LOG" || true)

echo -e "----------------------------------------------------"
echo -e "Total Authorized Logins           : ${BOLD}${GREEN}${ACCEPTED_COUNT}${RESET}"

# ------------------------------------------------------------------------------
# 8. FINAL SECURITY AUDIT SUMMARY & THRESHOLD EVALUATION
# ------------------------------------------------------------------------------
echo
echo -e "${CYAN}====================================================${RESET}"
echo -e "${BOLD}${CYAN}               SECURITY AUDIT SUMMARY               ${RESET}"
echo -e "${CYAN}====================================================${RESET}"
printf "%-32s : %d\n" "Total Failed Auth Events" "$FAILED_COUNT"
printf "%-32s : %d\n" "Total Invalid User Attempts" "$INVALID_COUNT"
printf "%-32s : %d\n" "Distinct Suspicious Source IPs" "$UNIQUE_IPS"
printf "%-32s : %d\n" "Total Authorized Logins" "$ACCEPTED_COUNT"
echo -e "${CYAN}----------------------------------------------------${RESET}"

# Alert threshold: >= 5 failed attempts warrants security alert
if (( FAILED_COUNT >= 5 )); then
    echo -e "${RED}${BOLD}[ALERT] HIGH THREAT DETECTED: ${FAILED_COUNT} failed attempts exceed threshold (>= 5).${RESET}"
    echo -e "${YELLOW}Recommendation: Review top offending IPs and update firewall / fail2ban rules.${RESET}"
    echo -e "${CYAN}====================================================${RESET}"
    exit 1
else
    echo -e "${GREEN}${BOLD}[STATUS] NORMAL: Failed authentication count is within acceptable threshold (< 5).${RESET}"
    echo -e "${CYAN}====================================================${RESET}"
    exit 0
fi
```

# 10. Technical Interview Scenarios & Knowledge Checks

### Q1: What is the exact difference between BRE (`grep`) and ERE (`grep -E`)?
**Answer:**
- In Basic Regular Expressions (BRE), meta-characters like `+`, `?`, `|`, `(`, `)`, `{`, and `}` are treated as literal characters unless escaped with a backslash (`\+`, `\?`, `\|`, `\{1,3\}`).
- In Extended Regular Expressions (ERE), these characters are native operators representing alternation, repetition, and grouping. No backslashes are needed, resulting in cleaner, less error-prone regex patterns.

### Q2: What are the three possible exit statuses returned by `grep`?
**Answer:**
- `0`: Match found — at least one line matched the pattern.
- `1`: No match found — zero lines matched the pattern.
- `2`: Error — syntax error in the regex, missing input file, or permission denied.

### Q3: Why is `grep -q` preferred inside `if` statements over `grep | wc -l`?
**Answer:**
`if grep -q "pattern" file; then` evaluates the exit code of `grep` directly. Furthermore, `grep -q` activates **early exit**: it terminates immediately upon reading the first matching line, avoiding reading the rest of a gigabyte-sized log file. In contrast, `grep | wc -l` forces reading the entire file, spawns a pipeline subshell, and invokes a second process (`wc`).

### Q4: Explain the difference between `grep -o` and default `grep`.
**Answer:**
- Default `grep` outputs the entire line that contains the match.
- `grep -o` (only matching) extracts and outputs **only the exact matching character substring**, placing each match on a new line. It is essential for token extraction (e.g. extracting IP addresses or email addresses from unstructured log lines).

### Q5: How do `^` and `$` behave when searching files with CRLF (Windows) line endings?
**Answer:**
Windows files use CRLF (`\r\n`). If a pattern uses `$`, the regex engine matches the end of the line before `\n`. The trailing carriage return `\r` becomes part of the line buffer, causing regexes like `grep 'pattern$' file.txt` to fail unless `\r` is explicitly stripped or matched (`grep -E 'pattern\r?$'`).
