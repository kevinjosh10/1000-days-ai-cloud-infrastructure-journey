# 2. Architectural Foundation of Linux Streams & File Descriptors

Under the UNIX "Everything is a File" philosophy, all I/O operations (keyboard input, terminal output, network sockets, physical disks, pipes) are exposed to the kernel as streams of bytes accessed via integer handles called **File Descriptors (FDs)**.

When any Linux process launches, the kernel automatically binds three standard streams to it:

```text
                     Standard Process File Descriptor Table
                     
  File Descriptor   Name      Standard Source / Destination     Default Stream Binding
  ────────────────────────────────────────────────────────────────────────────────────
        0           stdin     Keyboard / Pipe / Redirected File   [ Input Stream ]
        1           stdout    Terminal Screen / Display Buffer    [ Output Stream ]
        2           stderr    Terminal Screen / Diagnostic Buffer [ Error / Log Stream ]
```

```text
                          Dual-Channel Stream Separation
                          
                               ┌───────────────────┐
                               │   deploy_app.sh   │
                               └─────────┬─────────┘
                                         │
                    ┌────────────────────┴────────────────────┐
                    │                                         │
                    ▼ (FD 1: stdout)                          ▼ (FD 2: stderr)
          Structured Payloads                       Operational Diagnostics
          JSON / CSV / Configs                      [INFO], [WARN], [ERROR]
                    │                                         │
                    ▼                                         ▼
            > deployment.json                         2> deployment.log
```

### Essential Stream Redirection Operators

| Operator | Syntax | Description |
|---|---|---|
| Redirect stdout | `cmd > file` | Overwrites `file` with standard output (FD 1) |
| Append stdout | `cmd >> file` | Appends standard output (FD 1) to `file` |
| Redirect stderr | `cmd 2> file` | Overwrites `file` with standard error (FD 2) |
| Append stderr | `cmd 2>> file` | Appends standard error (FD 2) to `file` |
| Combine Streams | `cmd &> file` / `cmd > file 2>&1` | Merges stdout and stderr into a single destination |
| Redirect stdin | `cmd < file` | Feeds contents of `file` into standard input (FD 0) |
| Duplicate stream | `exec 3>&1` | Clones stdout's current destination onto custom FD 3 |

### The Production Golden Rule of Stream Separation
Never output human-readable progress logs (`"Processing server 1 of 50..."`) to stdout (`FD 1`) if the script generates a data payload meant to be parsed by downstream tools (e.g. `jq`, `curl`, or an Ansible inventory parser).
- **Rule:** Send data payloads to `stdout` (`echo "$json"`); send all status updates, timings, and error alerts to `stderr` (`echo "[INFO] Starting..." >&2`).

# 3. Deep Dive into the `read` Builtin & Options

The Bash `read` command is a shell builtin that reads a single line of text from standard input (or a specified file descriptor) and splits it into fields.

### The Role of `$IFS` (Internal Field Separator)
By default, Bash sets `$IFS` to space, tab, and newline (`$' \t\n'`). When `read` ingests a line, it automatically:
1. Strips all leading and trailing whitespace characters.
2. Splits the remaining string on any `$IFS` character and assigns the tokens to the provided variable names.

```bash
# Problem: Default read strips leading and trailing whitespace
read line <<< "   production-cluster-01   "
echo "[$line]"  # Outputs: "[production-cluster-01]" (Whitespace stripped!)
```

To preserve every byte of whitespace verbatim:
```bash
# Solution: Temporarily clear IFS for the read invocation
IFS= read line <<< "   production-cluster-01   "
echo "[$line]"  # Outputs: "[   production-cluster-01   ]" (Intact!)
```

### The Role of `-r` (Raw Mode)
By default, `read` treats backslashes (`\`) as escape characters. If a line contains `C:\Users\ADMIN` or an escaped delimiter, `read` strips the backslashes!
- The `-r` flag forces **Raw Mode**, preventing backslash escape interpretation.

```bash
# Problem: Unescaped read corrupts backslashes
read path <<< "server\production\node1"
echo "$path"  # Outputs: "serverproductionnode1"

# Solution: Raw mode preserves literal backslashes
read -r path <<< "server\production\node1"
echo "$path"  # Outputs: "server\production\node1"
```

### The Definitive Professional Standard
Whenever reading data in shell scripts, always use:
```bash
IFS= read -r variable_name
```

# 4. Reading Files Line-by-Line & The Unterminated Final Line

The standard pattern for reading a file line-by-line in Bash is:

```bash
while IFS= read -r line; do
    echo "Processing line: $line"
done < input_file.txt
```

### The Unterminated Final Line Edge Case
According to the POSIX standard, a line is defined as a sequence of characters terminated by a **newline character (`\n`)**.
If a file is created without a final newline (common when generated on Windows, exported from text editors, or truncated during network transfers), `read` encounters End-Of-File (EOF) before reading `\n`.
- When `read` hits EOF, it assigns the remaining characters to the variable, but **returns an exit code of 1 (Failure)**!
- Because `read` returned 1, the `while` loop terminates immediately, **silently discarding the last line**!

```text
                     The Unterminated Final Line Drop
                     
  File contents:
  Line 1: "web-server-01\n"   ──► read succeeds (exit 0) ──► Loop processes Line 1
  Line 2: "db-server-01\n"    ──► read succeeds (exit 0) ──► Loop processes Line 2
  Line 3: "backup-01" [EOF]   ──► read hits EOF (exit 1) ──► LOOP TERMINATES!
                                                             (Line 3 is dropped!)
```

### The Complete Fail-Safe Reading Idiom

```bash
while IFS= read -r line || [[ -n "$line" ]]; do
    echo "Guaranteed processing: $line"
done < input_file.txt
```

**Why this works:**
1. If `read` reads a normal terminated line, it returns `0`. The `||` short-circuits, and the loop body executes.
2. If `read` reads the final line lacking `\n`, it returns `1`. The `||` evaluates `[[ -n "$line" ]]`.
3. Because the final line was loaded into `$line`, `[[ -n "$line" ]]` returns `0` (True)!
4. The loop body executes one final time for the last line.
5. On the subsequent iteration, `read` encounters EOF with zero bytes, `$line` is empty, both conditions fail, and the loop terminates gracefully.

# 5. The Pipeline Subshell Trap & Scope Erasure

One of the most notorious bugs in Bash scripting occurs when developers pipe a file into a `while` loop:

```bash
#!/usr/bin/env bash
# THE PIPELINE SUBSHELL TRAP (ANTI-PATTERN)

counter=0

cat servers.txt | while IFS= read -r server; do
    ((counter += 1))
    echo "Found server: $server"
done

echo "Total servers counted: $counter"
```

```text
Actual Output:
Total servers counted: 0
```

### Architectural Root Cause
In POSIX compliance, **each command in a pipeline runs in a separate subshell (`fork(2)`)**:
1. The parent shell initializes `counter=0`.
2. The pipeline spawns a child process for `cat` and a child subshell for the `while` loop.
3. The child subshell increments its own localized copy of `counter` (`1, 2, 3, 4`).
4. When the loop finishes, the child subshell process terminates, destroying its memory space.
5. Control returns to the parent shell, where `counter` remains untouched at `0`!

```text
                    Visualizing Subshell Scope Erasure
                    
  [ PARENT SHELL ]
  counter = 0
         │
         ▼ (pipe spawns subshell)
  ┌───────────────────────────────────────────────┐
  │ [ CHILD SUBSHELL ]                            │
  │ counter = 0                                   │
  │ counter = 1 -> counter = 2 -> counter = 4     │
  │ (Child subshell process terminates)           │
  └───────────────────────┬───────────────────────┘
                          │
  [ PARENT SHELL RESUMES ]
  echo "Total: $counter"  ──► 0 ! (Parent memory was never modified)
```

### Solution 1: Direct File Redirection (Runs in Current Shell)

```bash
counter=0
while IFS= read -r server || [[ -n "$server" ]]; do
    ((counter += 1))
done < servers.txt

echo "Total servers counted: $counter" # Correctly outputs: 4
```

### Solution 2: The `lastpipe` Option
In Bash 4.2+, the `lastpipe` option forces the last command of a pipeline to execute in the current shell rather than a subshell. (Note: Job control must be disabled via `set +m` for `lastpipe` to work in interactive shells):

```bash
shopt -s lastpipe
set +m

counter=0
cat servers.txt | while IFS= read -r server; do
    ((counter += 1))
done
echo "Total: $counter" # Outputs: 4
```

# 6. Process Substitution (`< <(command)`)

What if the stream to be processed is generated dynamically by a command (like `grep`, `awk`, `find`, or `aws ec2 describe-instances`) rather than a static file on disk?

If we pipe it (`command | while read`), we hit the subshell trap.
If we write it to a temporary file, we incur disk I/O, risk race conditions, and leave orphan temp files.

### The Solution: Process Substitution

```bash
while IFS= read -r line || [[ -n "$line" ]]; do
    echo "Processing: $line"
    ((counter += 1))
done < <(command_generating_stream)
```

```text
                        Process Substitution Anatomy
                        
             while IFS= read -r line; do ... done < <(command)
                                                  │ │
      Input Redirection Operator (Standard <) ────┘ │
                                                    │
      Process Substitution Construct ───────────────┘
      (Kernel exposes command output as anonymous pipe: /dev/fd/63)
```

- `<(command)` runs `command` asynchronously and connects its standard output to an anonymous named pipe (FIFO) or a `/dev/fd/` virtual file descriptor.
- The outer `<` redirects that descriptor into the `while` loop's standard input.
- **Result:** The `while` loop executes inside the **current shell environment**, preserving all variables, counters, and array mutations!

```bash
#!/usr/bin/env bash
set -euo pipefail

total_running_instances=0

# Stream active production servers directly into the current shell
while IFS= read -r instance_id || [[ -n "$instance_id" ]]; do
    echo "Auditing running instance: $instance_id"
    ((total_running_instances += 1))
done < <(printf '%s\n' "i-01234abc" "i-05678def" "i-09999xyz")

echo "Total running instances audited: $total_running_instances" # Outputs: 3
```

# 7. Custom File Descriptors (Beyond 0, 1, 2)

Linux processes can open and manage additional file descriptors from `3` up to the system limit (`ulimit -n`).

Using custom file descriptors allows scripts to:
- Open files once and read from them incrementally across multiple functions.
- Read from multiple distinct files simultaneously without nesting.
- Save and restore stdout/stderr for clean telemetry logging.

### The File Descriptor Control Matrix (`exec`)

| Command | Action Performed on File Descriptor Table |
|---|---|
| `exec 3>&1` | Duplicates stdout (`1`) onto new descriptor `3` (Saves terminal/stdout) |
| `exec 1> output.log` | Redirects stdout (`1`) permanently to `output.log` |
| `exec 1>&3` | Restores stdout (`1`) back to original destination saved in `3` |
| `exec 3>&-` | Closes output file descriptor `3` |
| `exec 4< input.csv` | Opens `input.csv` for read-only access on descriptor `4` |
| `exec 4<&-` | Closes input file descriptor `4` |
| `exec 5>> audit.log` | Opens `audit.log` for append-only access on descriptor `5` |

### Stream Duplication and Restoration Walkthrough

```bash
#!/usr/bin/env bash

# 1. Clone stdout (FD 1) to FD 3
exec 3>&1

# 2. Redirect stdout (FD 1) to a logfile
exec 1> /tmp/application.log

echo "This message is written directly into /tmp/application.log"

# 3. Write directly to the terminal screen using saved FD 3
echo "This message bypasses the logfile and goes directly to stdout!" >&3

# 4. Restore original stdout
exec 1>&3

echo "This message is now back on standard terminal stdout"

# 5. Clean up by closing FD 3
exec 3>&-
```

### Full Source Code: `linux-mastery/scripts/11_csv_database_reader.sh`

```bash
#!/usr/bin/env bash

# ==============================================================================
# PROJECT  : 11_csv_database_reader.sh
# TRACK    : Mastering Shell Scripting & Automation — Day 11/30 (Week 10)
# JOURNEY  : Day 267 / 1000
# PURPOSE  : Stream Processing with read, Custom File Descriptors & Schema Validation
# USAGE    : ./11_csv_database_reader.sh [csv_file]
# ==============================================================================

# Defensive strict mode
set -uo pipefail

# ------------------------------------------------------------------------------
# 1. COLOR & FORMATTING CONSTANTS
# ------------------------------------------------------------------------------
RED='\033[0;31m'
GREEN='\033[0;32m'
YELLOW='\033[1;33m'
BLUE='\033[0;34m'
CYAN='\033[0;36m'
BOLD='\033[1m'
RESET='\033[0m'

# ------------------------------------------------------------------------------
# 2. CONFIGURATION & SCRIPT DIRECTORY RESOLUTION
# ------------------------------------------------------------------------------
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
SCRIPT_NAME="${0##*/}"

show_help() {
    cat <<EOF
Usage: ${SCRIPT_NAME} [CSV_FILE]

Stream Processing CSV Database Engine with Custom File Descriptors.

Arguments:
  CSV_FILE               Path to CSV database (default: servers.csv in script directory)

Options:
  --help, -h             Display this documentation and exit

Separating Structured Data from Diagnostics:
  ./${SCRIPT_NAME} > structured_payload.txt 2> operational.log

Exit Codes:
  0 : Processing completed successfully (regardless of individual record validation)
  1 : Missing/unreadable CSV file, empty file, or schema mismatch
EOF
}

if [[ $# -ge 1 && ( "$1" == "--help" || "$1" == "-h" ) ]]; then
    show_help
    exit 0
fi

# Locate default CSV in current directory or script directory
DEFAULT_CSV="servers.csv"
if [[ ! -f "$DEFAULT_CSV" && -f "${SCRIPT_DIR}/servers.csv" ]]; then
    DEFAULT_CSV="${SCRIPT_DIR}/servers.csv"
fi

CSV_FILE="${1:-$DEFAULT_CSV}"

# Counters
TOTAL=0
VALID=0
INVALID=0

# ------------------------------------------------------------------------------
# 3. STREAM & FILE DESCRIPTOR SETUP
# ------------------------------------------------------------------------------
# Duplicate stdout (FD 1) onto custom File Descriptor 3 for structured payload delivery
exec 3>&1

# Operational diagnostic loggers route strictly to stderr (FD 2)
log() {
    printf "${CYAN}[INFO]${RESET} %s\n" "$*" >&2
}

warn() {
    printf "${YELLOW}[WARN]${RESET} %s\n" "$*" >&2
}

error() {
    printf "${RED}[ERROR]${RESET} %s\n" "$*" >&2
}

# ------------------------------------------------------------------------------
# 4. DATA SANITIZATION & SCHEMA VALIDATION HELPERS
# ------------------------------------------------------------------------------
# Pure Bash whitespace trimming (eliminates leading & trailing whitespace without subprocess fork)
trim() {
    local value="$1"
    value="${value#"${value%%[![:space:]]*}"}"
    value="${value%"${value##*[![:space:]]}"}"
    printf '%s' "$value"
}

# Validate record schema and enum field constraints
validate_record() {
    local server="$1"
    local region="$2"
    local instance="$3"
    local environment="$4"
    local status="$5"

    # Mandatory field presence checks
    [[ -n "$server" ]] || return 1
    [[ -n "$region" ]] || return 1
    [[ -n "$instance" ]] || return 1

    # Environment enum validation
    case "$environment" in
        production|staging|development) ;;
        *) return 1 ;;
    esac

    # Status enum validation
    case "$status" in
        active|inactive) ;;
        *) return 1 ;;
    esac

    return 0
}

# ------------------------------------------------------------------------------
# 5. CSV FILE VERIFICATION & DESCRIPTOR BINDING
# ------------------------------------------------------------------------------
if [[ ! -f "$CSV_FILE" || ! -r "$CSV_FILE" ]]; then
    error "CSV database missing or unreadable at: ${CSV_FILE}"
    exec 3>&- # Close custom FD 3 before exiting
    exit 1
fi

# Open CSV file for read operations specifically on custom File Descriptor 4
exec 4< "$CSV_FILE"

# Ingest header line from FD 4
if ! IFS= read -r -u 4 header; then
    error "CSV file is completely empty."
    exec 4<&-
    exec 3>&-
    exit 1
fi

# Normalize and validate header against expected schema
header=$(trim "$header")
expected_header="server_name,region,instance_type,environment,status"

if [[ "$header" != "$expected_header" ]]; then
    error "Invalid CSV schema."
    error "Expected: ${expected_header}"
    error "Received: ${header}"
    exec 4<&-
    exec 3>&-
    exit 1
fi

log "CSV processing initiated for target: ${CSV_FILE}"

# ------------------------------------------------------------------------------
# 6. STREAM PROCESSING RECORD LOOP (Custom FD 4)
# ------------------------------------------------------------------------------
while IFS=, read -r -u 4 \
    server_name region instance_type environment status extra || \
    [[ -n "${server_name:-}${region:-}${instance_type:-}${environment:-}${status:-}${extra:-}" ]]
do
    # Skip empty lines
    if [[ -z "${server_name:-}${region:-}${instance_type:-}${environment:-}${status:-}${extra:-}" ]]; then
        continue
    fi

    TOTAL=$((TOTAL + 1))

    # Sanitize whitespace on every column
    server_name=$(trim "${server_name:-}")
    region=$(trim "${region:-}")
    instance_type=$(trim "${instance_type:-}")
    environment=$(trim "${environment:-}")
    status=$(trim "${status:-}")
    extra=$(trim "${extra:-}")

    # Reject records with unexpected extraneous columns
    if [[ -n "$extra" ]]; then
        INVALID=$((INVALID + 1))
        warn "Record ${TOTAL}: Extraneous column detected. Discarding corrupted line."
        continue
    fi

    # Execute schema validation rules
    if ! validate_record \
        "$server_name" \
        "$region" \
        "$instance_type" \
        "$environment" \
        "$status"; then
        INVALID=$((INVALID + 1))
        warn "Record ${TOTAL}: Validation failed for entity '${server_name:-[UNNAMED]}'. Missing fields or illegal enum."
        continue
    fi

    VALID=$((VALID + 1))

    # Stream structured configuration payload directly to FD 3 (Saved stdout)
    printf '%s\n' "----------------------------------------" >&3
    printf 'SERVER_NAME=%s\n' "$server_name" >&3
    printf 'REGION=%s\n' "$region" >&3
    printf 'INSTANCE_TYPE=%s\n' "$instance_type" >&3
    printf 'ENVIRONMENT=%s\n' "$environment" >&3
    printf 'STATUS=%s\n' "$status" >&3

    log "Successfully validated and emitted payload: ${server_name} (${environment})"
done

# ------------------------------------------------------------------------------
# 7. DESCRIPTOR CLEANUP & SUMMARY REPORTING
# ------------------------------------------------------------------------------
# Close input descriptor FD 4
exec 4<&-

# Output operational summary to stderr (FD 2)
log "========================================"
log "        CSV PROCESSING SUMMARY          "
log "========================================"
log "Total Records Ingested : ${TOTAL}"
log "Valid Records Emitted  : ${VALID}"
log "Invalid Records Skipped: ${INVALID}"
log "========================================"

# Close saved stdout descriptor FD 3
exec 3>&-

exit 0
```

# 10. Technical Knowledge Check (All 8 Questions Answered)

### Q1: What is the exact fundamental difference between stdin (0), stdout (1), and stderr (2)?
**Answer:**
- `stdin (0)` is the default input channel from which a process consumes character streams.
- `stdout (1)` is the primary output stream intended strictly for valid program output, computed results, and data payloads.
- `stderr (2)` is the secondary, unbuffered output stream dedicated to diagnostic logging, warnings, debugging telemetry, and fatal error reporting.

### Q2: Why is `IFS= read -r` the universal enterprise standard for reading streams?
**Answer:**
- Setting `IFS=` (empty string) disables word splitting and field trimming, preserving all leading and trailing whitespace exactly as formatted in the source stream.
- The `-r` flag activates raw mode, preventing backslashes (`\`) from being interpreted as escape characters and preserving literal path strings or escape codes.

### Q3: Why does a counter inside a pipeline `while` loop (`cat file | while read; do ((cnt++)); done`) remain zero after the loop finishes?
**Answer:** Under POSIX shell architecture, commands linked by pipes (`|`) are executed in separate, forked subshell child processes (`( ... )`). The variable `$cnt` is incremented inside the memory space of the child subshell. When the input stream closes, the child process terminates and its memory is destroyed. The parent process's variable was never modified and remains `0`.

### Q4: What is the purpose of `|| [[ -n "$line" ]]` in a `while read` construct?
**Answer:** If the final line of a file does not terminate with a newline character (`\n`), `read` loads the final line's contents into `$line` but returns exit status `1` (Failure) upon encountering EOF. Without `|| [[ -n "$line" ]]`, the loop would abort and discard that last line. The OR condition checks if `$line` contains non-empty data, allowing the loop body to execute one final time for the unterminated line.

### Q5: What does `< <(command)` mean syntactically?
**Answer:** It is the combination of standard input redirection (`<`) and process substitution (`<(command)`). The subshell command runs asynchronously and its stdout is attached to an anonymous named pipe or `/dev/fd/N` file descriptor. The outer `<` redirects that descriptor into the command (such as a `while` loop), enabling the loop to run in the current shell context without forking a pipeline subshell.

### Q6: What does `exec 3>&1` accomplish?
**Answer:** It creates custom File Descriptor `3` as a duplicate of standard output (`FD 1`). This saves the current destination of `stdout` (e.g. the terminal console) into FD 3 so that `FD 1` can be redirected to a log file or suppressed, and later restored back using `exec 1>&3`.

### Q7: How do you close File Descriptor 3?
**Answer:**
- For an output descriptor: `exec 3>&-`
- For an input descriptor: `exec 3<&-`

### Q8: What is the difference between `exec 3<&-` and `exec 3>&-`?
**Answer:** Syntactically, `3<&-` closes File Descriptor 3 opened for **reading/input**, while `3>&-` closes File Descriptor 3 opened for **writing/output**. In modern Bash, both commands achieve file descriptor closure, but distinguishing them explicitly documents the stream's directional intent in production code.
