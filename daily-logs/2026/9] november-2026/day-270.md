# 3. Architecture of Process Lifecycle Management

Managing background daemon processes directly through Bash requires mastering Linux process signals, state preservation, and asynchronous execution.

```text
                       Daemon Process Lifecycle Pipeline
                       
    [ Start Command ]
           │
           ▼
    Check PID File ──► Is PID alive? (kill -0) ──► YES: Error "Already Running"
           │                                          └── NO : Remove stale PID file
           ▼
    Launch daemon: nohup python3 -m http.server $PORT > log 2>&1 &
           │
           ▼
    Capture background PID: SERVICE_PID=$!
    Save PID to state directory: echo "$SERVICE_PID" > "$PID_FILE"
           │
           ▼
    Sleep 1s & Verify viability: kill -0 "$SERVICE_PID"
           ├── SUCCESS: Report running state with PID
           └── FAILURE: Read tail of log file, remove PID file, exit 1
```

### Essential Process Management Primitives

| Command / Variable | Architectural Purpose |
|---|---|
| `nohup <cmd> &` | Runs process in background; shields it from `SIGHUP` when parent terminal closes |
| `$!` | Special parameter holding the PID of the most recently backgrounded process |
| `kill -0 PID` | Sends null signal; checks process existence and permissions without affecting it |
| `kill -15 PID` / `kill -TERM` | Sends `SIGTERM`; requests graceful shutdown allowing process to flush buffers |
| `kill -9 PID` / `kill -KILL` | Sends `SIGKILL`; kernel immediately destroys process (cannot be caught or ignored) |
| `PID_FILE` | Persistent file storing daemon PID across independent CLI invocations |

# 4. The 3-Tier Verification Hierarchy

A fundamental tenet of site reliability engineering is that **process existence does not equal service availability**. A process can be locked in a CPU spin, deadlocked on a mutex, or failing socket initialization while still appearing in `ps`.

```text
                        3-Tier Verification Model
                        
  Tier 1: Process Verification (OS Level)
  └── Command: kill -0 "$PID"
  └── Answers: Is the process scheduled in the kernel process table?
  
  Tier 2: Port & Socket Verification (Transport Level)
  └── Command: ss -ltnp | grep ":$PORT"
  └── Answers: Has the daemon successfully bound its listening socket?
  
  Tier 3: Application Health Verification (Application Layer)
  └── Command: curl -fsS --max-time "$TIMEOUT" "http://127.0.0.1:$PORT/"
  └── Answers: Is the application accepting requests and returning HTTP 200 OK?
```

`14_service_ctl.sh` enforces this hierarchy:
- `status` checks **Tier 1** (Process state) and handles stale PID files.
- `health` validates **Tier 1 AND Tier 3** (Process liveness and HTTP response readiness).

### Full Source Code: `14_service_ctl.sh`

```bash
#!/usr/bin/env bash

# ==============================================================================
# PROJECT  : 14_service_ctl.sh
# TRACK    : Mastering Shell Scripting & Automation — Day 14/30 (Week 10 Capstone)
# JOURNEY  : Day 270 / 1000
# PURPOSE  : Enterprise Microservice Process Lifecycle Controller & Health Auditor
# USAGE    : ./14_service_ctl.sh <COMMAND> [OPTIONS]
# ==============================================================================

# Defensive strict mode
set -uo pipefail

# ------------------------------------------------------------------------------
# 1. COLOR & FORMATTING CONSTANTS
# ------------------------------------------------------------------------------
RED='\033[0;31m'
GREEN='\033[0;32m'
YELLOW='\033[1;33m'
BLUE='\033[0;34m'
CYAN='\033[0;36m'
BOLD='\033[1m'
RESET='\033[0m'

# ------------------------------------------------------------------------------
# 2. DEFAULT STATE & CONFIGURATION
# ------------------------------------------------------------------------------
SCRIPT_NAME="${0##*/}"
SERVICE_NAME="auth-service"
ENVIRONMENT="dev"
PORT=8001
TIMEOUT=10
VERBOSE=false

# Resolve state storage directory
STATE_DIR="${XDG_STATE_HOME:-$HOME/.local/state}/service-ctl"

# Detect Python interpreter
if command -v python3 &>/dev/null; then
    PYTHON_BIN="python3"
elif command -v python &>/dev/null; then
    PYTHON_BIN="python"
else
    PYTHON_BIN=""
fi

# ------------------------------------------------------------------------------
# 3. LOGGING FUNCTIONS
# ------------------------------------------------------------------------------
log() {
    echo -e "${CYAN}[INFO]${RESET} $(date '+%Y-%m-%d %H:%M:%S') - $*"
}

debug() {
    if [[ "$VERBOSE" == true ]]; then
        echo -e "${BLUE}[DEBUG]${RESET} $(date '+%Y-%m-%d %H:%M:%S') - $*"
    fi
}

warn() {
    echo -e "${YELLOW}[WARN]${RESET} $(date '+%Y-%m-%d %H:%M:%S') - $*" >&2
}

error() {
    echo -e "${RED}[ERROR]${RESET} $(date '+%Y-%m-%d %H:%M:%S') - $*" >&2
}

# ------------------------------------------------------------------------------
# 4. HELP & USAGE DOCUMENTATION
# ------------------------------------------------------------------------------
usage() {
    echo -e "${BOLD}${CYAN}====================================================${RESET}"
    echo -e "${BOLD}${CYAN}       MICROSERVICE PROCESS CONTROLLER v1.0         ${RESET}"
    echo -e "${BOLD}${CYAN}====================================================${RESET}"
    echo
    echo -e "${BOLD}Usage:${RESET}"
    echo "  ${SCRIPT_NAME} <COMMAND> [OPTIONS]"
    echo
    echo -e "${BOLD}Primary Commands:${RESET}"
    echo "  start       Start the background service daemon"
    echo "  stop        Gracefully terminate the running service (SIGTERM)"
    echo "  restart     Stop and restart the service"
    echo "  status      Verify if the service process is currently active"
    echo "  health      Perform an HTTP endpoint health check (HTTP probe)"
    echo
    echo -e "${BOLD}Options:${RESET}"
    echo "  -e ENV      Deployment environment: dev | staging | prod (default: dev)"
    echo "  -p PORT     Network listening port: 1 - 65535 (default: 8001)"
    echo "  -t SECONDS  Graceful shutdown / probe timeout: >= 1 (default: 10)"
    echo "  -v          Enable verbose debug telemetry"
    echo "  -h, --help  Display this documentation and exit"
    echo
    echo -e "${BOLD}Examples:${RESET}"
    echo "  ${SCRIPT_NAME} start -e dev -p 8001 -v"
    echo "  ${SCRIPT_NAME} status -p 8001"
    echo "  ${SCRIPT_NAME} health -p 8001 -t 5"
    echo "  ${SCRIPT_NAME} restart -e staging -p 8001 -t 15"
    echo "  ${SCRIPT_NAME} stop -p 8001"
    echo
    echo -e "${BOLD}Exit Codes:${RESET}"
    echo "  0 : Success / Service operational / Command completed"
    echo "  1 : Operational failure / Unhealthy service / Process not running"
    echo "  2 : Invalid CLI arguments or syntax error"
    echo
    echo -e "${BOLD}${CYAN}====================================================${RESET}"
}

# ------------------------------------------------------------------------------
# 5. PRE-PARSING & COMMAND EXTRACTION
# ------------------------------------------------------------------------------
if [[ $# -eq 0 ]]; then
    error "Missing required command."
    usage >&2
    exit 2
fi

# Pre-scan for help
for arg in "$@"; do
    if [[ "$arg" == "-h" || "$arg" == "--help" ]]; then
        usage
        exit 0
    fi
done

COMMAND="$1"
shift

# Validate primary command
case "$COMMAND" in
    start|stop|restart|status|health)
        ;;
    *)
        error "Unknown command: '$COMMAND'"
        usage >&2
        exit 2
        ;;
esac

# ------------------------------------------------------------------------------
# 6. OPTION PARSING VIA GETOPTS
# ------------------------------------------------------------------------------
while getopts ":e:p:t:vh" opt; do
    case "$opt" in
        e)
            ENVIRONMENT="$OPTARG"
            ;;
        p)
            PORT="$OPTARG"
            ;;
        t)
            TIMEOUT="$OPTARG"
            ;;
        v)
            VERBOSE=true
            ;;
        h)
            usage
            exit 0
            ;;
        :)
            error "Option -${OPTARG} requires a valid argument."
            exit 2
            ;;
        \?)
            error "Unrecognized option: -${OPTARG}"
            exit 2
            ;;
    esac
done

shift $((OPTIND - 1))

# Reject any unexpected leftover positional parameters
if [[ $# -gt 0 ]]; then
    error "Unexpected trailing arguments: $*"
    usage >&2
    exit 2
fi

# ------------------------------------------------------------------------------
# 7. DEFENSIVE INPUT VALIDATION
# ------------------------------------------------------------------------------
# Normalize environment
ENVIRONMENT="${ENVIRONMENT,,}"
case "$ENVIRONMENT" in
    dev|staging|prod)
        ;;
    *)
        error "Invalid environment '$ENVIRONMENT'. Allowed values: dev | staging | prod"
        exit 2
        ;;
esac

# Validate port
if [[ ! "$PORT" =~ ^[0-9]+$ ]]; then
    error "Port must be an integer. Received: '$PORT'"
    exit 2
fi

if (( PORT < 1 || PORT > 65535 )); then
    error "Port '$PORT' is out of range (1 - 65535)."
    exit 2
fi

# Validate timeout
if [[ ! "$TIMEOUT" =~ ^[0-9]+$ ]] || (( TIMEOUT < 1 )); then
    error "Timeout must be a positive integer >= 1. Received: '$TIMEOUT'"
    exit 2
fi

# ------------------------------------------------------------------------------
# 8. STATE DIRECTORY & FILE TARGETS
# ------------------------------------------------------------------------------
mkdir -p "$STATE_DIR"
PID_FILE="$STATE_DIR/${SERVICE_NAME}-${ENVIRONMENT}-${PORT}.pid"
LOG_FILE="$STATE_DIR/${SERVICE_NAME}-${ENVIRONMENT}-${PORT}.log"

debug "Configuration established:"
debug "  Command      : $COMMAND"
debug "  Service      : $SERVICE_NAME"
debug "  Environment  : $ENVIRONMENT"
debug "  Port         : $PORT"
debug "  Timeout      : ${TIMEOUT}s"
debug "  State Dir    : $STATE_DIR"
debug "  PID File     : $PID_FILE"
debug "  Log File     : $LOG_FILE"

# ------------------------------------------------------------------------------
# 9. SERVICE LIFECYCLE MANAGEMENT FUNCTIONS
# ------------------------------------------------------------------------------

# Start the background microservice
start_service() {
    # Check if a PID file already exists
    if [[ -f "$PID_FILE" ]]; then
        local existing_pid
        existing_pid=$(<"$PID_FILE")

        if [[ "$existing_pid" =~ ^[0-9]+$ ]] && kill -0 "$existing_pid" 2>/dev/null; then
            error "Service is already running with PID ${existing_pid} on port ${PORT}."
            return 1
        fi

        warn "Removing stale PID file: $PID_FILE (Previous PID: ${existing_pid:-unknown})"
        rm -f "$PID_FILE"
    fi

    # Verify Python runtime availability
    if [[ -z "$PYTHON_BIN" ]]; then
        error "Python runtime (python3 or python) not found in PATH."
        return 1
    fi

    log "Starting ${SERVICE_NAME} on port ${PORT} (${ENVIRONMENT})..."
    debug "Executing command: nohup $PYTHON_BIN -m http.server $PORT --bind 127.0.0.1 > '$LOG_FILE' 2>&1 &"

    # Launch service in background, decoupled from terminal
    nohup "$PYTHON_BIN" -m http.server "$PORT" --bind 127.0.0.1 > "$LOG_FILE" 2>&1 &
    local service_pid=$!

    echo "$service_pid" > "$PID_FILE"
    debug "Saved PID $service_pid to $PID_FILE"

    # Allow 1 second for initialization and probe viability
    sleep 1

    if kill -0 "$service_pid" 2>/dev/null; then
        echo -e "${GREEN}${BOLD}[SUCCESS] ${SERVICE_NAME} started successfully with PID ${service_pid}.${RESET}"
        log "Listening on http://127.0.0.1:${PORT}/ (Log: ${LOG_FILE})"
        return 0
    else
        error "Service process terminated immediately after start."
        if [[ -s "$LOG_FILE" ]]; then
            error "Last log output:"
            tail -n 5 "$LOG_FILE" >&2
        fi
        rm -f "$PID_FILE"
        return 1
    fi
}

# Gracefully terminate the service process
stop_service() {
    if [[ ! -f "$PID_FILE" ]]; then
        warn "PID file not found at: ${PID_FILE}"
        echo -e "${YELLOW}[STOPPED] Service is not running.${RESET}"
        return 0
    fi

    local service_pid
    service_pid=$(<"$PID_FILE")

    if [[ ! "$service_pid" =~ ^[0-9]+$ ]]; then
        error "Invalid or corrupted PID file content: '${service_pid}'"
        rm -f "$PID_FILE"
        return 1
    fi

    # Check if process is actually running
    if ! kill -0 "$service_pid" 2>/dev/null; then
        warn "Stale PID file detected. Process ${service_pid} is no longer running."
        rm -f "$PID_FILE"
        echo -e "${YELLOW}[STOPPED] Service is not running.${RESET}"
        return 0
    fi

    log "Sending SIGTERM to process PID ${service_pid}..."
    kill -15 "$service_pid" 2>/dev/null || true

    # Poll for graceful shutdown up to TIMEOUT seconds
    local elapsed=0
    while (( elapsed < TIMEOUT )); do
        if ! kill -0 "$service_pid" 2>/dev/null; then
            rm -f "$PID_FILE"
            echo -e "${GREEN}${BOLD}[SUCCESS] Service PID ${service_pid} stopped gracefully after ${elapsed}s.${RESET}"
            return 0
        fi
        debug "Waiting for PID ${service_pid} to shut down (${elapsed}/${TIMEOUT}s)..."
        sleep 1
        ((elapsed += 1))
    done

    # Timeout reached: Escalate or report failure
    warn "Graceful shutdown timed out after ${TIMEOUT}s. Service still responsive."
    echo -e "${RED}[ERROR] Process ${service_pid} did not terminate within ${TIMEOUT} seconds.${RESET}" >&2
    return 1
}

# Restart the service (Graceful Stop followed by Start)
restart_service() {
    log "Initiating service restart sequence..."
    stop_service || {
        error "Failed to stop running service cleanly. Aborting restart."
        return 1
    }
    sleep 1
    start_service
}

# Report running state of the service
status_service() {
    if [[ ! -f "$PID_FILE" ]]; then
        echo -e "${YELLOW}[STOPPED] Service is not running (No PID file).${RESET}"
        return 1
    fi

    local service_pid
    service_pid=$(<"$PID_FILE")

    if [[ "$service_pid" =~ ^[0-9]+$ ]] && kill -0 "$service_pid" 2>/dev/null; then
        echo -e "${GREEN}${BOLD}[RUNNING]${RESET} ${SERVICE_NAME} active | PID: ${service_pid} | Port: ${PORT} | Env: ${ENVIRONMENT}"
        return 0
    else
        echo -e "${RED}[STOPPED] Stale PID file detected (${service_pid} not alive).${RESET}"
        rm -f "$PID_FILE"
        return 1
    fi
}

# Perform HTTP application health check probe
health_check() {
    # Check if process is running first
    if [[ ! -f "$PID_FILE" ]]; then
        echo -e "${RED}[UNHEALTHY] Process is not running (PID file missing).${RESET}" >&2
        return 1
    fi

    local service_pid
    service_pid=$(<"$PID_FILE")
    if ! kill -0 "$service_pid" 2>/dev/null; then
        echo -e "${RED}[UNHEALTHY] Process PID ${service_pid} is dead.${RESET}" >&2
        rm -f "$PID_FILE"
        return 1
    fi

    local endpoint="http://127.0.0.1:${PORT}/"
    log "Probing service health endpoint: ${endpoint} (Timeout: ${TIMEOUT}s)..."

    # Probe HTTP endpoint
    if curl -fsS --connect-timeout 2 --max-time "$TIMEOUT" "$endpoint" -o /dev/null 2>/dev/null; then
        echo -e "${GREEN}${BOLD}[HEALTHY] Service on port ${PORT} responded with HTTP 200 OK.${RESET}"
        return 0
    else
        echo -e "${RED}${BOLD}[UNHEALTHY] Service on port ${PORT} failed health check (Connection refused or timed out).${RESET}" >&2
        return 1
    fi
}

# ------------------------------------------------------------------------------
# 10. COMMAND DISPATCHER
# ------------------------------------------------------------------------------
case "$COMMAND" in
    start)
        start_service
        ;;
    stop)
        stop_service
        ;;
    restart)
        restart_service
        ;;
    status)
        status_service
        ;;
    health)
        health_check
        ;;
esac
```

# 8. Technical Knowledge Check (All 10 Questions Answered)

### Q1: What does `$!` return in Bash?
**Answer:** `$!` returns the Process ID (PID) of the most recently executed background command (i.e. the process launched with `&`). It is essential for storing daemon PIDs into state files immediately after launch.

### Q2: What is the exact purpose of `kill -0 PID`?
**Answer:** `kill -0 PID` sends the null signal (signal number 0) to the specified PID. It does not terminate or suspend the target process; instead, it performs kernel error checking to verify whether the target process is actively running and whether the calling user has permission to send signals to it.

### Q3: Why should production systems strictly prefer SIGTERM over SIGKILL?
**Answer:** `SIGTERM` (signal 15) is a polite termination request that can be trapped and handled by the process. It allows the application to finish in-flight HTTP requests, close database connections, flush memory buffers to disk, and remove lockfiles. In contrast, `SIGKILL` (signal 9) immediately aborts the process at the kernel level without cleanup, which can cause database corruption and orphaned network resources.

### Q4: What does the `-f` flag do in `curl -f`?
**Answer:** The `-f` (`--fail`) flag instructs `curl` to treat HTTP server error codes (4xx and 5xx) as operational failures, returning exit status 22 without outputting the server's HTML error body. This allows Bash conditionals (`if curl -f ...`) to correctly evaluate HTTP errors as failures.

### Q5: Why do we execute `shift` before invoking `getopts` in a subcommand script?
**Answer:** The script's first positional argument (`$1`) is the subcommand (e.g. `start`, `stop`). `getopts` only parses options prefixed with `-`. Calling `shift` removes the subcommand from the argument array (`"$@"`), shifting option flags (`-e`, `-p`) into position for `getopts` to process cleanly.

### Q6: What is the fundamental difference between Process Verification and Health Verification?
**Answer:** Process verification (`kill -0 PID`) confirms only that the operating system has an active process entry in the kernel table. Health verification (`curl -fsS http://...`) confirms that the process has initialized its network stack, bound its listening socket, and is actively processing application requests with healthy HTTP responses.

### Q7: Why is `$OPTARG` critical during `getopts` execution?
**Answer:** When an option requiring an argument is encountered (e.g. `-p 8001`), `getopts` stores the argument value in `$OPTARG`. In silent error mode (`":..."`), if a required argument is missing, `$OPTARG` captures the option character that caused the fault, enabling custom error logging.

### Q8: Why should service lifecycle operations be organized into modular functions?
**Answer:** Functions provide single-responsibility modularity, prevent global variable cross-contamination via `local`, allow clean return code error propagation (`return 1`), and enable reusable composite workflows (such as `restart_service` calling `stop_service` and `start_service`).

### Q9: What is the purpose of PID files, and what hazard do they present?
**Answer:** PID files record the process ID of a running background service so that external tools can identify and manage it across disconnected sessions. The primary hazard is **stale PID files**: if a service crashes or the host reboots, the file remains on disk with a defunct PID. If the OS reassigns that PID to an unrelated program, an unverified script could kill the wrong process.

### Q10: Why is graceful shutdown essential in cloud and distributed systems?
**Answer:** In autoscaling and rolling deployments, pods and instances are continuously created and destroyed. Graceful shutdown ensures that active customer requests finish processing, database transactions commit, distributed cluster leases (etcd/Consul) release cleanly, and downstream load balancers deregister targets without dropping user traffic.
