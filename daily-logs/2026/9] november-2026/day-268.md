# 2. Architectural Foundation of Bash Functions

In Bash, a function is a named compound command stored in the shell's memory. When invoked, it executes inside the **current shell execution environment** (unless explicitly wrapped in a subshell or pipeline).

```text
                     Bash Function Execution Context
                     
  Script-Level Environment                       Function Environment
  ┌────────────────────────────────────┐         ┌────────────────────────────────────┐
  │ $0 : ./deploy.sh                   │         │ $0 : ./deploy.sh (Preserved!)      │
  │ $1 : "us-east-1"                   │  CALL   │ $1 : "web-cluster-01" (Overridden!)│
  │ $2 : "production"                  │ ──────► │ $2 : "t3.medium"                   │
  │ $# : 2                             │         │ $# : 2                             │
  │ "$@" : ("us-east-1" "production")  │         │ "$@" : ("web-cluster-01" ...)      │
  └────────────────────────────────────┘         └────────────────────────────────────┘
```

### Syntax Standards: POSIX vs. Bash Extension

```bash
# Standard 1: POSIX Standard (Recommended for portability)
function_name() {
    # commands
}

# Standard 2: Bash/Korn Extension (Redundant keyword)
function function_name {
    # commands
}
```
**Enterprise Convention:** Use `function_name() { ... }` without the `function` keyword. It is universally portable across Bash, Dash, Zsh, and POSIX `sh`.

### Positional Parameters Inside Functions
When a function is called, the shell swaps the script's positional parameters (`$1`, `$2`, `$#`, `"$@"`) with the arguments passed to the function:
- `$0` remains the name of the script.
- `$1` through `$9` represent the function's arguments.
- `shift` inside a function shifts only the function's arguments, leaving the parent script's arguments untouched.

```bash
#!/usr/bin/env bash

inspect_args() {
    echo "Function argument count : $#"
    echo "Function first argument : $1"
    shift
    echo "After shift, first arg  : $1"
}

inspect_args "alpha" "beta" "gamma"
```

# 3. Local Variables & Dynamic Scoping

### The Global Variable Hazard
By default, **every variable declared in Bash is global**, even if declared inside a function!

```bash
#!/usr/bin/env bash
# ANTI-PATTERN: Accidental Global Pollution

target_env="production"

configure_stage() {
    target_env="staging" # Mutates the global variable!
}

configure_stage
echo "Target environment is: $target_env" # PRINTS: staging (FATAL BUG!)
```

### Namespace Isolation via `local`
The `local` keyword restricts the variable's scope strictly to the function and its child call stack:

```bash
#!/usr/bin/env bash

target_env="production"

configure_stage() {
    local target_env="staging" # Confined to function scope
    echo "Inside function: $target_env"
}

configure_stage
echo "Outside function: $target_env" # PRINTS: production (Safe!)
```

### The Mechanics of Bash Dynamic Scoping
Unlike languages like Python, Go, or C which use **Lexical (Static) Scoping**, Bash uses **Dynamic Scoping**:
- A variable declared `local` in an outer function is visible to any inner function called down the execution stack, unless the inner function explicitly shadows it with its own `local` declaration.

```text
                         Bash Dynamic Scoping Model
                         
  ┌────────────────────────────────────────────────────────┐
  │ outer_function()                                       │
  │   local auth_token="secret_xyz"                        │
  │   inner_function() ─────────────────────────────┐      │
  └─────────────────────────────────────────────────┼──────┘
                                                    │
                                                    ▼
  ┌────────────────────────────────────────────────────────┐
  │ inner_function()                                       │
  │   echo "Token: $auth_token"                            │
  │   (Accesses outer_function's local variable directly!) │
  └────────────────────────────────────────────────────────┘
```

```bash
#!/usr/bin/env bash

outer() {
    local cluster_region="ap-south-1"
    inner
}

inner() {
    # cluster_region is visible because inner was invoked during outer's lifecycle!
    echo "Inner function accessed caller scope: $cluster_region"
}

outer # Outputs: Inner function accessed caller scope: ap-south-1
```

> [!WARNING]
> While dynamic scoping can be leveraged for implicit context passing, relying on it heavily creates brittle code. Always pass dependencies explicitly as function parameters whenever possible.

# 4. Function Return Protocols (0–255)

A critical conceptual distinction in shell scripting is the difference between:
1. **Returning a Status Code:** Indicating success or failure (`return N`).
2. **Returning Data / Payloads:** Outputting values (strings, arrays, numbers) via stdout or name references.

### Exit Status Semantics (`return`)
The `return` statement immediately terminates the function and yields an exit status integer between `0` and `255`:
- `0`: **Success / True**
- `1`–`255`: **Failure / Error Code**

```bash
is_service_active() {
    local service="$1"
    systemctl is-active --quiet "$service" && return 0 || return 1
}

if is_service_active "nginx"; then
    echo "Nginx is running"
fi
```

### The Modulo-256 Truncation Trap
In the Linux kernel and POSIX specification, process and function exit statuses are stored as an 8-bit unsigned integer ($2^8 = 256$ possible values: $0$ to $255$).
- If you attempt to return a number $\ge 256$, Bash performs modulo-256 arithmetic:
$$\text{Exit Status} = \text{Value} \pmod{256}$$

```bash
calculate_status() {
    return 256 # 256 % 256 = 0
}

calculate_status
echo "Exit status: $?" # PRINTS: 0 (FALSE SUCCESS!)
```

```text
  Value Returned     Internal Arithmetic     Actual $? Status
  ───────────────────────────────────────────────────────────
      return 1             1 % 256                1  (Error)
      return 255         255 % 256              255 (Error)
      return 256         256 % 256                0  (SUCCESS! FATAL BUG)
      return 512         512 % 256                0  (SUCCESS! FATAL BUG)
```

**Golden Rule:** `return` is strictly for status signaling. Never use `return` to emit data or numerical values!

# 5. Data Emission Approach A: Command Substitution (`$()`)

To return strings, formatted text, calculated numbers, or JSON payloads from a function, write the payload to standard output and capture it in the caller using **Command Substitution**:

```bash
generate_node_id() {
    local region="$1"
    local timestamp
    timestamp=$(date +%s)
    printf '%s-worker-%s\n' "$region" "$timestamp"
}

# Caller captures stdout in variable
new_node=$(generate_node_id "us-east-1")
echo "Created node: $new_node"
```

### The Subshell Limitation of `$()`
Command substitution executes the enclosed command inside a **forked subshell (`( ... )`)**:
- Any modifications to variables, associative arrays, or shell flags made inside the function **vanish** when the subshell terminates!

```bash
active_nodes=10

scale_up() {
    active_nodes=$((active_nodes + 5))
    echo "$active_nodes"
}

# Invoked via command substitution subshell
scaled_count=$(scale_up)

echo "Returned payload : $scaled_count" # Prints: 15
echo "Caller variable  : $active_nodes" # Prints: 10 (NOT MUTATED!)
```

# 6. Data Emission Approach B: Name References (`declare -n` / `local -n`)

Introduced in **Bash 4.3**, Name References provide true **Pass-by-Reference** capabilities in shell scripting without spawning subshells.

### Syntax & Mechanics
Using `local -n ref=$1` creates an alias variable `ref` that points directly to the variable whose *name* was passed in `$1`. Modifying `ref` modifies the caller's variable in place!

```bash
#!/usr/bin/env bash

# Function modifies caller's variable directly
get_cluster_endpoint() {
    local cluster="$1"
    local -n target_var=$2 # target_var aliases the caller's variable

    if [[ "$cluster" == "prod" ]]; then
        target_var="k8s.production.internal:6443"
    else
        target_var="k8s.staging.internal:6443"
    fi
}

endpoint=""
get_cluster_endpoint "prod" endpoint
echo "Resolved Endpoint: $endpoint" # PRINTS: k8s.production.internal:6443
```

### Returning Multiple Values Atomically
Name references eliminate the need to serialize multiple return values into strings:

```bash
get_server_metrics() {
    local -n cpu_out=$1
    local -n ram_out=$2
    local -n disk_out=$3

    cpu_out=42
    ram_out=68
    disk_out=15
}

cpu=0; ram=0; disk=0
get_server_metrics cpu ram disk
echo "CPU: ${cpu}% | RAM: ${ram}% | Disk: ${disk}%"
```

### The Name Collision & Shadowing Trap
A critical hazard occurs if a library function declares a `local` variable whose name matches the caller's variable name passed to `local -n`:

```bash
# HAZARDOUS COLLISION:
calculate() {
    local -n result_ref=$1
    local total=100         # If caller passes variable named 'total'...
    result_ref=$total       # result_ref may alias the local 'total' instead!
}
```

> [!IMPORTANT]
> **Enterprise Library Convention:** When writing reusable library functions that use `local -n`, always prefix internal variables with a unique library namespace (e.g., `local _lib_var`, `local _cs_net_int`) to prevent collisions with user variables.

# 7. Comparison: Command Substitution vs. Name References

| Architectural Dimension | Approach A: Command Substitution (`$()`) | Approach B: Name References (`declare -n`) |
|---|---|---|
| **Bash Version Requirement** | Compatible with all POSIX shells & Bash 2+ | Requires **Bash 4.3+** |
| **Execution Context** | Spawns a forked child subshell (`fork(2)`) | Executes in current shell (Zero fork overhead) |
| **Performance in Loops** | Slower (hundreds of process forks) | Blazing fast (in-memory variable aliasing) |
| **Return Multiple Values** | Requires delimiter parsing (`IFS` / arrays) | Native: pass multiple variable references |
| **Scope Side-Effects** | Completely isolated (cannot mutate caller) | Direct mutation of caller variables |
| **Primary Use Cases** | String processing, pipelines, filters | High-performance math, multi-value returns |

1. `validate_ip`: Strict IPv4 format and boundary checking ($0$–$255$) with base-10 arithmetic (`10#$octet`) to prevent leading-zero octal parsing bugs.

3. `ip_to_int`: Conversion of dotted-decimal IPv4 to unsigned 32-bit integers.
4. `calculate_subnet`: CIDR subnet mathematics calculating Network Address, Broadcast Address, and Usable Host count via `local -n` name references.
5. `ping_latency`: ICMP probe extracting round-trip latency via regular expression matching `${BASH_REMATCH[1]}`.

### Full Source Code: `linux-mastery/scripts/12_network_math_lib.sh`

```bash
#!/usr/bin/env bash

# ==============================================================================
# LIBRARY  : 12_network_math_lib.sh
# TRACK    : Mastering Shell Scripting & Automation — Day 12/30 (Week 10)
# JOURNEY  : Day 268 / 1000
# PURPOSE  : Modular IPv4 Validation, Integer Conversion, and CIDR Math Library
# USAGE    : source ./12_network_math_lib.sh
# ==============================================================================

# Guard against double-sourcing
if [[ -n "${_NETWORK_MATH_LIB_LOADED:-}" ]]; then
    return 0
fi
_NETWORK_MATH_LIB_LOADED=1

# ------------------------------------------------------------------------------
# 1. IPV4 FORMAT & BOUNDARY VALIDATION
# ------------------------------------------------------------------------------
# Validates whether a given string is a syntactically valid IPv4 address.
# Returns 0 on valid IPv4, 1 on invalid format or out-of-range octet.
validate_ip() {
    local ip="${1:-}"
    local IFS='.'
    local -a octets

    [[ -n "$ip" ]] || return 1

    read -r -a octets <<< "$ip"

    # IPv4 must have exactly 4 octets
    [[ ${#octets[@]} -eq 4 ]] || return 1

    local octet
    for octet in "${octets[@]}"; do
        # Each octet must be 1 to 3 decimal digits
        [[ "$octet" =~ ^[0-9]{1,3}$ ]] || return 1

        # Must be between 0 and 255. Use base-10 (10#$octet) to prevent octal errors on leading zeroes
        (( 10#$octet <= 255 )) || return 1
    done

    return 0
}

# ------------------------------------------------------------------------------
# 2. INTEGER TO IPV4 CONVERSION (Approach A: Command Substitution)
# ------------------------------------------------------------------------------
# Converts an unsigned 32-bit integer (0 - 4294967295) to dotted-decimal IPv4 string.
# Emits dotted IP string to stdout. Returns 0 on success, 1 on invalid input.
int_to_ip() {
    local number="${1:-}"

    [[ "$number" =~ ^[0-9]+$ ]] || return 1
    (( number <= 4294967295 )) || return 1

    printf '%d.%d.%d.%d\n' \
        "$(( (number >> 24) & 255 ))" \
        "$(( (number >> 16) & 255 ))" \
        "$(( (number >> 8) & 255 ))" \
        "$(( number & 255 ))"
}

# ------------------------------------------------------------------------------
# 3. IPV4 TO INTEGER CONVERSION (Approach A: Command Substitution)
# ------------------------------------------------------------------------------
# Converts a dotted-decimal IPv4 address into its unsigned 32-bit integer representation.
# Emits 32-bit unsigned integer to stdout. Returns 0 on success, 1 on invalid input.
ip_to_int() {
    local ip="${1:-}"
    validate_ip "$ip" || return 1

    local IFS='.'
    local -a octets
    read -r -a octets <<< "$ip"

    printf '%u\n' "$(( (10#${octets[0]} << 24) + (10#${octets[1]} << 16) + (10#${octets[2]} << 8) + 10#${octets[3]} ))"
}

# ------------------------------------------------------------------------------
# 4. CIDR SUBNET CALCULATION (Approach B: Name References declare -n)
# ------------------------------------------------------------------------------
# Calculates network address, broadcast address, and usable host count.
# Modifies caller variables directly in place via name references without subshell overhead.
# Usage: calculate_subnet <ip> <prefix> <network_var> <broadcast_var> <hosts_var>
calculate_subnet() {
    local _cs_ip="$1"
    local _cs_prefix="$2"
    local -n _cs_net_ref=$3
    local -n _cs_bcast_ref=$4
    local -n _cs_hosts_ref=$5

    validate_ip "$_cs_ip" || return 1
    [[ "$_cs_prefix" =~ ^[0-9]{1,2}$ ]] || return 1
    (( _cs_prefix >= 0 && _cs_prefix <= 32 )) || return 1

    local _cs_ip_int
    _cs_ip_int=$(ip_to_int "$_cs_ip") || return 1

    local _cs_mask_int _cs_net_int _cs_bcast_int _cs_calc_hosts

    if (( _cs_prefix == 32 )); then
        _cs_mask_int=4294967295
        _cs_calc_hosts=1
    elif (( _cs_prefix == 0 )); then
        _cs_mask_int=0
        _cs_calc_hosts=4294967294
    else
        _cs_mask_int=$(( (0xFFFFFFFF << (32 - _cs_prefix)) & 0xFFFFFFFF ))
        _cs_calc_hosts=$(( (1 << (32 - _cs_prefix)) - 2 ))
    fi

    _cs_net_int=$(( _cs_ip_int & _cs_mask_int ))
    _cs_bcast_int=$(( _cs_net_int | (~_cs_mask_int & 0xFFFFFFFF) ))

    _cs_net_ref=$(int_to_ip "$_cs_net_int")
    _cs_bcast_ref=$(int_to_ip "$_cs_bcast_int")
    _cs_hosts_ref="$_cs_calc_hosts"

    return 0
}

# ------------------------------------------------------------------------------
# 5. ICMP PING LATENCY MEASUREMENT
# ------------------------------------------------------------------------------
# Sends a single probe and extracts round-trip latency in milliseconds.
# Emits "<latency> ms" to stdout. Returns 0 on success, 1 on unreachable host or error.
ping_latency() {
    local host="${1:-}"
    local output

    [[ -n "$host" ]] || return 1

    # Probe host with single packet (supporting Linux -c and Windows -n fallback)
    output=$(ping -c 1 -W 2 "$host" 2>/dev/null) || \
    output=$(ping -n 1 -w 2000 "$host" 2>/dev/null) || return 1

    # Match timing payload across standard ping implementations (Linux and Windows)
    local regex='time[=<]([0-9.]+)[[:space:]]*ms'
    local fallback_regex='time=([0-9.]+)'

    if [[ "$output" =~ $regex ]]; then
        printf '%s ms\n' "${BASH_REMATCH[1]}"
        return 0
    elif [[ "$output" =~ $fallback_regex ]]; then
        printf '%s ms\n' "${BASH_REMATCH[1]}"
        return 0
    else
        return 1
    fi
}
```

# 10. Technical Interview Scenarios (Questions & Answers)

### Q1: What is the exact difference between `return` and `exit` inside a Bash function?
**Answer:**
- `return N` terminates **only the function**, yielding exit code `N` to the calling shell environment, allowing script execution to continue.
- `exit N` terminates the **entire shell process** immediately, aborting the script regardless of how deeply nested the function call is.

### Q2: What happens if a function attempts to return the number 300 via `return 300`?
**Answer:** Linux exit statuses are stored as an 8-bit unsigned integer ($0$–$255$). Any value $\ge 256$ undergoes modulo-256 arithmetic. `return 300` yields $300 \pmod{256} = 44$. If a function attempts `return 256`, it returns $256 \pmod{256} = 0$, falsely reporting complete success.

### Q3: Why should variables inside functions always be declared with `local`?
**Answer:** In Bash, all variables are global by default. Declaring variables without `local` pollutes the global shell environment and overwrites identically named variables in the parent script or other functions, causing catastrophic state mutations that are notoriously difficult to debug.

### Q4: Explain the difference between Lexical Scoping and Dynamic Scoping in Bash.
**Answer:**
- In **Lexical Scoping** (used by Python, Go, JavaScript), variable visibility is resolved statically based on the lexical structure and location of definitions in the source code.
- In **Dynamic Scoping** (used by Bash), variable visibility is resolved at runtime based on the **call stack**. A `local` variable declared in `funcA()` remains visible to any subsequent function `funcB()` invoked by `funcA()`, unless shadowed.

### Q5: How do Command Substitution (`$()`) and Name References (`declare -n`) differ in performance and memory side-effects?
**Answer:**
- Command substitution (`$()`) forks a child process (subshell) to execute the function and capture its stdout stream via an OS pipe. It has higher process creation overhead and **cannot** modify caller variables.
- Name references (`declare -n`) execute inside the current shell without forking child processes. They alias the caller's variables directly in memory, permitting instant, high-performance in-place mutation of multiple variables.

### Q6: What is the "Name Collision Trap" when using `local -n` in Bash libraries, and how do you protect against it?
**Answer:** If a function declares `local -n ref=$1`, and also declares an internal local variable (e.g. `local val=5`), and the caller happened to pass a variable named `"val"`, the name reference collides with the function's internal local variable instead of referencing the caller's variable. To protect against this, library functions must namespace all internal variables (e.g., `local _lib_val=5`).
